# 오디오에서 코드 읽기

WAV 나 스템을 불러서 **무슨 코드인지** 알아내는 기능. 편곡의 출발점이 되는 것.

## 결정된 것

| | |
|---|---|
| **기본 어휘** | **7화음** — maj/min/dom7/maj7/min7/dim/m7b5/sus 등 |
| **정확도 우선** | 분리 엔진을 먼저 돌립니다 (드럼 제거) |
| **표기** | `C`, `Am7`, `G7` — 절대 코드명. 로마숫자 안 씁니다 |

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| **A** | CQT + 튜닝 추정 + 크로마 | **완료** |
| **B** | 템플릿 매칭 + 비트 동기 + 코드 트랙 기록 | **완료** |
| **C** | HMM / 비터비 평활 | **완료** |
| **D** | 벤치마크 커맨드 + 실제 음원 측정 | **완료 (커맨드)** — 진짜 음원 숫자는 사용자 차례 |

# A단계 — 크로마

**크로마**는 12개 숫자입니다. 지금 도가 얼마나, 도샾이 얼마나, 레가 얼마나
울리고 있는가. 이 아래로는 전부 룩업 테이블이고, **크로마가 틀리면 코드가
틀립니다** — 어떤 템플릿도 어떤 HMM 도 변환이 버린 정보를 되살리지 못합니다.

## 왜 기존 STFT 로는 안 되는가

이 저장소에는 이미 완전 복원 가능한 STFT 가 있습니다(`stft.ts`). 스펙트럴
에디팅용이고, **주파수가 선형**입니다. 음악은 로그입니다.

스펙트럴 에디터가 쓰는 2048 포인트로 44.1 kHz 를 보면 빈 간격이 21.5 Hz 입니다.
베이스가 사는 동네에서:

```
E2 = 82.41 Hz     F2 = 87.31 Hz     →  4.9 Hz 차이
```

**인접한 두 반음이 같은 빈에 들어갑니다.** E 와 F 를 구분 못 하는 변환은 Am 과
Dm 을 구분할 수 없고, 그건 나중에 아무리 영리해져도 복구가 안 됩니다.

FFT 크기를 키워도 해결이 안 됩니다. C1(32.7 Hz)에서 반음을 분해하려면 창이
**1.5초**쯤 필요한데, 1.5초짜리 창은 곡의 모든 코드 체인지를 뭉갭니다.
요구조건이 모순인 건 **창 길이가 하나여야 할 때뿐**이고, 상수-Q 변환은 정확히
그 가정을 버립니다.

## 상수-Q

Q = 중심주파수 / 대역폭. 이걸 **상수로 유지**한다는 건 모든 빈이 같은 **센트**
폭을 갖는다는 뜻입니다 — 80 Hz 빈은 헤르츠로 좁고 3 kHz 빈은 넓습니다. 사람 귀가
하는 일이고, "반음당 한 빈"이 요구하는 것입니다. 대가는 **빈마다 창 길이가
다르다**는 것.

순진하게 하면 프레임마다 빈마다 필터 하나 → 4분짜리 곡에는 너무 느립니다.
그래서 **Brown-Puckette 스펙트럴 커널**을 씁니다: 각 기저함수를 빌드 타임에 한 번
FFT 도메인으로 옮기면 거의 전부 0인 좁은 봉우리가 됩니다. 봉우리만 남기면
**희소 행렬**이 되고, 변환 전체가

```
프레임당 FFT 한 번  →  희소 행렬 곱 한 번
```

이 됩니다. 실측: 커널이 전체 가중치의 **0.4 %** 만 유지. 22 kHz 에서
**실시간의 56 배**.

## 반음당 3빈인 이유 — 튜닝

레코드가 전부 A=440 이 아닙니다. 아날로그 테이프는 흐르고, 오케스트라는 442 로
맞추고, 옛날 음원은 이유 없이 사분음 어긋나 있고, 귀로 피치 맞춘 샘플은
어디든 갑니다.

40센트 샤프한 곡을 그냥 12빈으로 접으면 **모든 음이 에너지 대부분을 옆 음으로
흘립니다.** 크로마가 지저분한 게 아니라 **체계적으로 틀리고**, 아래쪽에서는
그걸 알 방법이 없습니다.

반음당 3빈이면 봉우리가 자기 반음 **안에서 어디쯤인지** 잴 수 있습니다. 파일
전체에서 재서 축을 밀어놓고 접습니다.

**투표는 각도로 평균냅니다.** 이 양은 반음마다 순환하기 때문에, +49센트인
봉우리와 −49센트인 봉우리는 2센트 차이지 98센트 차이가 아닙니다. 산술평균을
내면 0 이 나오는데, 그건 확실히 틀린 유일한 답입니다.

실측 (±8센트 이내):

```
   -47 →  -46.6      -17 →  -16.6       31 →   31.4
   -40 →  -39.5        0 →    0.3       47 →   47.3
```

## 배음 억제 — 톱니파 도가 C7 로 읽히는 문제

톱니파 C 하나의 배음은 C(×2), G(×3), C(×4), **E(×5)**, G(×6), **B♭(×7)** 입니다.
그냥 접으면 **음 하나가 C7 로 읽힙니다** — 아무도 안 친 코드죠. 템플릿 매처에서
3음과 7음이 틀리는 가장 큰 원인이 이겁니다.

그래서 억제는 **뺄셈**입니다: 더 낮은 배음이 **예측하는** 에너지를 접기 전에
제거합니다. 더하기(하모닉 합)로 하면 진짜 있는 근음도 강화하고 **없는 근음도**
강화합니다 — 베이스에 5도만 있고 근음이 없으면 그게 근음이 돼버립니다.

배음 8번까지 봅니다. 5번(장3도)에서 멈춰봤더니 부족했습니다 — 톱니파 C 가
여전히 **B♭ 8.5 %**(7번 배음), F♯ 3.6 %(11번), G♯ 3.6 %(13번)을 냈습니다.
7번 배음이 결정적입니다. **단7도**라서, 남겨두면 모든 3화음이 도미넌트로 보입니다.

## 파라미터는 재서 골랐습니다

억제 강도 × 감마를 훑어서:

```
0.5 / 3   단일 C   → C 0.98, 다음 0.10
          C major  → C, E, G 전부 0.58, 다음 0.05
          C minor  → C, D♯, G 전부 0.58
          Cmaj7    → C, E, G 0.51 과 B 0.47
          C7       → C, E, G 0.51 과 A♯ 0.47, 상위 5개에 B 없음
```

억제가 낮으면(0.3) 배음열의 3도·5도가 남고, 높으면 배음과 겹치는 **진짜 5도**를
먹을 위험이 있습니다.

## 로그 압축에서 한 번 크게 틀렸습니다

처음엔 `log(1 + 100·x)` 를 **원시 CQT 크기**에 걸었습니다. 그 값들은 수천
단위입니다. 결과:

```
원시:   C 75.3 %   A♯ 8.5 %      (8:1)
압축 후: C 0.43     A♯ 0.36       (1.2:1)
```

압축이 **조용한 음을 들어올린 게 아니라, 모든 음과 모든 잡음의 차이를
지우고 있었습니다.** `log(1 + γ·x)` 는 x 가 이미 0…1 일 때만 의미가 있습니다.
지금은 접은 뒤 최댓값으로 나누고 나서 γ=3 으로 압축합니다.

## 무음은 0 입니다

정규화된 잡음이 아니라 진짜 0. 상대 기준(파일에서 제일 큰 프레임의 2 %)만
쓰면 **잡음만 든 파일**에서는 제일 큰 프레임이 잡음이라 2 % 는 잡음보다
조용합니다. 실측: ±1e-7 디더 파일이 12음 크로마를 자신 있게 내놨습니다.
지금은 절대 기준(−80 dBFS RMS)도 같이 봅니다.

## 셀프테스트

```
pnpm --filter @aimaster/desktop test:chroma      # 18개
```

재는 것:

- 사인파가 **자기 피치클래스**에 떨어지는가 — C2~B6 전 음역 49개 전부
- **E2 와 F2 가 다른 음**으로 나오는가 (STFT 가 못 하는 바로 그것)
- 30센트 샤프한 곡을 30센트 샤프하다고 재고, 보정 후 크로마가 원래 조율된
  곡만큼 깨끗한가
- 톱니파 C 가 **C 로 읽히는가, C7 로 읽히는가**
- 3화음이 세 음으로 균형 있게 읽히는가 / 마이너가 메이저가 아닌가
- **7음이 보이는가** (사용자가 고른 기본 어휘가 요구하는 것)
- 무음이 0 인가 / 32 dB 차이 나는 같은 코드가 같은 벡터인가
- 곡에 쓸 수 있을 만큼 빠른가

일곱 개를 **일부러 망가뜨려서** 전부 잡히는 것을 확인했습니다: 튜닝 시프트
부호 뒤집기, 원시 크기에 압축 걸기, 배음 억제 끄기, 반음당 1빈으로 줄이기,
조밀 커널 만들기, 분석 시작을 C 가 아닌 A 로 옮기기, 그리고 순환평균을
산술평균으로 바꾸기.

**마지막 건 처음에 안 잡혔습니다.** 튜닝 테스트가 −40~+31 만 쓰고 있어서,
±50센트 **경계 근처**를 한 번도 안 밟았습니다. 순환평균이 산술평균과 달라지는
건 거기뿐입니다. ±47 을 추가하니 잡혔습니다.

## 이 단계의 한계

- **C2 부터** 봅니다. C1 빈은 이 Q 에서 창이 1.5초쯤 필요한데 웬만한 코드보다
  깁니다. 코드의 저음 끝은 나중에 **베이스 스템**에서 따로 읽습니다.
- 억제 강도 0.5 는 **배음과 겹치는 진짜 조용한 음**을 조금 먹습니다. 트레이드
  오프고, 파라미터로 열어뒀습니다.
- 여기까지는 **크로마일 뿐 코드가 아닙니다.** 코드는 B단계.

# B단계 — 코드

크로마 12개 숫자에서 **코드 이름**까지. A단계 끝에 "여기까지는 크로마일 뿐
코드가 아닙니다"라고 썼던 그 부분입니다.

```
크로마 (0.1초마다)  →  비트별 평균  →  템플릿 매칭  →  런 병합  →  코드 차트
```

## 왜 코사인 × 이진 템플릿인가

템플릿은 그 코드의 음을 1, 나머지를 0 으로 놓고 **L2 정규화**한 벡터입니다.
점수는 내적, 즉 코사인.

이 선택이 공짜로 해주는 일이 하나 있습니다. **C7 은 C 장3화음을 포함합니다.**
맞은 음 개수만 세면 3화음 위에서는 3화음이(세 음 다 있으니까), 7화음 위에서도
3화음이 이깁니다. 템플릿 자기 크기로 나누면 양방향이 동시에 풀립니다:

```
진짜 3화음  →  3화음 1.000,  7화음 0.866
진짜 7화음  →  7화음 1.000,  3화음 0.866
```

**부분집합도 상위집합도 진실에게 집니다.** 손으로 쓴 규칙이 필요 없습니다.

## 어휘 = 정확도 다이얼

`basic` 24개(maj/min) · `sevenths` **168개** · `full` 264개.

사용자가 고른 **7화음이 기본값**입니다. 값은 있습니다: 7음은 대부분의 보이싱에서
제일 조용한 음이고, **m7 과 그 관계장조의 6화음은 같은 네 음**입니다.

## 베이스가 결정적인 이유

```
Am7 = A C E G
C6  = A C E G      ← 완전히 같음
```

어떤 크로마도 이 둘을 구분 못 합니다. **베이스가 완전히 구분합니다.**

실측으로 확인했습니다. 베이스 없이 `Cmaj7 Am7 Dm7 G7` 을 넣으면

```
Cmaj7  C6  F6  G7      ← 같은 음, 같은 소리, 틀린 차트
```

가 나왔습니다. 그래서 베이스 스템이 없을 때는 **믹스에서 제일 낮은 음**을
직접 읽습니다(`lowestPitchClass`). 스템만은 못하지만 없는 것보다 훨씬 낫고,
이걸 넣자 위 진행이 100 % 로 돌아왔습니다.

가중치는 0.1 — 근음이 베이스면 만점, 그냥 포함만 하면 절반(전위). 코드와
자기 템플릿의 코사인이 0.85~1.0, 이웃 코드와는 0.75~0.9 이므로 그 간극 크기.

## 비트 동기 — 가장 큰 정확도 이득

크로마는 초당 10번 나옵니다. 코드는 한 마디 갑니다. 프레임마다 매칭해서 찍으면
**항목 400개짜리 차트**가 나오고 대부분 정답과 그 이웃 사이에서 깜빡입니다.

비트로 평균내면 두 가지가 겹쳐서 좋아집니다: 한 번의 결정에 **10배의 증거**가
쌓이고, 개별 프레임을 틀리게 만드는 **아르페지오·경과음·꾸밈음**이 바로 평균이
지우는 것들입니다.

그리고 결과가 **편집 가능**해집니다. 비트에서 시작하는 코드는 끌고 다시 칠 수
있고, 12.7314초에서 시작하는 코드는 못 합니다.

템포를 못 믿을 때(신뢰도 0.35 미만)는 고정 창으로 떨어지고 **그렇다고 말합니다**
— 없는 그리드를 있는 척 덮어씌우지 않습니다.

실측 — 틀린 그리드의 대가는 **이름이 아니라 위치**입니다:

```
맞는 그리드:  코드 체인지가 실제 위치에서 0.000 초
137 % 그리드:                      0.230 초
```

## 스탭이 드러낸 버그

가장 크게 틀렸던 곳입니다. `C G Am F` 를 **마디의 1/4 만 치는 스탭**으로 넣으면

```
C  C  Am  Am        ← G 와 F 가 통째로 사라짐
```

원인이 두 개 겹쳤습니다.

1. 스탭의 **꼬리가 자기 메이저 7화음으로 읽힙니다.** 감쇠하면서 배음 균형이
   바뀌어서요. 그래서 `G` 한 비트 + `Gmaj7` 한 비트로 **쪼개집니다.**
2. `minBeats` 가 **매칭된 비트 수**를 셌습니다. 둘 다 1비트라 둘 다 버려지고,
   앞의 C 가 그 구멍 위로 늘어났습니다.

주석에는 이미 "짧은 구간은 **이웃에 흡수된다**"고 써 있었는데 코드는 그냥
버리고 있었습니다. 고친 내용:

- **흡수하되 버리지 않습니다.** 살아남는 이름은 **증거가 더 많은 쪽** — 점수를
  비트에 걸쳐 **합산**해서 비교합니다. 그래서 8비트짜리 C 가 1비트 F#dim7 을
  이기고, 똑같이 짧은 둘 사이에서는 **깨끗한 어택이 뭉개진 감쇠를 이깁니다.**
- 길이는 **덮는 범위**로 잽니다 — 시작부터 **다음 코드가 시작할 때까지**. 한 번
  치고 울리게 둔 코드는 마디의 대부분이 무음이고, **그래도 그 마디 내내 그
  코드입니다.**
- 무음인 이웃이 없는 짧은 런은 흡수할 곳이 없으므로 버립니다(진짜 블립).

이후 실측:

```
1/4마디 스탭:   100 %   C G Am F
마디당 한 방:   100 %   C G Am F   (덮는 범위 [4,4,4,5] 비트)
```

한계도 쟀습니다. **1/14 마디**(0.17초)까지 줄이면 50 % 로 무너집니다
(`Cmaj7 G Am Fmaj7`) — 그 길이에서는 어택 스펙트럼이 코드보다 크게 나옵니다.

## 튜닝 보정이 정말 일을 하는지

A단계에서 만든 보정이 **실제로 값을 하는지**는 따로 재야 합니다. 30센트에서는
**이름만 봐서는 안 보입니다** — 베이스 판독이 손상된 크로마에서도 정답을
건져내기 때문입니다. 그래서 두 군데를 잽니다:

```
30센트: 매칭 점수  보정 1.069  vs  무보정 0.974      (증거가 나빠짐)
45센트: 정확도     보정 100 %  vs  무보정 0 %
                   무보정 결과: C#mMaj7/C  C#mMaj7/C  Fmaj7/A  A#mMaj7/F
```

45센트는 이국적인 값이 아닙니다. 빨리 돈 테이프, 귀로 피치 맞춘 샘플.

## 불확실한 건 불확실하다고

`margin` — 2등과의 격차. **0.95 인데 2등을 0.001 차로 이긴 건 앞면이 예쁜
동전던지기입니다.** 0.04 미만인 구간 수를 리드아웃에 실어 보냅니다.
90마디를 다 검산할 수는 없어도 **6마디는 검산할 수 있으니까요.**

흡수 대신 버리기 · 흡수된 런이 절대 이름을 못 가져가게 하기 ·

어휘 바꾸기는 **체인 배선까지** 확인하는 용도였습니다. 이번 세션에서 이미 두 번
빠뜨린 실수(`test:instrument-presets`, `test:sampler`)라서, package.json 에
넣은 뒤 진짜로 깨서 **종료 코드 1** 이 나오는 것을 확인했습니다. `&&` 체인은
거기서 멈춥니다.

워커 드리프트는 **처음에 안 잡혔습니다** — 주석만 고쳤는데 esbuild 가 주석을
지워서 번들이 한 글자도 안 바뀌었습니다. **망가뜨리기가 실패한 것이지 검사가
실패한 게 아니었습니다.** 진짜 코드를 고치니 잡혔습니다.

**끝까지 잡히지 않은 하나는 테스트가 아니라 코드에 대한 발견이었습니다.**
**무음 프레임을 평균에 넣어도 매칭이 안 바뀝니다.** 주석은 "임계값에 진다"고
주장하고 있었는데 **거짓말이었습니다.** 0 을 같이 세면 벡터 전체가 균일하게
작아질 뿐이고, 소비자가 전부 스케일 불변입니다(`matchChord` 는 내적 전에
정규화, `bassPitchOf` 는 비율 비교). **20배 범위에서 점수·마진이 비트 단위로
동일**한 것을 확인했습니다. 주석을 사실대로 고쳤습니다.

## 통과하면서 아무것도 안 재던 검사

망가뜨리기와 별개로, **자기가 찍은 숫자에 스스로 반박하는** 검사가 하나
있었습니다. 이름은 "틀린 비트 그리드는 정확도를 깎는다"인데 출력은
`wrong grid 100%` 였습니다. 실제로 단언하는 것은 대조군이 통과했다는 것뿐이었고요.

이 코드들은 한 마디씩 가므로 그리드가 틀려도 **마디 한가운데서 읽은 이름은
살아남습니다.** 틀린 그리드가 부수는 건 이름이 아니라 **위치**입니다 — 그리고
위치야말로 차트를 편집 가능하게 만드는 것이죠. 지금은 위치를 잽니다.

## 세션에 쓰기 — 누를 곳

**기능이 있는데 누를 데가 없으면 없는 것과 구별이 안 됩니다.** 그래서 코드
레인 헤더에 **`오디오에서`** 버튼이 있습니다. 재생헤드 아래의 오디오 클립을
읽어서 코드 트랙에 씁니다.

**분리가 먼저 돕니다** — 사용자가 고른 "정확하게"가 사는 곳입니다. 두 가지를
삽니다: 드럼이 매칭에서 **빠지고**(스네어는 12개 피치클래스에 동시에 떨어지는
광대역 에너지입니다), 베이스 스템이 베이스 판독으로 **들어옵니다**. 느립니다.
분리가 거부하면 **거부 이유를 말하고 믹스로 분석합니다** — 조금 덜 정확한
차트가 차트 없음보다 낫습니다.

**템포는 세션에서 가져오되 위상을 계산합니다.** 클립이 마디 중간에서 시작하면
그 첫 샘플은 다운비트가 아닙니다. `beatPhaseFor` 가 클립 시작점에서 다음
비트까지의 거리를 냅니다 — 이걸 틀리면 차트의 모든 경계가 박에서 벗어납니다.

**덮어쓰기는 자기 구간에서만.** 코드는 **시작점만** 저장하므로, 한 구간에
두 차트가 겹치면 "의견 두 개"가 아니라 **둘 다 아닌 하나**로 엇갈립니다.
구간 밖은 전부 보존합니다 — 2절을 분석했다고 1절이 지워지면 안 되니까요.
일부러 append 로 바꿔보면 이렇게 나옵니다:

```
0:C 4:F 8:Am 8:Am7 10:D7 12:G 14:Gmaj7 18:Dm
```

## UI 스레드에서 내려보냈습니다

버튼을 붙이고 나서 잰 숫자가 문제를 드러냈습니다:

```
30초 @ 44.1 kHz  ->  2525 ms
60초 @ 44.1 kHz  ->  2078 ms   (실시간의 28.9배)
```

4분짜리 클립이면 **8초**입니다. 8초 동안 창이 안 그려지는 건 이 저장소가
분리 엔진에서 이미 내린 판단 그대로 **멈춘 것과 구별이 안 됩니다.** 게다가 더
나쁜 게 있습니다 — 메인 스레드가 막히면 **버튼이 보여주려는 진행률이 절대
안 그려집니다.** 바쁜 게 아니라 죽은 것처럼 보이죠.

그래서 분리 워커와 **똑같은 경로**로 내렸습니다: `worker-entry.ts` 를
`public/chord.worker.js` 로 번들하고, 텍스트로 fetch 해서 Blob 으로 Worker 를
만듭니다(패키징된 빌드는 `file://` 이라 `new Worker(url)` 을 크로미움이
거부합니다). 워커가 안 뜨면 **인라인으로 돌리고 그렇다고 말합니다.**

생성 파일은 커밋되므로(`pnpm dev` 가 그냥 돌아야 하니까) **드리프트 검사**가
같이 있습니다 — 분리 워커가 갖고 있는 것과 같은 장치입니다.

못 쟀습니다.**

# C단계 — 비트마다가 아니라 한꺼번에

B단계는 각 비트를 혼자 판단했습니다. 이 단계는 그걸 고칩니다. "평활을 추가한다"는
말이 마감 작업처럼 들리는데 **아닙니다.**

## 먼저: 뭐가 틀리는지 쟀습니다

고칠 게 없으면 평활은 증명이 안 됩니다. 그래서 어려운 재료를 12가지 만들어서
B단계를 돌려봤습니다. 답은 명확했습니다 — **아르페지오**.

```
블록 코드, 1마디씩        100%
아르페지오, 1마디씩        25%   C C C C
아르페지오 + 드럼           0%   Csus2 Gmaj7 Gmaj7 Gmaj7
16코드 아르페지오          19%   C C C C C C C C C C C C C C C C
재즈 아르페지오             0%   Am Am Am Am Am Am Am Am
```

**16개 코드가 전부 C 하나로 뭉개졌습니다.** 이건 "비트 판단이 좀 흔들린다"가
아니라 붕괴입니다. 원인을 파봤더니 **B단계 버그가 두 개** 나왔습니다.

### 버그 1 — 믹스 최저음이 슬래시 코드를 만들고 있었습니다

아르페지오에는 베이스가 따로 없습니다. 매 순간 "제일 낮은 음"은 **패턴이 지금
도달한 코드 구성음**일 뿐입니다. 실측한 프레임별 최저음:

```
C마디:  C C C C E E E G G C C C C E E E
G마디:  B B B B D D D G G G B B B D D
```

이게 베이스로 읽히면 매 비트가 `G`, `G/B`, `G/D` 로 **이름이 셋**이 됩니다.
이름이 다르면 런이 쪼개지고, 쪼개진 런은 전부 minBeats 미만이 됩니다.

### 버그 2 — 흡수가 폭주했습니다

B단계에서 넣은 "짧은 런은 이웃에 흡수"가, **모든 런이 짧으면** 연쇄합니다.
흡수될 때마다 이긴 쪽의 점수합이 커지고, 커진 쪽이 다음 흡수도 이깁니다.
부익부. 그래서 16마디가 C 하나가 됐습니다.

**두 버그 다 B단계 테스트가 못 잡았습니다** — 그 테스트의 재료가 전부 블록
코드였고, 블록 코드는 최저음이 안 움직이기 때문입니다.

## 모델

숨은 마르코프 모델. 상태는 어휘의 코드 168개 + **"코드 없음" 하나**.
방출은 B단계가 이미 계산하는 템플릿 점수. 비터비가 **가장 그럴듯한 경로**를
찾습니다 — 이건 **가장 그럴듯한 답들의 나열과 다른 질문**입니다.

숫자가 **두 개뿐**인 데는 이유가 있습니다.

교과서 HMM 은 N×N 전이 행렬을 씁니다. 그런데 비대각을 균등하게 두면 —
어떤 코드 변화든 똑같이 일어날 수 있다고 보면 — 그 행렬은 **숫자 하나로
붕괴합니다**:

```
log p(유지) − log((1 − p(유지)) / (N − 1))
```

그러니 `switchCost` 는 모델의 단순화가 아니라 **모델 그 자체**입니다. 어떤
코드 다음에 어떤 코드가 오는지 안다고 주장하지 않는 한.

구현은 O(N) — 자기 자신이 아닌 모든 상태의 최적 선행자는 **전부 같습니다**
(전역 최대). 그래서 O(N²) 이 아니라 O(N) 이고, 4분짜리 곡이 즉시 끝납니다.

## 세 번째 숫자 — 여분의 음은 값을 해야 합니다

여기서 실제로 뭘 발견했습니다. 아르페지오 C장3화음이 **Cmaj7 으로 읽힙니다.**
어디에도 잘못이 없는데요.

**3음이 혼자 울리면 자기 3배음이 근음의 장7도입니다.** E 의 3배음이 B 입니다.
블록 코드에서는 다른 음에 묻히는데, 아르페지오에서는 안 묻힙니다.

측정으로 확인했습니다 — 렌더한 오디오, 페널티만 껐다 켰다:

```
아르페지오 C장3화음:  페널티 없이 Cmaj7   →   페널티 켜면 C
```

그래서 `sizePenalty`: 3화음을 넘는 구성음마다 점수에서 뺍니다. 꼼수가 아니라
**진짜 비대칭의 보정**입니다 — 4음 템플릿은 사고가 떨어질 자리가 하나 더 있고,
아르페지오 음악에서 그 사고는 **체계적**입니다.

## 다른 길로 가봤다가 접었습니다

배음 억제를 0.5 → 0.7 로 올리면 전체 라벨 정확도가 48 % → 66 % 로 뜁니다.
매력적이죠. **그런데 A단계 셀프테스트가 깨졌습니다**:

```
[FAIL] 30센트 샤프한 단일 C 가  G 0.69  C 0.69  로 읽힘
```

**단일 음이 두 피치클래스로 읽히면** 그 아래 전부가 무너집니다. 크로마는
토대라서 여기서 타협하면 안 됩니다. 그래서 억제는 0.5 그대로 두고, 크로마를
안 건드리는 `sizePenalty` 로 같은 문제를 잡았습니다 — 48 % → **73 %**.

## 파라미터는 두 번 쟀습니다

`(sharpness, switchCost)` 를 7×8 격자로 훑고, **이긴 조합을 다시 전체 파이프라인**
으로 확인했습니다. 스윕은 디코더만 채점하고 사용자는 파이프라인을 쓰니까요.

```
sharpness 10, switchCost 1.5, sizePenalty 0.02
```

전체 파이프라인 비교 (정확 라벨 합계): 10/1.5 → **938**, 12/2.4 → 901,
10/2 → 901, 12/1.5 → 901.

## 세 가지로 나눠서 잽니다

처음엔 "정확한 라벨"만 쟀는데, 그 지표가 **성공을 가리고 있었습니다.** 평활이
`C G Am F` 의 마디 경계를 완벽하게 잡았는데도 `Cmaj7` 이라 0점이었거든요.
코드 인식은 원래 세 층으로 잽니다:

```
                근음    3화음    전체 라벨
B단계 (비트별)   68 %    62 %     49 %
C단계 (평활)     83 %    81 %     75 %
```

**평활은 "어느 코드인가"를 크게 고치고, sizePenalty 가 "7화음인가"를 고칩니다.**

## 최종 실측 — 처음의 그 재료로

```
                          B단계 → C단계
블록 코드, 1마디씩          100% → 100%
아르페지오, 1마디씩          25% → 100%
아르페지오, 2비트씩          25% → 100%
아르페지오 + 드럼             0% → 100%
16코드 아르페지오            19% → 100%
16코드 아르페지오 + 드럼       0% → 100%

아르페지오 + 멜로디           25% →   0%   ← 유일한 후퇴
```

**마지막 줄은 숨기지 않습니다.** 아르페지오 위에 8분음표 스케일 멜로디가
얹히면 음의 절반이 화음 밖입니다. 근음 기준으로는 25 % → 50 % 로 오르지만
정확 라벨은 0 % 입니다 — 평활이 **틀린 답을 안정적으로** 만들어버립니다.
평활의 진짜 위험이 이거고, 그래서 적어둡니다.

## 일부러 안 만든 것

**음악을 아는 전이 행렬** — V→I 가 V→♭II 보다 흔하다는 것 — 이 없습니다.
이유가 있습니다: 그건 **조성에 상대적으로만** 의미가 있는데 이 검출기는 조를
추정하지 않습니다. 조 없이 넣으면 그건 "음악 지식"이 아니라 **C장조 편향**이고,
개발자가 테스트하는 재료에서만 좋아지고 나머지 전부에서 나빠집니다.

정직한 순서는: 조를 추정하고 → 전이를 조에 조건화하고 → **재서 도움이 됐는지
확인**. 그건 그것대로 한 단계입니다.

# D단계 — 진짜 음원에서 재기

A~C 단계가 인쇄한 정확도는 **전부 이 저장소가 스스로 렌더한 오디오**에서 나왔습니다.
자기가 쓴 악기로, 자기가 고른 진행을 연주한 것. 코드가 주장대로 동작하는지는
공정하게 재지만, **레코드에서 어떤지는 말해주지 못합니다.** 합성 재료를 아무리
어렵게 만들어도 레코드가 되지는 않습니다 — 리버브 꼬리가 코드를 다음 코드로
번지게 하고, 기타가 보컬을 3도 위로 겹쳐 치고, 프로듀서가 좋다는 이유로 sus4 를
세 마디 걸어둡니다.

```
pnpm --filter @aimaster/desktop benchmark:chords "~/Music/annotated"
pnpm --filter @aimaster/desktop benchmark:chords "~/Music/song.wav"
```

## 아무것도 기기 밖으로 나가지 않습니다

오디오는 읽고, 재고, 버립니다. 나오는 건 숫자표와 코드 차트뿐. 곡 폴더는
누군가의 음악이고, **"파일 좀 보내주세요"는 "진짜 음악에서 얼마나 잘 되나요"의
답이 아닙니다.** 분리 벤치마크가 이미 택한 규칙 그대로입니다.

## 정답 파일 — `.lab`

세 열, 한 줄에 코드 하나. **Harte 문법**이고, 공개 정답 세트가 전부 이걸로
쓰여 있습니다 — Isophonics(비틀즈·퀸), McGill Billboard, RWC Popular.

```
0.000000  1.672902  N
1.672902  5.194149  C:maj
5.194149  8.712000  A:min7
8.712000  12.20000  G:maj/5
```

이걸 정확히 지원한다는 건, **남이 손으로 달아놓은 코퍼스**에 그냥 겨눌 수
있다는 뜻입니다. 자기 곡에 먼저 코드를 달아야 검출기가 쓸 만한지 알 수 있는
상황을 피하려고요.

**괄호 수정자는 파싱하고 버립니다.** `C:min7(*b3,9)` 같은 것. 크로마는 숫자가
12개뿐이라 `C:min7` 과 `C:min7(9)` 의 차이는 **원리적으로도** 답할 수 없습니다.
표준 단순화고, 누가 나중에 발견하게 두지 않고 여기 적어둡니다.

## 정답이 없으면 — 인쇄합니다

`.lab` 이 없는 파일은 **찾은 코드를 인쇄합니다. 점수가 아니고, 점수인 척도
안 합니다.** 들으면서 확인하는 용도고, 아무도 정답을 달지 않은 음악에서
검출기가 쓸 만한지 알아내는 방법은 실제로 이겁니다. 불확실한 구간 개수도
같이 나옵니다 — 90마디는 못 검산해도 6마디는 검산할 수 있으니까.

## 네 층으로 나눠서, 초 단위 가중으로

```
근음 · 3화음 · 7화음 · 전체 라벨
```

**초로 가중합니다. 코드 개수가 아니라.** 여덟 마디짜리 C 와 지나가는 F♯dim7 은
코드 하나씩이지만 **맞은 값이 하나씩은 아닙니다** — 듣는 사람은 C 를 8초 듣습니다.
코드 개수로 세는 벤치마크는 **블립을 맞히고 곡을 놓친 검출기에게 상을 줍니다.**

경계 오차도 같이 냅니다. 이름이 다 맞아도 **모든 변화가 반 마디씩 늦으면**
그건 쓸 수 있는 차트가 아니고, 층별 점수는 그 상태에서도 멀쩡해 보입니다.

**이 네 숫자의 정의는 우리 것입니다.** MIREX 과제와 같은 취지지만 라이브러리를
가져다 쓴 게 아니라 `chord-lab.ts` 에 직접 써놨습니다. 그러니 **우리 자신의
변화를 재는 데는 쓸 수 있고, 논문 숫자와 직접 비교할 수는 없습니다.** 이걸
말하는 것이 벤치마크와 홍보 숫자의 차이입니다.

## 벤치마크가 첫 실행에서 찾아낸 것

**템포가 맞는데 버려지고 있었습니다.**

```
pop.wav    검출 96.0 BPM  신뢰도 28%   (정답 96)  →  고정 창
jazz.wav   검출 96.0 BPM  신뢰도 30%   (정답 96)  →  고정 창
```

템포 검출기가 **정확히 맞혔는데**, B단계에서 정한 `MIN_TEMPO_CONFIDENCE = 0.35`
아래라 코드 검출기가 기각하고 0.5초 고정 창을 깔았습니다. 두 임계값이 서로 다른
척도 위에 있었던 거죠.

**그런데 임계값을 안 건드렸습니다.** 강제로 채택시켜서 재봤더니:

```
있는 그대로 (고정 창)   95.2  95.2  95.2  95.2   코드 6/7
템포 강제 채택          95.2  95.2  95.2  95.2   코드 7/7
```

점수가 **똑같습니다.** 이 재료에서는 코드가 2.5초씩 가서 0.5초 창으로도 충분한
겁니다. 도움이 된다는 증거가 없는데 파라미터를 고치는 건, 재고 고치는 게 아니라
그냥 고치는 겁니다. **대신 리포트가 그 사실을 말하게 했습니다** — 기각된 BPM 을
그리드인 것처럼 인쇄하면 안 되니까요.

## 시도했다가 되돌린 것

95.2 % 의 남은 4.8 % 가 **끝의 1초 무음**이었습니다. 정답은 `N` 인데 검출기가
마지막 코드를 파일 끝까지 끌고 갔거든요. "끝의 긴 무음은 코드가 아니다"는
규칙을 넣었습니다.

**테스트가 잡았습니다.** 한 번 치고 울리게 둔 코드의 링아웃을 잘라먹어서
마지막 마디가 비었습니다. 그리고 다시 보니 **4.8 % 는 검출기 문제가 아니라
제 정답 파일이 자기 오디오보다 엄격했던 것**이었습니다 — 피아노는 그 1초 동안
아직 울리고 있었습니다.

측정된 이득이 없고 실제 해가 있어서 **되돌렸습니다.**

그 코드가 실제로 하는 일은 **파일 모양**입니다. 정답 주석은 녹음 전체를 덮고,
구멍 난 `.lab` 은 정답 파일이 아닙니다. 그래서 그걸 검사하게 바꿨습니다.

그리고 하나는 **테스트할 수 있게 코드를 옮겨야 했습니다.** "기각된 템포를
그리드로 인쇄하지 않는다"는 정직성 속성이 벤치마크 출력 코드 안에 묻혀 있으면
검사할 수가 없고, **검사 못 하는 정직성은 장식**입니다.

만든 정답에 대해 90~95 % 를 냅니다. **그 숫자는 검출기가 아니라 하네스가
맞다는 증거**입니다.

진짜 숫자는 위 커맨드를 **본인 음악 폴더에** 겨누면 나옵니다.

# 코드 트랙 화면 — 불확실한 마디를 보이게

A~D 를 다 끝내고 화면을 보니 **약속 하나가 지켜지지 않고 있었습니다.**

B단계부터 리드아웃은 `margin` 을 냅니다 — 1위가 2위를 얼마나 이겼는지.
문서에는 이렇게 써놨고요:

> **0.95 인데 2등을 0.001 차로 이긴 건 앞면이 예쁜 동전던지기입니다.**
> 90마디를 다 검산할 수는 없어도 6마디는 검산할 수 있으니까요.

그런데 `ChordEvent` 에는 그 숫자를 담을 자리가 없었습니다. **차트에 쓰는 순간
버려지고 있었습니다.** 토스트에 "불확실 6개"가 뜨고 사라지면 끝. **어느 6개인지
화면 어디에도 없었습니다.**

## 이제 마디에 표시됩니다

`margin` 이 코드와 함께 이동해서 이벤트에 남습니다. 화면에서:

- 불확실한 코드는 **금색 테두리 + 이름 뒤에 `?`**
- 헤더에 **`불확실 3 →`** 버튼 — 누르면 **다음 불확실 코드 위치로 이동**합니다
- 툴팁이 **세 가지를 구분해서** 말합니다

빨강이 아니라 **금색**입니다. 검출기는 "이건 틀렸다"고 보고하는 게 아니라
**"하마터면 다른 걸로 갈 뻔했다"**고 보고하는 거니까요. 빨강은 여기 아무도 할 수
없는 주장입니다.

세는 것보다 **가는 것**이 핵심입니다. 숫자만 있으면 "할 일이 있다"만 알려주고
**어디인지는 안 알려줍니다.** 90마디 중 6마디는, 갈 수 있어야 검산이 됩니다.
끝에서 첫 번째로 **되돌아옵니다** — 마지막에서 버튼이 죽으면 첫 번째를 손으로
다시 찾아야 하니까요.

## 사람이 쓴 코드는 절대 불확실이 아닙니다

여기서 거꾸로 하기 쉬운 규칙입니다. 손으로 친 코드에는 margin 이 **아예
없습니다**. 그리고 **"숫자가 없다"가 "확신이 없다"로 읽히면 안 됩니다** — 그건
표시가 반대 방향으로 거짓말하는 거고, **사용자 본인의 결정을 "가서 확인할 것"
목록에 집어넣는** 짓입니다.

그래서 `isUnsure` 는 `margin !== undefined && margin < 0.04` 입니다. 첫 조건이
없으면 빈 차트의 모든 코드가 노랗게 물듭니다.

**고쳐 쓰면 표시가 사라집니다.** 의심하던 사람이 답을 말했으니까요. 안 그러면
그 마디가 영원히 목록에 남습니다. 반대로 **끌어서 옮기거나 조옮김하는 건 답을
말한 게 아니므로** margin 이 유지됩니다.

## 저장하면 남습니다

옆 테이블이 아니라 **이벤트 자체에** 붙였습니다 — 클립의 `pitchSegments` 와 같은
선택입니다. **파일 닫자마자 어느 마디가 의심스러웠는지 잊는 차트는 아무도 검산
안 합니다.** 세션은 JSON 이라 그대로 따라갑니다.

## 표시 로직을 화면 밖으로 꺼냈습니다

`isUnsure` / `unsureChords` / `nextUnsureAfter` / `describeChordBlock` 은
`daw/edit/chord-confidence.ts` 에 있습니다. React 컴포넌트 안이 아니라요.

D단계에서 배운 것 그대로입니다: **검사할 수 없는 정직성은 장식.** "사람이 쓴
코드는 불확실이 아니다" 같은 규칙이 뷰 안에 있으면 조용히 썩습니다.

경로에서 margin 빼기.

**마지막 것은 처음에 안 잡혔습니다.** 순수 함수는 전부 검사하고 있었는데
**그 사이의 배선은 아무도 안 보고 있었습니다** — 액션이 디코딩된 클립을 요구해서
테스트가 못 부르거든요. 이번 세션에서 네 번째로 밟은 같은 지뢰입니다.
`chordEventsFor()` 로 꺼내서 검사 가능하게 만들었습니다.

## 실행 중인 앱에서 확인한 것

EDIT 창에서 **8마디 뼈대**를 만들고 봤습니다:

```
블록 8개 그려짐
불확실 버튼 없음                       ← 손으로 만든 코드에 오탐 없음
툴팁 "C — 더블클릭해서 고쳐 쓰세요"      ← margin 없는 분기
테두리 전부 rgba(150,130,200,0.7)      ← 의심 표시 없음
```

**표시되는 쪽(금색)은 앱에서 못 쟀습니다.** 검출된 코드가 필요하고, 그러려면
오디오 디코딩이 필요한데 이 컨테이너에서는 렌더러가 죽습니다. 그 분기는
단위 테스트와 망가뜨리기로만 확인했습니다.

# 코드 트랙을 연주하기 — 반주 파트 생성

읽은 코드로 **소리 나는 파트**를 만듭니다. 코드 레인 헤더의 **`파트`** 버튼과
그 옆 종류 선택(패드 / 컴핑 / 아르페지오 / 베이스).

**새 트랙에 놓습니다.** 선택된 트랙에 덮어쓰지 않습니다 — 남의 보컬 테이크 위에
피아노 네 마디를 얹는 건 되돌리기로 복구되는 종류의 사고가 아닙니다(먼저
알아채야 하니까). 뮤트할 수 있는 트랙이 "물어보기"의 싼 버전입니다.

## 이미 있던 것과 뭐가 다른가

Riff Machine(`ai/riff.ts`)도 코드 트랙을 읽고 음을 씁니다. **다른 일입니다** —
저건 이미 만들어둔 파트에 **라인을 지어냅니다**(윤곽·밀도·모티프·변주).
이건 **차트를 쓰인 대로 연주하고, 파트를 직접 만듭니다.**

그리고 Riff Machine 은 **`MIDI 파트를 먼저 여세요`** 라고 합니다. 오디오에서
코드를 읽어도 그걸 들으려면 **트랙 만들고 → 파트 만들고 → 길이 맞추고 →
패널 열어서** 돌려야 했습니다. 그 사이가 비어 있었습니다.

## 진짜 일은 보이싱이었습니다

코드가 정해지면 **음은 이미 정해집니다.** 남는 선택은 **어디에 놓느냐**뿐이고,
그게 파트처럼 들리는지 숙제처럼 들리는지를 가릅니다.

기존 `voiceChord` 는 **항상 근음 자리**입니다. 코드 하나에는 맞는 답이고
진행에는 틀린 답입니다:

```
C G Am F   근음자리:  [60,64,67] [67,71,74] [69,72,76] [65,69,72]
                     이동 20 반음, 최고음이 9 반음 요동
           보이스리딩: [64,67,72] [62,67,71] [64,69,72] [65,69,72]
                     이동 9 반음, 최고음 폭 1
```

7화음 진행 37 → 9, 재즈 8코드 70 → 17. **손이 안 움직입니다.**

## 여기서 한 번 크게 틀렸습니다

"근음 자리보다 낫다"는 테스트를 통과시켜 놓고 만족했는데, **일부러 이동 비용을
0 으로 만들어봤더니 테스트가 그대로 통과했습니다.**

재보니 **음역이 2옥타브(55–79)라 후보가 5개뿐**이고 전부 가운데 몰려 있어서,
**"가운데에 가장 가까운 걸 고른다"만 해도 보이스리딩과 같은 답**이 나왔습니다.
9개 중 8개가 동일. 이동 22 vs 23.

즉 **이동 비용은 거의 장식이었고, 테스트는 그걸 몰랐습니다.**

음역을 3옥타브(48–84)로 넓히니 후보가 8개가 되고:

```
이동  리딩 22  vs  앵커만 33      다른 보이싱 4/9
```

**넓혀도 실제로 쓰는 음역은 그대로입니다**(모든 재료에서 59–72 안). 앵커가
가운데로 당기니까요. 넓힌 게 사는 건 **더 나은 데로 움직일 자유**고, 그게
보이스리딩의 전부입니다.

그래서 테스트도 바꿨습니다 — **근음 자리가 아니라 "앵커만"과 비교**합니다.
정직한 라이벌하고 비교해야 의미가 있습니다.

## 슬래시 코드는 차트가 결정합니다

`C/E` 면 제일 낮은 음은 **E 입니다.** 차트가 그렇게 말했으니까요. 이동을
아끼려고 전위를 뒤집는 보이서는 **아무도 안 물어본 질문에 답하는** 겁니다.

## 네 가지 종류

| | |
|---|---|
| **패드** | 코드당 한 번, 길게. 데모 밑에 깔아서 화성 움직임을 듣는 용도 |
| **컴핑** | 박마다 짧게. 장르 패턴이 아니라 **아무 데나 얹고 고칠 수 있는 중립** |
| **아르페지오** | 8분음표로 올라갔다 내려옴 |
| **베이스** | 근음, 코드가 걸친 **마디마다** 하나씩 |

베이스가 한 번 치고 네 마디 쉬면 그건 베이스 라인이 아닙니다. 그래서 마디마다
칩니다. 그리고 베이스는 **보이스리딩에서 빼놨습니다** — 이동을 아끼려고 전위를
고르면 근음 진행이 방황하는 내성이 됩니다.

## 아르페지오에서 버그 하나

올라갔다 내려올 때 **양 끝을 안 빼면** 꼭대기와 바닥에서 음이 겹칩니다:

```
64 67 72 67 64 [64] 67 72     ← 마디마다 두 번씩 더듬거림
```

음표 목록에서는 명백한데 **귀로는 놓치기 쉽습니다.** `slice(1, -1)` 로 고쳤고
검사도 넣었습니다.

## 실행 중인 앱이 버그를 하나 잡았습니다

8마디 뼈대를 만들고 `파트` 를 눌렀더니:

```
"패드 파트를 만들었습니다 — 코드 7개, 음 21개"      ← 8개인데?
```

**마지막 코드가 조용히 사라지고 있었습니다.** `songEnd` 는 **클립**을 재는데,
내용이 코드 차트뿐인 세션은 0 을 돌려줍니다. 그래서 마지막 코드의 구간 길이가
0 이 되고 걸러졌습니다.

**레인은 이 문제가 안 보입니다** — 뷰포트 끝까지 그리니까요. 그래서 **차트와
거기서 만든 파트가 코드 개수를 서로 다르게 알고** 있었습니다. 단위 테스트로는
안 잡혔을 겁니다. 세션에 클립이 없다는 조건을 만들어볼 생각을 못 했을 테니까요.

아무것도 끝을 정해주지 않으면 마지막 코드에 **한 마디**를 줍니다. 고친 뒤:

```
"패드 파트를 만들었습니다 — 코드 8개, 음 24개"
```

## 셀프테스트

```
pnpm --filter @aimaster/desktop test:chord-audio    # 65개
```

**14개를 심어서 14개 다 잡혔습니다.** 처음엔 2개가 안 잡혔고, 위에 적은 대로
**둘 다 "테스트가 틀린 걸 재고 있었다"** 였습니다.

앱에서 확인한 것: 코드 없을 때 `파트` 비활성 + 이유, 8마디 뒤 활성,
누르면 **`패드 (코드)` 트랙이 생기고** 토스트가 개수를 보고합니다.
