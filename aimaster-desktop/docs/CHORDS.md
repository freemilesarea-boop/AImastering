# 오디오에서 코드 읽기

WAV 나 스템을 불러서 **무슨 코드인지** 알아내는 기능. 편곡의 출발점이 되는 것.

## 결정된 것

| | |
|---|---|
| **기본 어휘** | **7화음** — maj/min/dom7/maj7/min7/dim/m7b5/sus 등 |
| **정확도 우선** | 분리 엔진을 먼저 돌립니다 (드럼 제거) |
| **표기** | `C`, `Am7`, `G7` — 절대 코드명. 로마숫자 안 씁니다 |

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| **A** | CQT + 튜닝 추정 + 크로마 | **완료** |
| **B** | 템플릿 매칭 + 비트 동기 + 코드 트랙 기록 | **완료** |
| C | HMM / 비터비 평활 | |
| D | 벤치마크 커맨드 + 실제 음원 측정 | |

# A단계 — 크로마

**크로마**는 12개 숫자입니다. 지금 도가 얼마나, 도샾이 얼마나, 레가 얼마나
울리고 있는가. 이 아래로는 전부 룩업 테이블이고, **크로마가 틀리면 코드가
틀립니다** — 어떤 템플릿도 어떤 HMM 도 변환이 버린 정보를 되살리지 못합니다.

## 왜 기존 STFT 로는 안 되는가

이 저장소에는 이미 완전 복원 가능한 STFT 가 있습니다(`stft.ts`). 스펙트럴
에디팅용이고, **주파수가 선형**입니다. 음악은 로그입니다.

스펙트럴 에디터가 쓰는 2048 포인트로 44.1 kHz 를 보면 빈 간격이 21.5 Hz 입니다.
베이스가 사는 동네에서:

```
E2 = 82.41 Hz     F2 = 87.31 Hz     →  4.9 Hz 차이
```

**인접한 두 반음이 같은 빈에 들어갑니다.** E 와 F 를 구분 못 하는 변환은 Am 과
Dm 을 구분할 수 없고, 그건 나중에 아무리 영리해져도 복구가 안 됩니다.

FFT 크기를 키워도 해결이 안 됩니다. C1(32.7 Hz)에서 반음을 분해하려면 창이
**1.5초**쯤 필요한데, 1.5초짜리 창은 곡의 모든 코드 체인지를 뭉갭니다.
요구조건이 모순인 건 **창 길이가 하나여야 할 때뿐**이고, 상수-Q 변환은 정확히
그 가정을 버립니다.

## 상수-Q

Q = 중심주파수 / 대역폭. 이걸 **상수로 유지**한다는 건 모든 빈이 같은 **센트**
폭을 갖는다는 뜻입니다 — 80 Hz 빈은 헤르츠로 좁고 3 kHz 빈은 넓습니다. 사람 귀가
하는 일이고, "반음당 한 빈"이 요구하는 것입니다. 대가는 **빈마다 창 길이가
다르다**는 것.

순진하게 하면 프레임마다 빈마다 필터 하나 → 4분짜리 곡에는 너무 느립니다.
그래서 **Brown-Puckette 스펙트럴 커널**을 씁니다: 각 기저함수를 빌드 타임에 한 번
FFT 도메인으로 옮기면 거의 전부 0인 좁은 봉우리가 됩니다. 봉우리만 남기면
**희소 행렬**이 되고, 변환 전체가

```
프레임당 FFT 한 번  →  희소 행렬 곱 한 번
```

이 됩니다. 실측: 커널이 전체 가중치의 **0.4 %** 만 유지. 22 kHz 에서
**실시간의 56 배**.

## 반음당 3빈인 이유 — 튜닝

레코드가 전부 A=440 이 아닙니다. 아날로그 테이프는 흐르고, 오케스트라는 442 로
맞추고, 옛날 음원은 이유 없이 사분음 어긋나 있고, 귀로 피치 맞춘 샘플은
어디든 갑니다.

40센트 샤프한 곡을 그냥 12빈으로 접으면 **모든 음이 에너지 대부분을 옆 음으로
흘립니다.** 크로마가 지저분한 게 아니라 **체계적으로 틀리고**, 아래쪽에서는
그걸 알 방법이 없습니다.

반음당 3빈이면 봉우리가 자기 반음 **안에서 어디쯤인지** 잴 수 있습니다. 파일
전체에서 재서 축을 밀어놓고 접습니다.

**투표는 각도로 평균냅니다.** 이 양은 반음마다 순환하기 때문에, +49센트인
봉우리와 −49센트인 봉우리는 2센트 차이지 98센트 차이가 아닙니다. 산술평균을
내면 0 이 나오는데, 그건 확실히 틀린 유일한 답입니다.

실측 (±8센트 이내):

```
   -47 →  -46.6      -17 →  -16.6       31 →   31.4
   -40 →  -39.5        0 →    0.3       47 →   47.3
```

## 배음 억제 — 톱니파 도가 C7 로 읽히는 문제

톱니파 C 하나의 배음은 C(×2), G(×3), C(×4), **E(×5)**, G(×6), **B♭(×7)** 입니다.
그냥 접으면 **음 하나가 C7 로 읽힙니다** — 아무도 안 친 코드죠. 템플릿 매처에서
3음과 7음이 틀리는 가장 큰 원인이 이겁니다.

그래서 억제는 **뺄셈**입니다: 더 낮은 배음이 **예측하는** 에너지를 접기 전에
제거합니다. 더하기(하모닉 합)로 하면 진짜 있는 근음도 강화하고 **없는 근음도**
강화합니다 — 베이스에 5도만 있고 근음이 없으면 그게 근음이 돼버립니다.

배음 8번까지 봅니다. 5번(장3도)에서 멈춰봤더니 부족했습니다 — 톱니파 C 가
여전히 **B♭ 8.5 %**(7번 배음), F♯ 3.6 %(11번), G♯ 3.6 %(13번)을 냈습니다.
7번 배음이 결정적입니다. **단7도**라서, 남겨두면 모든 3화음이 도미넌트로 보입니다.

## 파라미터는 재서 골랐습니다

억제 강도 × 감마를 훑어서:

```
0.5 / 3   단일 C   → C 0.98, 다음 0.10
          C major  → C, E, G 전부 0.58, 다음 0.05
          C minor  → C, D♯, G 전부 0.58
          Cmaj7    → C, E, G 0.51 과 B 0.47
          C7       → C, E, G 0.51 과 A♯ 0.47, 상위 5개에 B 없음
```

억제가 낮으면(0.3) 배음열의 3도·5도가 남고, 높으면 배음과 겹치는 **진짜 5도**를
먹을 위험이 있습니다.

## 로그 압축에서 한 번 크게 틀렸습니다

처음엔 `log(1 + 100·x)` 를 **원시 CQT 크기**에 걸었습니다. 그 값들은 수천
단위입니다. 결과:

```
원시:   C 75.3 %   A♯ 8.5 %      (8:1)
압축 후: C 0.43     A♯ 0.36       (1.2:1)
```

압축이 **조용한 음을 들어올린 게 아니라, 모든 음과 모든 잡음의 차이를
지우고 있었습니다.** `log(1 + γ·x)` 는 x 가 이미 0…1 일 때만 의미가 있습니다.
지금은 접은 뒤 최댓값으로 나누고 나서 γ=3 으로 압축합니다.

## 무음은 0 입니다

정규화된 잡음이 아니라 진짜 0. 상대 기준(파일에서 제일 큰 프레임의 2 %)만
쓰면 **잡음만 든 파일**에서는 제일 큰 프레임이 잡음이라 2 % 는 잡음보다
조용합니다. 실측: ±1e-7 디더 파일이 12음 크로마를 자신 있게 내놨습니다.
지금은 절대 기준(−80 dBFS RMS)도 같이 봅니다.

## 셀프테스트

```
pnpm --filter @aimaster/desktop test:chroma      # 18개
```

재는 것:

- 사인파가 **자기 피치클래스**에 떨어지는가 — C2~B6 전 음역 49개 전부
- **E2 와 F2 가 다른 음**으로 나오는가 (STFT 가 못 하는 바로 그것)
- 30센트 샤프한 곡을 30센트 샤프하다고 재고, 보정 후 크로마가 원래 조율된
  곡만큼 깨끗한가
- 톱니파 C 가 **C 로 읽히는가, C7 로 읽히는가**
- 3화음이 세 음으로 균형 있게 읽히는가 / 마이너가 메이저가 아닌가
- **7음이 보이는가** (사용자가 고른 기본 어휘가 요구하는 것)
- 무음이 0 인가 / 32 dB 차이 나는 같은 코드가 같은 벡터인가
- 곡에 쓸 수 있을 만큼 빠른가

일곱 개를 **일부러 망가뜨려서** 전부 잡히는 것을 확인했습니다: 튜닝 시프트
부호 뒤집기, 원시 크기에 압축 걸기, 배음 억제 끄기, 반음당 1빈으로 줄이기,
조밀 커널 만들기, 분석 시작을 C 가 아닌 A 로 옮기기, 그리고 순환평균을
산술평균으로 바꾸기.

**마지막 건 처음에 안 잡혔습니다.** 튜닝 테스트가 −40~+31 만 쓰고 있어서,
±50센트 **경계 근처**를 한 번도 안 밟았습니다. 순환평균이 산술평균과 달라지는
건 거기뿐입니다. ±47 을 추가하니 잡혔습니다.

## 이 단계의 한계

- **C2 부터** 봅니다. C1 빈은 이 Q 에서 창이 1.5초쯤 필요한데 웬만한 코드보다
  깁니다. 코드의 저음 끝은 나중에 **베이스 스템**에서 따로 읽습니다.
- 억제 강도 0.5 는 **배음과 겹치는 진짜 조용한 음**을 조금 먹습니다. 트레이드
  오프고, 파라미터로 열어뒀습니다.
- 여기까지는 **크로마일 뿐 코드가 아닙니다.** 코드는 B단계.

# B단계 — 코드

크로마 12개 숫자에서 **코드 이름**까지. A단계 끝에 "여기까지는 크로마일 뿐
코드가 아닙니다"라고 썼던 그 부분입니다.

```
크로마 (0.1초마다)  →  비트별 평균  →  템플릿 매칭  →  런 병합  →  코드 차트
```

## 왜 코사인 × 이진 템플릿인가

템플릿은 그 코드의 음을 1, 나머지를 0 으로 놓고 **L2 정규화**한 벡터입니다.
점수는 내적, 즉 코사인.

이 선택이 공짜로 해주는 일이 하나 있습니다. **C7 은 C 장3화음을 포함합니다.**
맞은 음 개수만 세면 3화음 위에서는 3화음이(세 음 다 있으니까), 7화음 위에서도
3화음이 이깁니다. 템플릿 자기 크기로 나누면 양방향이 동시에 풀립니다:

```
진짜 3화음  →  3화음 1.000,  7화음 0.866
진짜 7화음  →  7화음 1.000,  3화음 0.866
```

**부분집합도 상위집합도 진실에게 집니다.** 손으로 쓴 규칙이 필요 없습니다.

## 어휘 = 정확도 다이얼

`basic` 24개(maj/min) · `sevenths` **168개** · `full` 264개.

사용자가 고른 **7화음이 기본값**입니다. 값은 있습니다: 7음은 대부분의 보이싱에서
제일 조용한 음이고, **m7 과 그 관계장조의 6화음은 같은 네 음**입니다.

## 베이스가 결정적인 이유

```
Am7 = A C E G
C6  = A C E G      ← 완전히 같음
```

어떤 크로마도 이 둘을 구분 못 합니다. **베이스가 완전히 구분합니다.**

실측으로 확인했습니다. 베이스 없이 `Cmaj7 Am7 Dm7 G7` 을 넣으면

```
Cmaj7  C6  F6  G7      ← 같은 음, 같은 소리, 틀린 차트
```

가 나왔습니다. 그래서 베이스 스템이 없을 때는 **믹스에서 제일 낮은 음**을
직접 읽습니다(`lowestPitchClass`). 스템만은 못하지만 없는 것보다 훨씬 낫고,
이걸 넣자 위 진행이 100 % 로 돌아왔습니다.

가중치는 0.1 — 근음이 베이스면 만점, 그냥 포함만 하면 절반(전위). 코드와
자기 템플릿의 코사인이 0.85~1.0, 이웃 코드와는 0.75~0.9 이므로 그 간극 크기.

## 비트 동기 — 가장 큰 정확도 이득

크로마는 초당 10번 나옵니다. 코드는 한 마디 갑니다. 프레임마다 매칭해서 찍으면
**항목 400개짜리 차트**가 나오고 대부분 정답과 그 이웃 사이에서 깜빡입니다.

비트로 평균내면 두 가지가 겹쳐서 좋아집니다: 한 번의 결정에 **10배의 증거**가
쌓이고, 개별 프레임을 틀리게 만드는 **아르페지오·경과음·꾸밈음**이 바로 평균이
지우는 것들입니다.

그리고 결과가 **편집 가능**해집니다. 비트에서 시작하는 코드는 끌고 다시 칠 수
있고, 12.7314초에서 시작하는 코드는 못 합니다.

템포를 못 믿을 때(신뢰도 0.35 미만)는 고정 창으로 떨어지고 **그렇다고 말합니다**
— 없는 그리드를 있는 척 덮어씌우지 않습니다.

실측 — 틀린 그리드의 대가는 **이름이 아니라 위치**입니다:

```
맞는 그리드:  코드 체인지가 실제 위치에서 0.000 초
137 % 그리드:                      0.230 초
```

## 스탭이 드러낸 버그

가장 크게 틀렸던 곳입니다. `C G Am F` 를 **마디의 1/4 만 치는 스탭**으로 넣으면

```
C  C  Am  Am        ← G 와 F 가 통째로 사라짐
```

원인이 두 개 겹쳤습니다.

1. 스탭의 **꼬리가 자기 메이저 7화음으로 읽힙니다.** 감쇠하면서 배음 균형이
   바뀌어서요. 그래서 `G` 한 비트 + `Gmaj7` 한 비트로 **쪼개집니다.**
2. `minBeats` 가 **매칭된 비트 수**를 셌습니다. 둘 다 1비트라 둘 다 버려지고,
   앞의 C 가 그 구멍 위로 늘어났습니다.

주석에는 이미 "짧은 구간은 **이웃에 흡수된다**"고 써 있었는데 코드는 그냥
버리고 있었습니다. 고친 내용:

- **흡수하되 버리지 않습니다.** 살아남는 이름은 **증거가 더 많은 쪽** — 점수를
  비트에 걸쳐 **합산**해서 비교합니다. 그래서 8비트짜리 C 가 1비트 F#dim7 을
  이기고, 똑같이 짧은 둘 사이에서는 **깨끗한 어택이 뭉개진 감쇠를 이깁니다.**
- 길이는 **덮는 범위**로 잽니다 — 시작부터 **다음 코드가 시작할 때까지**. 한 번
  치고 울리게 둔 코드는 마디의 대부분이 무음이고, **그래도 그 마디 내내 그
  코드입니다.**
- 무음인 이웃이 없는 짧은 런은 흡수할 곳이 없으므로 버립니다(진짜 블립).

이후 실측:

```
1/4마디 스탭:   100 %   C G Am F
마디당 한 방:   100 %   C G Am F   (덮는 범위 [4,4,4,5] 비트)
```

한계도 쟀습니다. **1/14 마디**(0.17초)까지 줄이면 50 % 로 무너집니다
(`Cmaj7 G Am Fmaj7`) — 그 길이에서는 어택 스펙트럼이 코드보다 크게 나옵니다.

## 튜닝 보정이 정말 일을 하는지

A단계에서 만든 보정이 **실제로 값을 하는지**는 따로 재야 합니다. 30센트에서는
**이름만 봐서는 안 보입니다** — 베이스 판독이 손상된 크로마에서도 정답을
건져내기 때문입니다. 그래서 두 군데를 잽니다:

```
30센트: 매칭 점수  보정 1.069  vs  무보정 0.974      (증거가 나빠짐)
45센트: 정확도     보정 100 %  vs  무보정 0 %
                   무보정 결과: C#mMaj7/C  C#mMaj7/C  Fmaj7/A  A#mMaj7/F
```

45센트는 이국적인 값이 아닙니다. 빨리 돈 테이프, 귀로 피치 맞춘 샘플.

## 불확실한 건 불확실하다고

`margin` — 2등과의 격차. **0.95 인데 2등을 0.001 차로 이긴 건 앞면이 예쁜
동전던지기입니다.** 0.04 미만인 구간 수를 리드아웃에 실어 보냅니다.
90마디를 다 검산할 수는 없어도 **6마디는 검산할 수 있으니까요.**

## 셀프테스트

```
pnpm --filter @aimaster/desktop test:chord-audio    # 30개
```

**진짜 악기로 렌더해서** 잽니다 — `OfflineAudioContext` 로 폴리신스·로즈·
어쿠스틱기타를 실제로 울려서 그 오디오를 넣습니다. 합성 사인파가 아닙니다.

측정된 정확도:

```
팝 진행 (C G Am F)                        100 %
7화음 진행 (Cmaj7 Am7 Dm7 G7)             100 %
재즈 턴어라운드 (Dm7 G7 Cmaj7)            100 %
악기 3종 동일 진행                        100 %
코드 위에 경과음 섞인 멜로디               100 %
로즈 + 베이스, 코드 16개                  100 %
```

## 일부러 망가뜨려서 확인한 것

**15개를 심어서 14개가 잡혔습니다.**

템플릿 정규화 제거 · 베이스 가중치 0 · 믹스 최저음 판독 제거 · minBeats 1 ·
재병합 패스 제거 · 그리드 역방향 보행 제거 · 무음 임계 1e-12→0 ·
흡수 대신 버리기 · 흡수된 런이 절대 이름을 못 가져가게 하기 ·
덮는 범위 대신 매칭 비트 수로 재기 · 기본 어휘를 basic 으로 바꾸기 ·
비트 위상을 반대로 반올림하기 · 구간 교체 대신 append 하기 ·
워커를 원본과 어긋나게 두기 · 분석을 다시 UI 스레드로 올리기.

어휘 바꾸기는 **체인 배선까지** 확인하는 용도였습니다. 이번 세션에서 이미 두 번
빠뜨린 실수(`test:instrument-presets`, `test:sampler`)라서, package.json 에
넣은 뒤 진짜로 깨서 **종료 코드 1** 이 나오는 것을 확인했습니다. `&&` 체인은
거기서 멈춥니다.

워커 드리프트는 **처음에 안 잡혔습니다** — 주석만 고쳤는데 esbuild 가 주석을
지워서 번들이 한 글자도 안 바뀌었습니다. **망가뜨리기가 실패한 것이지 검사가
실패한 게 아니었습니다.** 진짜 코드를 고치니 잡혔습니다.

**끝까지 잡히지 않은 하나는 테스트가 아니라 코드에 대한 발견이었습니다.**
**무음 프레임을 평균에 넣어도 매칭이 안 바뀝니다.** 주석은 "임계값에 진다"고
주장하고 있었는데 **거짓말이었습니다.** 0 을 같이 세면 벡터 전체가 균일하게
작아질 뿐이고, 소비자가 전부 스케일 불변입니다(`matchChord` 는 내적 전에
정규화, `bassPitchOf` 는 비율 비교). **20배 범위에서 점수·마진이 비트 단위로
동일**한 것을 확인했습니다. 주석을 사실대로 고쳤습니다.

## 통과하면서 아무것도 안 재던 검사

망가뜨리기와 별개로, **자기가 찍은 숫자에 스스로 반박하는** 검사가 하나
있었습니다. 이름은 "틀린 비트 그리드는 정확도를 깎는다"인데 출력은
`wrong grid 100%` 였습니다. 실제로 단언하는 것은 대조군이 통과했다는 것뿐이었고요.

이 코드들은 한 마디씩 가므로 그리드가 틀려도 **마디 한가운데서 읽은 이름은
살아남습니다.** 틀린 그리드가 부수는 건 이름이 아니라 **위치**입니다 — 그리고
위치야말로 차트를 편집 가능하게 만드는 것이죠. 지금은 위치를 잽니다.

## 세션에 쓰기 — 누를 곳

**기능이 있는데 누를 데가 없으면 없는 것과 구별이 안 됩니다.** 그래서 코드
레인 헤더에 **`오디오에서`** 버튼이 있습니다. 재생헤드 아래의 오디오 클립을
읽어서 코드 트랙에 씁니다.

**분리가 먼저 돕니다** — 사용자가 고른 "정확하게"가 사는 곳입니다. 두 가지를
삽니다: 드럼이 매칭에서 **빠지고**(스네어는 12개 피치클래스에 동시에 떨어지는
광대역 에너지입니다), 베이스 스템이 베이스 판독으로 **들어옵니다**. 느립니다.
분리가 거부하면 **거부 이유를 말하고 믹스로 분석합니다** — 조금 덜 정확한
차트가 차트 없음보다 낫습니다.

**템포는 세션에서 가져오되 위상을 계산합니다.** 클립이 마디 중간에서 시작하면
그 첫 샘플은 다운비트가 아닙니다. `beatPhaseFor` 가 클립 시작점에서 다음
비트까지의 거리를 냅니다 — 이걸 틀리면 차트의 모든 경계가 박에서 벗어납니다.

**덮어쓰기는 자기 구간에서만.** 코드는 **시작점만** 저장하므로, 한 구간에
두 차트가 겹치면 "의견 두 개"가 아니라 **둘 다 아닌 하나**로 엇갈립니다.
구간 밖은 전부 보존합니다 — 2절을 분석했다고 1절이 지워지면 안 되니까요.
일부러 append 로 바꿔보면 이렇게 나옵니다:

```
0:C 4:F 8:Am 8:Am7 10:D7 12:G 14:Gmaj7 18:Dm
```

## UI 스레드에서 내려보냈습니다

버튼을 붙이고 나서 잰 숫자가 문제를 드러냈습니다:

```
30초 @ 44.1 kHz  ->  2525 ms
60초 @ 44.1 kHz  ->  2078 ms   (실시간의 28.9배)
```

4분짜리 클립이면 **8초**입니다. 8초 동안 창이 안 그려지는 건 이 저장소가
분리 엔진에서 이미 내린 판단 그대로 **멈춘 것과 구별이 안 됩니다.** 게다가 더
나쁜 게 있습니다 — 메인 스레드가 막히면 **버튼이 보여주려는 진행률이 절대
안 그려집니다.** 바쁜 게 아니라 죽은 것처럼 보이죠.

그래서 분리 워커와 **똑같은 경로**로 내렸습니다: `worker-entry.ts` 를
`public/chord.worker.js` 로 번들하고, 텍스트로 fetch 해서 Blob 으로 Worker 를
만듭니다(패키징된 빌드는 `file://` 이라 `new Worker(url)` 을 크로미움이
거부합니다). 워커가 안 뜨면 **인라인으로 돌리고 그렇다고 말합니다.**

생성 파일은 커밋되므로(`pnpm dev` 가 그냥 돌아야 하니까) **드리프트 검사**가
같이 있습니다 — 분리 워커가 갖고 있는 것과 같은 장치입니다.

## 실행 중인 앱에서 확인한 것

EDIT 창의 코드 레인에 버튼이 **실제로 그려지고**, 재생헤드 아래에 오디오
클립이 없을 때 **비활성 상태로 이유를 답니다**:

```
"오디오에서"  disabled: true
title: "재생헤드 아래에 오디오 클립이 없습니다"
```

**활성 경로는 이 컨테이너에서 확인하지 못했습니다.** 실제 분석에는 디코딩된
오디오가 필요한데 이 환경에서는 `decodeAudioData` 가 렌더러를 죽입니다(exit 11).
버튼이 있고 대상 판정이 도는 것까지가 여기서 잰 것이고, **누른 뒤의 경로는
못 쟀습니다.**

## 이 단계의 한계

- **평활이 없습니다.** 각 비트가 혼자 판단하므로, 잠깐 애매한 비트가 반박당하지
  않고 틀린 이름을 가져갈 수 있습니다. 런 병합이 제일 짧은 것들을 가리지만
  그건 **코드가 지속된다는 것과 어떤 전이가 흔한지를 아는 모델**과 다릅니다 —
  C단계.
- 정확도 숫자는 전부 **이 저장소의 악기로 렌더한 오디오**에서 나온 것입니다.
  진짜 레코드에서의 숫자는 D단계(벤치마크)에서 잽니다.
