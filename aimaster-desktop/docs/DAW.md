# DAW 워크스페이스 (Pro Tools 구조 이식)

멀티트랙 Edit / Mix 워크스페이스. `Mod+Alt+D` 또는 우측 상단 **DAW** 버튼으로
들어갑니다.

핵심은 **하나의 세션 객체**입니다. Edit 윈도우와 Mix 윈도우는 같은
`DawSession`을 보는 두 개의 뷰이고, 오디오 엔진도 같은 객체를 읽어 그래프를
만듭니다. 그래서 페이더를 움직이면 다음 오디오 블록에서 바로 들리고,
Undo 한 번이 화면·소리·세션 파일을 동시에 되돌립니다.

## 레이어

| 레이어 | 위치 | 역할 |
|---|---|---|
| 모델 | `src/renderer/daw/model/` | 세션 데이터 + 순수 연산 (불변) |
| 편집 | `src/renderer/daw/edit/` | 클립 편집 verb, 트랜지언트, 컴핑, 탐색 |
| 엔진 | `src/renderer/daw/engine/` | WebAudio 그래프, 클립 스케줄러, 오프라인 렌더 |
| 상태 | `src/renderer/stores/dawStore.ts` | 세션 + 선택/재생헤드/그리드 + Undo |
| UI | `src/renderer/components/daw/edit·mix/` | Edit / Mix 윈도우 |

모델과 편집 레이어는 **DOM도 AudioContext도 모릅니다.** 그래서 전부 순수
함수로 테스트됩니다 (`test:daw`, 61 checks). 엔진은 실제
OfflineAudioContext로 렌더해서 검증합니다 (`test:daw-engine`, 12 checks).

## 신호 흐름 (채널 1개)

```
클립 (clip gain + fade)
  → 채널 입력
  → ADC 지연 (지연 보정)
  → 인서트 A…J
  → [프리 페이더 센드]
  → 페이더 (볼륨 × VCA × 뮤트/솔로)
  → 팬
  → [포스트 페이더 센드]
  → 출력 버스 / 마스터
```

버스는 합산 GainNode이고, `input`이 그 버스인 Aux 트랙이 리턴이 됩니다.
사이드체인 인서트는 버스 노드를 플러그인의 키 입력에 직접 물립니다.

## 왜 플러그인을 네이티브 노드로만 만들었나

ScriptProcessor나 컨트롤 레이트 JS로 디텍터를 만들면
OfflineAudioContext 렌더에서 타이머가 돌지 않아 **바운스 결과가 실시간과
달라집니다.** 사이드체인 컴프와 룩어헤드 리미터의 디텍터를
`|x| → 원폴 → 전달 곡선 → GainNode.gain` 오디오 연결로 구성한 이유입니다.
덕분에 Bounce / Freeze / Commit이 실시간 그래프와 같은 코드로 렌더됩니다.

## 지연 보정의 단일 출처

인서트의 지연은 **플러그인이** 계산합니다
(`descriptor.latencyFor(params, sampleRate)`). 룩어헤드를 5 ms로 바꾸면
보정도 같이 따라갑니다. `Insert.latencySamples`는 표시용 캐시이자, 이 빌드에
없는 플러그인을 쓴 세션을 열었을 때의 폴백입니다.

## DAW 안에서는 DAW 밖으로 나가지 않는다

DAW 는 몰입하는 창입니다. 세션 안에서 한 행동이 사용자를 홈 화면으로 내보내면,
그건 기능이 아니라 사고입니다.

파일이 어디로 갈지는 **지금 보고 있는 창**이 정합니다 (`daw/model/drop-target.ts`
— 순수 함수라 DataTransfer 없이 테스트합니다).

| 지금 창 | 오디오 | MIDI | 페이지 이동 |
|---|---|---|---|
| DAW | 플레이헤드 위치에 트랙으로 | 파트로 (Key Editor 자동 오픈) | **없음** |
| 그 외 | 마스터링 대기열 (최대 20) | 건너뜀 | 홈으로 |

대기열은 상한이 있으니 넘친 파일을 세어서 알려줍니다. 세션은 작업 공간이므로
상한이 없습니다 — 30트랙을 끌어다 놓는 건 실수가 아니라 결정입니다.

드래그 오버레이 문구도 목적지를 말합니다: DAW 안에서는 "세션에 트랙으로
추가합니다".

가져오기 경로는 하나입니다 (`daw/edit/session-import.ts`). 툴바 버튼 · 드래그
앤드 드롭 · `Mod+O` 가 전부 같은 함수를 지나므로, 어떻게 요청했든 "가져오기"의
뜻이 같고 언두 스택에도 똑같이 남습니다.

## 디코딩은 렌더러가 하지 않는다

렌더러는 `decodeAudioData` 를 부르지 않습니다. 크로미움 네이티브 코드이고,
macOS 에서 실제 곡을 넣으면 렌더러 프로세스를 **SIGSEGV** 로 데려갑니다.

```
[audio-cache] decode 31.6MB — I Like You.wav
[CRASH] render-process-gone reason=crashed exit=11
```

잡을 수 있는 예외가 아닙니다. 창에는 `backgroundColor` 만 남고, 보고할
프로세스가 이미 없으므로 에러도 안 나옵니다 — **검은 화면**의 정체입니다.
자기가 부른 호출 안에서 프로세스가 죽는 것을 렌더러가 방어할 방법은 없습니다.

그래서 디코딩을 렌더러 밖으로 옮겼습니다.

```
메인 프로세스               렌더러
ffprobe  → 채널 · 길이
ffmpeg   → f32le raw   ──►  createBuffer + copyToChannel
                            (그냥 메모리 복사 — 폴트 날 수 없다)
```

`daw:decode-pcm` IPC 하나입니다. ffmpeg 가 죽으면 IPC 하나가 reject 되고 앱이
그걸 말해줄 뿐, 창은 그대로 살아 있습니다. 덤으로 크로미움이 못 읽는 포맷도
전부 열립니다.

`decodeAudioData` 폴백은 `window.electronAPI` 자체가 없는 환경 — Node
셀프테스트 — 전용으로만 남아 있습니다.

브레드크럼(`decode → analyze → done`)은 그대로 둡니다. 네이티브 코드가
프로세스를 데려가면 스택이 남지 않으므로, 터미널의 마지막 줄이 어느 단계 ·
어느 파일이었는지 말해주는 유일한 기록입니다 (dev 에서만 출력).

## 디코딩 컨텍스트 — 절대 오프라인 컨텍스트로 디코딩하지 말 것

`decodeAudioData` 는 **실행 중인** 컨텍스트를 요구하지 않습니다. 크로미움이
별도 스레드에서 디코딩해 AudioBuffer 를 넘겨주므로 suspended 상태의
`AudioContext` 로 충분하고, 사용자 제스처도 필요 없습니다.

그런데 DAW 는 한때 `new OfflineAudioContext(1, 1, 48000)` — 프레임 하나짜리
오프라인 컨텍스트 — 로 디코딩했습니다. 앱 전체에서 여기 한 곳뿐이었습니다.
이걸로 실제 곡을 디코딩하면 macOS 에서 렌더러 프로세스가 **SIGSEGV
(`reason=crashed exit=11`)** 로 죽습니다. 이건 잡을 수 있는 예외가 아닙니다 —
창에는 `backgroundColor` 만 남고, 보고할 프로세스가 이미 없으므로 에러도
나오지 않습니다.

같은 파일 · 같은 `fetch` · 같은 `decodeAudioData` 를 쓰는 마스터링 화면
(`useWaveformPeaks`)은 **라이브 AudioContext** 로 디코딩하고 한 번도 죽은 적이
없습니다. 차이는 컨텍스트 종류 하나뿐이었습니다.

지금은 `audio/decode-context.ts` 하나가 앱 전체의 디코딩 컨텍스트를 들고 있고,
DAW 와 마스터링 화면이 그걸 공유합니다. 라이브 컨텍스트가 있으면 **항상**
그쪽이 이깁니다. 오프라인 폴백은 `AudioContext` 자체가 없는 Node 셀프테스트
전용입니다.

`loadAudio()` 는 단계마다 `console.info` 브레드크럼을 남깁니다
(`fetch → decode → analyze → done`). 네이티브 코드가 프로세스를 데려가면
스택이 남지 않으므로, 터미널의 **마지막 줄**이 어느 단계 · 어느 파일에서
죽었는지 말해주는 유일한 기록입니다. dev 에서만 터미널로 올라옵니다.

## 서드파티 플러그인 — 경로는 다 뚫렸고, 어댑터 하나가 남았습니다

### 왜 "그냥 VST 를 로드"가 아닌가

VST3 와 AU 는 네이티브 바이너리입니다. 실행한다는 건 서드파티 기계어를 우리
프로세스 안에서 돌린다는 뜻이고, 그럴 수 있었을 자리는 전부 **의도적으로**
막혀 있습니다.

- **렌더러**는 `sandbox: true` · Node 통합 없음이라 네이티브 애드온을 못 올립니다.
  실수가 아니라, UI 버그가 파일시스템 접근 버그가 되지 않게 하는 장치입니다
- **AudioWorklet** 은 더 격리돼 있습니다. 모듈 로딩도, IPC 도, 파일시스템도
  없습니다. 그런데 오디오 클럭을 가진 유일한 곳입니다
- **SharedArrayBuffer** — 디스크 스트리밍에서 리더 스레드와 오디오 스레드를
  이어준 그 링 — 은 **한 프로세스의 스레드들** 사이에서만 공유됩니다. 다른
  프로세스에는 매핑되지 않으므로, 스트리밍을 풀었던 그 트릭이 플러그인 호스트
  프로세스까지는 닿지 않습니다

메인 프로세스는 네이티브 코드를 올릴 수 있습니다. 그러니 오디오가 플러그인까지
갈 수는 있는데, **실시간 그래프를 벗어나야만** 갑니다.

### 그래서 맞는 모양

엔진에는 이미 이 경우를 위한 자리가 있습니다. `PluginDescriptor.offline` 은
실시간 그래프에서 돌 수 없는 장치를 표시하고, 체인에는 OFFLINE 배지를 달고
남아 있으며, 렌더 경로가 대신 적용합니다. 서드파티 플러그인이 정확히 그것입니다.

```
라이브 모니터링   바이패스 — 들으려면 트랙을 프리즈
바운스 · 프리즈    메인이 오디오를 플러그인에 통과시켜 돌려준다
```

전송로도 이미 있습니다. PCM 스토어가 float32 를 디스크에 쓰고 렌더러가
`aimaster-local://` 로 읽습니다. 호스트 패스는 그 왕복에 플러그인이 중간에
끼는 것뿐입니다.

### 호스트 — 남의 코드를 돌리는 프로세스

```
렌더러                     메인                        호스트 프로세스
────────────────────────────────────────────────────────────────────────
오프라인 렌더 결과
  → interleave(f32)  ──▶  스크래치 파일에 쓰기
                          fork(plugin-host.js) ─────▶  입력 파일 읽기
                                                       체인을 슬롯 순서대로 적용
                          ◀───── {ok, stages} ───────  출력 파일 쓰기
  ◀── outputPath
fetch(aimaster-local://)
pcmToBuffer → AudioBuffer
```

**작업 하나에 프로세스 하나.** 오래 사는 호스트는 시작 비용을 아끼는 대신 한
플러그인이 망가뜨린 상태를 다음 작업까지 끌고 갑니다. fork 는 수십 ms 고
바운스는 수 초입니다 — 바꿀 이유가 없습니다.

**죽어도 되고 멈춰도 됩니다.** 자식이 답하기 전에 끝나면 그건 크래시한
플러그인의 모습이고, `HOST_TIMEOUT_MS` 안에 답이 없으면 그건 멈춘
플러그인입니다. 둘 다 바운스 한 번의 **에러**로 돌아옵니다. `runJobInProcess`
는 절대 reject 하지 않습니다.

**오디오는 프로세스 경계를 메시지로 넘지 않습니다.** 작업은 입력 파일과 출력
파일의 이름일 뿐이라, 4분짜리 스테레오 트랙도 IPC 를 타지 않습니다.

**어댑터가 없는 포맷은 통과시키지 않고 거부합니다.** 오늘 VST3 스테이지는
`applied: false` 와 이유를 달고 돌아오며 샘플은 손대지 않습니다. 조용히 아무
일도 안 하는 플러그인은 안 열리는 플러그인보다 나쁩니다.

`host-worker.ts` 의 `ADAPTERS` 가 포맷 → 블록 처리 함수 맵입니다. VST3 나 AU
를 붙인다는 건 **여기 한 줄을 더하는 것**이고, 그 위의 어떤 것도 바뀌지
않습니다. 지금 구현된 건 `reference` — 앱이 직접 정의한 장치(게인 + 위상
반전)로, 렌더된 파일만 보면 적용됐는지 아닌지가 자명하기 때문에 파이프라인
전체를 증명하는 데 씁니다.

### 지금 되는 것

**스캔** (`main/plugins/scan.ts`) — macOS · Windows · Linux 의 시스템/사용자
폴더 양쪽에서 VST3 · AU · CLAP · VST2 를 찾습니다.

- VST 3.7 의 `moduleinfo.json` 을 읽어 **오디오 클래스만** 골라냅니다. 번들은
  컨트롤러 클래스도 내보내는데 그건 채널에 걸 물건이 아닙니다
- AU 는 `Info.plist` 의 `AudioComponents` 를 읽습니다. 바이너리 plist 면
  `plutil` 로 변환합니다 — OS 에 있는 도구고, **플러그인 코드는 열지 않습니다**
- 클래스 id 가 있으면 그게 정체성입니다. 사용자가 플러그인 폴더를 옮겨도 살아남습니다
- 시스템과 사용자 양쪽에 설치된 같은 플러그인은 **한 개**입니다

**스캔은 절대 바이너리를 열지 않습니다.** 남의 코드를 우리 프로세스에서
돌리는 건 플러그인 하나하나에 대한 결정이어야지, 폴더를 훑은 부작용이면
안 됩니다. 테스트가 소스에 `dlopen` · `require(` · `import(` 가 없는지까지
확인합니다.

### 남은 것 — 그리고 그게 왜 코드만의 문제가 아닌가

`external-host.ts` 의 `HOST_REQUIREMENTS` 가 목록입니다.

| 필요한 것 | 상태 | 왜 |
|---|---|---|
| 자식 프로세스 격리 | ✅ | 서드파티 코드가 죽으면 앱이 같이 죽습니다 |
| 네이티브 모듈 (N-API) | ❌ | 플러그인은 바이너리라 JS 로 못 엽니다 |
| `disable-library-validation` 엔타이틀먼트 | ❌ | notarize 된 앱은 서명이 다른 dylib 을 못 올립니다 |
| Steinberg VST3 라이선스 | ❌ | SDK 가 GPLv3 이거나 독점 라이선스입니다 |

마지막 항목이 **AU 를 먼저 하는 이유**입니다. AU 호스팅은 Apple 의
AudioToolbox 만 쓰므로 서드파티 라이선스 협의가 필요 없습니다. VST3 는
상용 클로즈드 소스로 배포하려면 Steinberg 와 계약이 먼저입니다.

목록은 코드 안에 있습니다. 문서에 두면 코드와 어긋나고, `met: true` 하나를
뒤집으면 그 포맷의 모든 플러그인 상태가 한 번에 움직이도록 순수 함수로
계산합니다.

### UI 는 "찾음"과 "쓸 수 있음"을 구분합니다

조용히 아무것도 안 하는 플러그인으로 가득한 픽커는 없느니만 못합니다 —
컴프레서가 왜 안 걸리는지 오후를 통째로 날리게 됩니다. 그래서 서드파티는
**별도 매니저**에 있고, 각 항목이 앱이 그걸로 뭘 할 수 있는지 말하며, 패널
상단이 지금 어디까지 되고 무엇이 왜 빠졌는지 적습니다.

인서트 랙의 빈 슬롯에서 **서드파티…** 를 누르면 그 슬롯을 기억한 채 매니저가
열리고, 항목을 고르면 슬롯에 꽂힙니다. 꽂힌 인서트는 `Insert.external` 에
포맷 · 경로 · uid · 이름 · 제조사를 들고 세션에 저장되므로, 그 플러그인이
없는 컴퓨터에서 열어도 **어느 플러그인이 없는지**를 말할 수 있습니다 —
슬롯이 조용히 사라지지 않습니다.

같은 랙에 **Reference Gain** 이 있습니다. 앱이 직접 만든 오프라인 장치라
서드파티 플러그인이 하나도 설치돼 있지 않아도 호스트 경로 전체를 직접 눌러볼
수 있습니다: 걸고, 바운스하고, 6 dB 내려간 파일을 확인하면 됩니다.

## AI 추천 — 프리셋과 추천의 차이

"AI 추천"은 DAW 에서 가장 위조하기 쉬운 기능입니다. 괜찮은 컴프레서 값을
돌려주는 함수는, 밖에서 보면 소스를 **측정한** 함수와 똑같이 생겼습니다 —
서로 다른 두 소스를 넣었더니 같은 답이 나오기 전까지는.

### 규칙 하나

**어드바이저가 내놓는 모든 숫자는 `SourceProfile` 의 측정값에서 나와야 하고,
어드바이저는 그 측정값의 이름을 댈 수 있어야 합니다.** 왜인지 말 못 하는
추천은 사연이 붙은 프리셋이고, 사연이 붙은 프리셋은 프리셋보다 나쁩니다 —
믿게 되니까요.

그래서 모든 추천이 `evidence` 를 같이 냅니다. 읽은 숫자를, 잰 단위 그대로.
설정이 마음에 안 들면 그게 나온 측정값을 확인할 수 있고, 그게 추천을 반박할
수 있는 유일한 방법입니다.

### 무엇을 어떤 단위로 재나

기존 Intelligence Layer 는 믹스를 잽니다 — 3밴드, 라우드니스, 폭. "믹스가
어두운가"에는 맞는 어휘고 **"디에서를 어디에 둘까"에는 틀린 어휘**입니다.
`high` 라는 이름의 밴드에서 주파수를 뽑을 수는 없으니까요.

`source-profile.ts` 는 같은 오디오를 **노브의 단위로** 다시 잽니다.

| 노브가 원하는 것 | 재는 것 |
|---|---|
| 디에서의 **주파수** | 5–10 kHz 에서 실제로 피크가 선 지점 |
| 게이트의 **스레숄드 dB** | 20 ms 창 레벨의 10 퍼센타일 = 노이즈 플로어 |
| 컴프의 **어택 ms** | 온셋에서 피크까지 걸린 시간의 중앙값 |
| 하이패스의 **코너** | 에너지의 3 % 가 그 아래인 지점 |
| 모노메이커의 **크로스오버** | 120 Hz 이하만의 상관도 |
| 딜레이의 **시간** | 세션 템포 — 측정 가능한 유일한 모듈레이션 값 |

여기 있는 모든 필드는 **어떤 노브가 필요로 해서** 있습니다.

### 험은 스펙트럼이 아니라 괴르첼로 찾습니다

스펙트럼 곡선은 20 Hz–20 kHz 를 48개 로그 밴드로 나눕니다 — 밴드당 1/4
옥타브. **50 Hz 에서 1/4 옥타브는 46–54 Hz** 이고, 그렇게 넓은 밴드는 50 Hz
라인과 54 Hz 라인을 구분할 수 없습니다. 그런데 그 구분이 이 일의 전부입니다.

그래서 샘플에 직접 괴르첼을 겁니다. 0.5초 창이면 2 Hz 를 분해합니다.
두 가지를 다 봅니다:

```
라인이 자기 이웃(±7 Hz)보다 8 dB 이상 서 있다   → 좁다
정확한 배음 2개 이상이 똑같이 서 있다            → 사다리다
```

두 번째가 60 Hz 근처 베이스 음과 험을 가릅니다. 지속된 사인파에는 배음이
없고 베이스 기타의 배음은 움직입니다. **이걸로도 못 가르는 것**: 창 전체에서
정확히 50 또는 60 Hz 로 유지되면서 자기 배음 사다리까지 가진 베이스 음.
그건 스펙트럼만으로는 누구도 못 가릅니다.

### 어드바이저가 거절하는 세 가지 경우

거절할 때는 그럴듯한 값을 내놓는 대신 **이유를 말합니다.**

```
소스가 무음이다              잴 게 없습니다
아무 문제가 없다             이미 평탄한 오디오에 컴프는 손상입니다
노브가 측정이 아니다          디더 비트는 배급이 정하지, 아무리 들어도 안 정해집니다
```

**항상 의견이 있는 장치는 의견이 쓸모없는 장치입니다.** 41개 중 3개(디더 ·
비트크러셔 · DC 블로커)는 원칙적으로 거절하고, 나머지도 측정값이 손댈 필요
없다고 하면 거절합니다 — 트루피크가 −18 인데 리미터를 걸지 않고, 노이즈
플로어가 45 dB 아래인데 디노이즈를 걸지 않습니다.

### 무엇을 측정하나 — 그 인서트에 도착하는 오디오

세 번째 슬롯의 컴프레서는 이미 EQ 를 지난 소리를 듣습니다. 그래서
`renderTrackWindow` 가 **그 인서트 앞까지만** 렌더합니다. 채널 완성본을 재면
컴프레서가 자기가 듣지도 않는 오디오에서 설정됩니다.

측정 구간은 **30초로 제한**됩니다. 노브에 필요한 숫자는 몇 분을 더 준다고
좋아지지 않고, 10초 걸리는 버튼은 아무도 두 번 안 누릅니다. 시간 선택
영역이 있으면 그게 이깁니다 — 후렴을 선택하고 추천을 누르는 건 명백히
"후렴 기준으로 잡아줘"입니다.

캐시는 **렌더가 의존하는 것**으로 키를 잡습니다: 트랙의 클립들과 그 인서트
**앞의** 인서트들. 한 채널에서 장치 여섯 개에 추천을 걸면 서로 다른 슬롯
위치 수만큼만 렌더하고, 클립을 옮기면 키가 바뀌어 무효화됩니다.

### 쓰는 법

플러그인 창 제목줄의 **AI** 버튼. 누르면 분석하고, 값을 채우고, 그 아래에
읽은 근거를 칩으로 보여줍니다. **undo 한 번이면 원래대로**입니다.

확신도가 0.45 아래면 "출발점입니다, 정답이 아닙니다" 라고 붙습니다 —
모듈레이션 깊이 같은 건 취향이고, 취향인 걸 측정인 척하지 않습니다.

### 파일

```
ai/source-profile.ts   버퍼 → 노브 단위의 측정값 (순수)
ai/plugin-advice.ts    41개 어드바이저. 측정값 → 값 + 근거 (순수)
ai/advice-runner.ts    인서트 앞까지 렌더 · 구간 선택 · 캐시
```

## 템포 트랙 — 곡이 숨 쉬게

세션에는 템포 숫자가 하나 있었습니다. 그 숫자는 음악이 아무것도 안 할 때까지만
맞습니다 — 끝에서 느려지는 순간, 6/8 브리지가 들어오는 순간, 라이브 연주를
올리는 순간 그리드가 전부 어긋나고, 그리드 위에 세워진 것 전부가 같이
어긋납니다.

### 초가 아니라 비트

모든 이벤트는 **4분음표 비트** 위에 있습니다. 초가 아닙니다. 워프 마커와
같은 이유입니다: 초로 적은 이벤트는 **앞쪽 템포가 바뀔 때마다 다시 적어야**
하고, 같은 사실을 두 곳에 적는 게 템포 맵이 썩는 방식입니다.

### 다음 템포까지 가는 두 가지 방법

```
jump   템포를 유지하다가 다음 이벤트에서 바뀝니다. 섹션 전환
ramp   두 이벤트 사이를 BPM 기준 선형으로 이동합니다. 리타르단도, 아첼레란도
```

**BPM 이 선형이면 시간은 선형이 아닙니다.** 비트당 초가 60/T 이므로 램프
구간의 경과 시간은

```
∫ 60/(t₀ + k·u) du  =  (60/k)·ln(T(b)/t₀)        k = ΔBPM / Δ비트
```

닫힌 형태고, 정확하고, 역함수도 정확합니다. 램프를 잘게 잘라 더하면 4분짜리
곡에서 오차가 쌓이고, **그 오차는 클릭이 다운비트에서 밀리는 소리로 들립니다.**
셀프테스트가 이 적분을 40만 스텝 수치적분과 대조합니다 — 1e-7 안에서 일치하고,
왕복은 1e-9 안에서 정확합니다.

### 박자는 비트가 아니라 마디에 붙습니다

"33마디부터 6/8" 이라고 쓰고 그렇게 읽으니까요. 6/8 한 마디는 **4분음표
셋**이라서 비트 축은 끝까지 4분음표로 남고, 박자는 그 위 어디에 마디선이
떨어지는지만 정합니다.

### 무엇이 템포 맵을 따라가나

| | 따라감 | |
|---|---|---|
| 마디/박 눈금자 · 그리드 · 스냅 | ✅ | 비트 축에서 반올림해서 되돌립니다 |
| 트랜스포트 마디\|박\|틱 | ✅ | |
| **워프된 오디오** | ✅ | 클립이 놓인 자리의 맵으로 마커를 풉니다 |
| 카운트인 · 클릭 | ✅ | 펀치 지점의 템포와 박자로 |
| 세션 뷰 → 어레인지 변환 | ✅ | 마디를 곱하지 않고 실제 마디선을 걷습니다 |
| **MIDI 노트** | ❌ | 아직 초 단위 저장 — 아래 참조 |

**MIDI 는 아직 따라가지 않습니다.** 노트가 `startSec`/`durationSec` 로
저장돼 있어서, 템포를 바꿔도 노트는 있던 시각에 그대로 남습니다. 노트 모델을
비트로 옮기는 건 키 에디터 · 스텝 시퀀서 · 퀀타이즈 · 노트 도구 · MIDI 파일
IO · 플레이어를 전부 건드리는 별도 작업입니다.

그래서 **문서에만 적지 않았습니다**: 템포 변화가 있고 MIDI 파트도 있는
세션에서는 툴바에 `⚠ MIDI 미추종` 이 뜹니다. 이런 건 귀로 알아내는 게 제일
나쁜 방법입니다.

### 워프가 맵을 어떻게 읽나

워프 마커는 **클립 시작으로부터의 비트**입니다. 그래서 맵을 클립 위치 기준으로
읽어야 합니다 — 리타르단도 도중에 시작하는 클립의 4번 비트와, 그게 끝난 뒤에
시작하는 클립의 4번 비트는 다른 초입니다.

API 는 숫자 하나(`sessionBpm`) 대신 작은 객체를 받도록 넓혔습니다. **기존
호출은 전부 숫자를 그대로 넘기고 동작이 한 톨도 안 바뀝니다** — 워프 테스트
33개가 그대로 통과합니다. 런타임만 맵에서 만든 객체를 넘깁니다.

렌더 캐시 키에는 **BPM 이 아니라 맵의 키**가 들어갑니다. 맵 아래에서는 명목
템포가 같은 두 클립이 실제로 다르게 늘어나므로, BPM 으로만 키를 잡으면 한
클립이 다른 클립의 오디오를 받습니다.

`followTempo: false` 인 클립은 맵을 무시합니다. 고정 루프가 자기와 상관없는
리타르단도를 따라 숨 쉬면 안 되니까요.

### 그리드는 이제 음가입니다

스냅 단위가 초가 아니라 **1 Bar · 1/2 · 1/4 · 1/8 · 1/8T · 1/16 · 1/16T ·
1/32** 입니다. 0.5초로 고정된 그리드는 템포가 움직이는 순간 비트가 아니게
됩니다.

### 편집

```
더블클릭        지금 걸려 있는 템포로 이벤트 추가 — 음악은 안 움직이고
                손잡이만 생깁니다
드래그          위아래로 BPM, 좌우로 그리드 위 이동
Alt · 우클릭    삭제 (맨 앞 이벤트는 남습니다 — 1마디에 답이 있어야 하니까)
아래 줄 클릭    박자 4/4 → 3/4 → 6/8 → 5/4 → 7/8 순환
```

곡선은 이벤트를 직선으로 잇지 않고 **시간축에서 샘플링해서** 그립니다. 램프는
BPM 이 **비트에 대해** 선형인데 템포가 움직이는 동안 비트는 시간축에서
등간격이 아니라서, 쉽게 그리면 음악이 만들지 않는 모양이 나옵니다.

### 단축키

| 기능 | 단축키 |
|---|---|
| 재생 위치에 템포 변화 | `Alt+T` |
| 템포 이벤트 Jump ↔ Ramp | `Shift+Alt+T` |

### 옛 세션은 그대로 열립니다

`tempoMap` 은 옵셔널입니다. 템포 트랙이 생기기 전에 저장된 세션에는 없고,
변화가 한 번도 없었던 프로젝트와 구분되지 않습니다. 그래서 폴백은 한 번 도는
마이그레이션이 아니라 **모든 읽기가 지나가는 길**입니다 — `tempoMapOf(session)`.
다른 어디서도 `session.tempoMap` 을 직접 읽지 않습니다.

맵을 저장할 때는 `tempoBpm` 과 `timeSignature` 를 곡의 시작 값으로 맞춰
둡니다. 놔두면 트랜스포트는 120 이라고 하고 1마디는 76 인 세션이 됩니다.

### 파일

```
model/tempo-map.ts   비트↔초 · 마디/박 · 그리드 · 스냅 · 편집 (전부 순수)
components/daw/edit/TempoTrack.tsx   곡선 · 이벤트 · 박자 줄
```

## 오토메이션 — 레인, 그리고 손으로 탄 걸 받아 적는 일

### 다섯 개 모드가 왜 다섯 개인가

오토메이션은 **아무것도 안 한 것과 제대로 한 것이 똑같이 생긴** 유일한 자리
입니다. 한 번도 안 쓴 레인과, 원래 값 그대로 써 넣은 레인은 같은 선을 그립니다.
차이는 **가장자리**에서만 드러납니다 — 패스 *앞*의 오토메이션은 어떻게 됐나,
손을 떼고 *난 뒤*엔 어떻게 되나. 그게 정확히 touch · latch · write 를 가르는
지점입니다.

| 모드 | 언제 쓰나 | 손을 떼면 |
|---|---|---|
| `off` | 레인을 무시하고 정적 값으로 | — |
| `read` | 재생만 | 아무것도 안 씀 |
| `touch` | 한 군데만 고칠 때 | **원래 오토메이션으로 돌아감** |
| `latch` | 여기서부터 끝까지 새로 | 마지막 값을 끝까지 유지 |
| `write` | 패스 전체를 갈아엎을 때 | 끝까지 씀 · **끝나면 touch 로 내려감** |
| `trim` | 이미 있는 모양을 통째로 올리고 내릴 때 | 오프셋만큼 이동 |

`write` 가 패스가 끝나면 스스로 `touch` 로 내려가는 건 안전장치입니다. 아무도
콘솔을 write 로 두고 가지 않지만, 딱 한 번 잊으면 그 다음 패스가 믹스를
지웁니다. 이 모드를 가진 데스크는 전부 이렇게 합니다.

### 하나의 패스는 하나의 undo

패스가 도는 동안은 전부 `applyTransient` 입니다 — 레인 생성도, 손을 따라가는
페이더도, 초당 예순 번씩. `commitEdit` 은 **패스가 끝날 때 한 번**입니다.
네 마디짜리 페이더 라이딩을 undo 하면 그 전 믹스가 돌아오지, 중간 위치
이백 개가 돌아오지 않습니다.

덤으로 고쳐진 것: 예전에는 페이더를 한 번 움직일 때마다 `apply` 가 히스토리를
쌓았습니다. 이제 드래그 하나가 undo 하나입니다.

### 손이 레인을 이깁니다

기록 중에는 같은 페이더를 두 개가 잡으려 합니다 — 지난 테이크를 들고 있는
레인과, 다음 테이크를 만들고 있는 손. **손이 이겨야 합니다.** 안 그러면
스케줄러가 다음 윈도를 걸 때마다 페이더가 옛날 오토메이션으로 튕겨 돌아갑니다.

그래서 `automation-live.ts` 가 있습니다 — 기록 중인 레인 키의 집합 하나.
기록하는 쪽이 쓰고, 스케줄러가 읽습니다. 스케줄러는 그 레인을 건너뛰고,
`clearAutomatedParam` 이 이미 큐에 걸린 램프까지 취소합니다. **플래그만
지우는 걸로는 부족합니다** — 앞 윈도에서 예약된 램프가 아직 AudioParam 에
남아서 `.value` 를 덮어씁니다.

오프라인 렌더에서는 이 집합이 비어 있습니다. 바운스에는 손이 없으니 모든
레인이 재생됩니다.

### 재생 중인 레인은 페이더를 움직입니다

**움직이는 게 안 보이는 오토메이션은 돌고 있다고 믿기 어렵습니다.** 재생 중
레인이 살아 있으면 믹서의 페이더는 정적 값이 아니라 **레인 값**을 그립니다.
플레이헤드는 구독하지 않고 읽습니다 — 미터 폴링이 이미 초당 스무 번 전 스트립을
다시 그리고 있고, 그게 움직이는 페이더에 필요한 딱 그 속도입니다.

### 레인은 소리와 같은 숫자로 그립니다

폴리라인은 브레이크포인트를 `pointValueAt` 이 보간하는 방식 **그대로**
보간한 것이고, 양 끝이 평평한 건 플레이어가 양 끝에서 평평하기 때문입니다.
장식이 하나도 없습니다.

편집은 어느 DAW 에나 있는 세 가지, 그리고 그 외에는 없습니다.

```
빈 곳 클릭      브레이크포인트를 놓고 그대로 잡고 있음
포인트 드래그   이웃 사이에서 이동 (넘어가지 못함)
Alt · 우클릭    삭제
```

드래그 하나가 undo 하나 — 클립 드래그, 플러그인 노브와 같은 규칙입니다.

### 레인이 있는 대상은 엔진이 재생하는 것뿐입니다

`AutomationTarget` 에는 뮤트 · 센드 팬도 있지만 `availableTargets` 는
**볼륨 · 팬 · 센드 레벨 · 그리고 장치가 램프할 수 있다고 말한 플러그인
파라미터만** 내놓습니다. 나머지는 레인이 예쁘게 그려지고 아무 일도 안
일어나기 때문입니다 — 그건 없는 것보다 나쁩니다. 그려 놓은 필터 스윕이 왜 안
걸리는지 오후를 통째로 날리게 됩니다.

목록을 늘리려면 `ClipPlayer.scheduleAutomation` 을 **먼저** 늘려야 합니다.
플러그인 파라미터가 어떻게 그 문턱을 넘었는지는 아래
[플러그인 파라미터 오토메이션](#플러그인-파라미터-오토메이션)에 있습니다.

### 그룹은 그룹으로 움직입니다

`setStaticValue` 는 볼륨과 팬을 믹서 자신의 세터로 넘깁니다. 그룹 안의 페이더는
혼자 움직이지 않고 멤버들이 오프셋을 지킨 채 따라오는데, 여기서 `volumeDb` 를
직접 쓰면 **이 파일이 존재하는 바로 그 상황에서** 그룹이 조용히 깨집니다.

### 단축키

| 기능 | 단축키 |
|---|---|
| 오토메이션 레인 열기 / 접기 | `Alt+A` |
| 오토메이션 모드 순환 | `Mod+Alt+Shift+A` |

레인을 접어도 브레이크포인트는 그대로 남고 계속 재생됩니다.

### 파일

```

edit/automation-lanes.ts   대상마다 범위 · 이름 · 정적 값 · 레인 생성
edit/automation-record.ts  제스처 → 레인. 모드가 무슨 뜻인지가 여기 있음
engine/automation-live.ts  기록 중인 레인 (스케줄러가 읽음)
stores/automationStore.ts  진행 중인 패스 · 트랜스포트 연결

```

### 플러그인 파라미터 오토메이션

여기까지 막혀 있던 이유는 명확했습니다: **플러그인 파라미터는 AudioParam 이
아닙니다.** `setParam(id, value)` 은 지금 값을 세팅할 뿐이고, 타이머로
때리는 방식은 **라이브 전용**입니다 — 오프라인 렌더는 실시간보다 빨리 돌아서
`setTimeout` 이 아예 의미가 없고, 모니터링한 스윕이 바운스에 안 들어가는
바운스는 바운스가 아닙니다.

`OfflineAudioContext.suspend()` 로 블록마다 멈춰 세우는 방법도 있지만,
이 저장소의 테스트가 도는 `node-web-audio-api` 에서 **직접 돌려보니
패닉합니다.** 그래서 증명할 수 없는 길이었습니다.

**그래서 반대로 갔습니다: 파라미터가 하나의 AudioParam 이면 오토메이션할 수
있고, 아니면 못 합니다.** 장치가 그걸 직접 말합니다.

```ts
automatableParams: ['hpfHz', 'lowDb', 'b1Hz', 'b1Q', /* … */]   // 디스크립터
automatable: automatableFrom({ hpfHz: hpf.frequency, /* … */ }) // 인스턴스
```

그러면 플러그인 레인이 **페이더와 똑같은 램프, 똑같은 시계, 똑같은 코드**를
탑니다. 오프라인 컨텍스트가 스케줄된 램프를 라이브와 똑같이 걸어가므로,
바운스가 모니터링한 스윕을 그대로 재현합니다.

### 레인은 그려진 대로 움직입니다

두 브레이크포인트 사이에서 `linearRampToValueAtTime` 하나만 쓰면 보간이
**AudioParam 의 단위**에서 선형입니다 — dB 레인이면 게인에서, 주파수 레인이면
헤르츠에서. 20 kHz → 400 Hz 로 그은 직선은 대부분의 길이를 고음에서 보내다가
끝에서 절벽처럼 떨어집니다. 그린 모양이 아닙니다.

그래서 플러그인 레인은 **20 ms 블록마다 레인을 자기 단위로 읽어서** 매핑한
값으로 램프를 겁니다. 호스트가 플러그인에 블록당 값 하나를 주는 것과 같은
모양이고, 각 스텝이 점프가 아니라 램프라서 지퍼 노이즈가 없습니다.

값이 안 변하는 구간은 이벤트를 안 냅니다 — 대신 움직이기 직전에 **값을 한 번
못 박습니다.** `linearRamp` 는 직전 이벤트에서 보간하므로, 1분 가만히 있다가
올라가는 레인이 못 박히지 않으면 1분 내내 올라갑니다.

### 어떤 노브가 되고 어떤 노브가 안 되나

| 되는 것 | 왜 |
|---|---|
| Parametric EQ 15개 파라미터 전부 | 하나하나가 BiquadFilter 의 AudioParam |
| EQ 3-Band 5개 전부 | 같은 이유 |
| Trim `gainDb` · Delay `timeMs`/`feedback` · Reverb `preDelayMs` | 하나의 GainNode / DelayNode |
| Compressor `attackMs` · `releaseMs` | DynamicsCompressorNode 의 시간 상수 |

| 안 되는 것 | 왜 |
|---|---|
| Delay/Reverb 의 `mix` | 게인 **두 개**가 반대로 움직입니다. 반만 오토메이션하면 드라이가 뒤에 남습니다 |
| Compressor `thresholdDb`/`ratio`/`kneeDb` | 노드의 숨은 자동 메이크업 보정을 같이 움직입니다. 램프만 걸면 레인이 움직일수록 커집니다 |
| Limiter 전부 | `ceilingDb` 는 전달곡선을 다시 만들고 `lookaheadMs` 는 **보고하는 레이턴시**를 바꿉니다 — 지연 보정이 이미 그 값에 맞춰 채널을 정렬해 둔 뒤입니다 |
| Reverb `decaySec`, Space Reverb 의 공간 | 임펄스 응답을 다시 만듭니다 |

**메뉴에는 되는 것만 나옵니다.** 나머지는 목록에 아예 없습니다 — 아름답게
그려지고 아무 일도 안 하는 레인은 이 저장소에서 가장 나쁜 결과입니다.
디스크립터의 선언과 인스턴스가 실제로 내놓는 것이 어긋나지 않는지는 셀프테스트가
**모든 장치를 만들어서** 양방향으로 확인합니다.

### 세션이 레인과 싸우지 않습니다

트랜스포트가 도는 동안 스토어는 끊임없이 바뀌고, 그때마다 세션의 인서트
파라미터가 인스턴스에 다시 써집니다. 그대로 두면 매번 램프를 취소하고 노브를
세션 값으로 되돌립니다. 그래서 오토메이션이 몰고 있는 파라미터는 sync 에서
건너뜁니다 — 페이더와 팬이 이미 쓰던 것과 같은 장치입니다.

### 레인 헤더가 대상 선택기입니다

채널 하나에 플러그인 파라미터가 수십 개라 "레인 전부 보기" 토글로는 닿을 수
없습니다. 레인 제목이 곧 드롭다운이고, 다른 대상을 고르면 그 레인으로
바뀝니다. 떠난 레인은 브레이크포인트를 그대로 들고 접힐 뿐입니다.

### 아직 안 되는 것

**매크로는 아직입니다.** 매크로 하나는 여러 모듈의 여러 파라미터로 퍼지는데,
그중 어느 것도 단일 AudioParam 이 아닙니다 — 매크로 값을 램프하려면 퍼진
파라미터 각각의 곡선을 따로 만들어야 하고, 그건 별도 작업입니다.

## 리버브 — 32개의 공간, 그리고 그걸 만드는 방법

리버브 프리셋은 보통 **노브 위치 묶음**입니다. 여기 있는 건 **방 묶음**입니다.
미터 단위의 크기, 감쇠 시간, 벽이 고역을 얼마나 먹는지, 반사가 얼마나 빨리
쌓이는지 — 그걸로 임펄스 응답을 합성해서 컨볼브합니다.

차이가 중요한 이유: 그래야 파라미터가 **의미**를 가집니다. Size 를 두 배로
하면 벽이 실제로 물러나고, 초기 반사가 같이 물러납니다. 벽 위치에서 계산했기
때문입니다.

### 임펄스 응답이 만들어지는 순서

**1. 초기 반사 — 진짜 이미지 소스 모델**

공간의 비율을 가진 직육면체, 그 안에 비대칭으로 놓인 음원과 청취자, 그리고
각 축으로 2차까지의 모든 거울상. 이미지 하나가 탭 하나입니다 — 거리만큼
지연되고, 1/거리로 줄고, 어느 쪽에서 오는지로 패닝됩니다. **작은 방이 작게
들리는 이유가 이것입니다**: 첫 반사가 정말로 8 ms 뒤에 옵니다.

Diffusion 은 반사면이 몇 개냐입니다. 야외 무대는 몇 개뿐이고 플레이트는 셀 수
없이 많습니다. 둘 다 124개 이미지를 다 쓰면 같은 방이 됩니다.

**2. 후기 잔향 — 밴드 하나가 아니라 셋**

노이즈 하나에 엔벨로프 하나를 곱하면 누구나 아는 "싸구려 리버브" 소리가
납니다. 여기서는 저 · 중 · 고 세 밴드가 각자의 감쇠 시간을 가집니다. 돌은
저역이 오래 남고(`bassMult` > 1), 나무 방은 저역을 먹고(< 1), 고역은 어느
방에서든 제일 먼저 죽습니다(`damping`).

**3. 이음매**

잔향은 반사 밑에서 서서히 올라옵니다. 올라오는 시간은 공간의 diffusion 에서
나옵니다 — 플레이트는 첫 샘플부터 꽉 차 있고, 야외 무대는 끝까지 밀도가
안 생깁니다.

### 이 파일이 지키는 두 가지

**결정적입니다.** 모든 난수는 시드가 박힌 LCG 에서 나옵니다. `Math.random` 은
한 번도 안 씁니다. 바운스가 모니터링과 같아야 하는데, 진짜 난수로 만든 IR 은
렌더할 때마다 다른 홀이 됩니다.

**에너지로 정규화합니다.** 모든 IR 이 같은 총 에너지로 스케일됩니다. 감쇠를
0.4초에서 6초로 바꾸면 **방이 바뀌지 레벨이 바뀌지 않습니다**. 컨볼버의
`normalize` 는 꺼둡니다 — 브라우저 공식은 우리 것이 아니고, 켜두면 레벨 점프를
도로 넣습니다. 전 공간의 IR 에너지 편차는 측정상 **0.1 dB 미만**입니다.

### 공간 목록

| 그룹 | 공간 |
|---|---|
| 라이브 · 무대 | 스테이지 모니터 · 합주실 · 소극장/클럽 · 라이브하우스 · 극장 무대 · 아레나 · 스타디움 · 야외 무대 |
| 홀 | 리사이틀 홀 · 스코어링 스테이지 · 콘서트 홀 · 심포니 홀 · 석조 교회 · 대성당 |
| 룸 | 보컬 부스 · 침실 · 스튜디오 룸 · 드럼 룸 · 우드 라이브룸 · 타일 룸 · 복도 |
| 플레이트 · 챔버 | 빈티지 플레이트 · 브라이트 플레이트 · 보컬 플레이트 · 에코 챔버 |

0.22초 보컬 부스부터 11초 무한 공간까지입니다.

### 네 개의 서로 다른 기계

프리셋 뱅크 네 개가 아니라 정말로 다른 알고리즘입니다.

**Space Reverb** — 위의 합성 IR 을 컨볼브합니다. **컨볼버가 하나가 아니라
둘**입니다: 초기 반사와 후기 잔향이 별도의 IR 이라서 둘의 밸런스가 진짜
페이더입니다. IR 하나에 "ER 레벨" 노브를 붙이면 그건 톤 컨트롤인 척하는
것입니다 — 이미 렌더된 컨볼루션의 앞 60 ms 만 나중에 들어올릴 수는 없습니다.

**Plate Reverb** — 피드백 딜레이 네트워크. 딜레이 4개가 하우스홀더 행렬로 서로
먹입니다. 직교 행렬이라 에너지가 재분배될 뿐 생기지 않고, 그래서 12초에서도
안정적입니다. 행렬이 `out_i = in_i − ½·Σ in` 이라서 게인 노드가 16개가 아니라
6개면 됩니다. **초기 반사가 없습니다** — 철판에는 벽이 없으니까요. 보컬이
가까우면서 동시에 거대하게 들리는 게 정확히 그 이유입니다.

**Spring Reverb** — 분산(dispersive) 딜레이 루프. 스프링은 저역이 고역보다
느리게 갑니다. 그래서 치면 고역이 먼저 오고 저역이 끌려옵니다 — 기타 앰프의
그 "보잉". 피드백 루프 안의 올패스 8개가 정확히 그 일을 합니다.

**Shimmer Reverb** — 잔향을 **한 옥타브 올려서** 다시 방에 먹입니다. 한 바퀴
돌 때마다 한 옥타브라, 음 하나가 코드가 되고 패드가 됩니다.

### 옥타브는 어떻게 만들었나

지연 시간이 **1초에 1초씩 줄어드는** 딜레이 라인은 입력을 두 배 속도로
재생합니다 — 한 옥타브 위. 윈도우 길이만큼만 그럴 수 있으므로 두 개를 반
주기 어긋나게 돌리고, 각 라인이 리셋되는 지점에서 정확히 0 이 되는 레이즈드
코사인으로 크로스페이드합니다.

위상을 어디서 가져오느냐가 문제였습니다. `OscillatorNode` 에는 위상 제어가
없고, `PeriodicWave` 로 흉내낼 수도 없습니다 — `disableNormalization` 을
크로미움은 지키고 셀프테스트가 쓰는 렌더러는 무시하는데, **이 모듈레이터의
진폭이 곧 피치 비율**이라 둘이 달라지면 다른 음정이 나옵니다. 그래서 규격에
정확히 정의된 내장 파형(사각 아닌 톱니 하나, 사인 하나)만 쓰고, 위상은
딜레이 라인에 통과시켜 만듭니다.

톱니의 불연속은 반 주기 지점에 있습니다(측정값이고 규격 공식이 그렇습니다):

```
라인 A   톱니 그대로              T/2 에서 점프
라인 B   톱니를 T/2 지연          T 에서 점프
윈도우   사인을 ¾T 지연, ±½, +½   A 는 T/2 에서 −1, B 는 T 에서 +1
```

두 윈도우가 같은 신호의 0.5 ± 이므로 **모든 샘플에서 합이 정확히 1**입니다.
440 Hz 를 넣으면 880 Hz 가 나오고, 220 · 660 · 1320 · 1760 은 전부 20배 이상
아래입니다. 측정했습니다.

### 피드백 루프 안의 필터는 버터워스여야 합니다

웹오디오는 로우패스/하이패스의 `Q` 를 **데시벨로** 읽습니다:
`alpha = sin(w0) / (2 · 10^(Q/20))`. 기본값 1 은 **1 dB 의 레조넌스**입니다.
루프 밖에서는 무해한데, 루프 안에서는 한 주파수에서 루프 게인에 곱해집니다.
패스당 게인 0.99 인 플레이트에 1 dB 피크가 있으면 그 주파수의 루프 게인은
1.11 — 리버브가 아니라 **발진기**입니다.

처음 구현했을 때 플레이트가 정확히 이랬습니다. decay 12초에서 피크가
**9,000만**까지 갔습니다. `Q = −3.0103`(최대 평탄, 피크 없음)으로 고치니
사라졌습니다.

### 올패스는 공짜가 아닙니다

스프링의 피드백 루프에는 올패스 8개가 있습니다. 올패스의 그룹 딜레이는
전 대역 평균이 자기 딜레이 길이와 같으므로, 32 ms 라인에 62 ms 가 더해집니다.
32 ms 만 보고 피드백 게인을 계산하면 **모든 감쇠 설정이 3배 가까이 길어집니다**
— 2초로 맞춘 게 5.5초가 나왔습니다. 루프 시간을 올패스까지 세서 계산하니
0.5 → 0.63, 2 → 2.23, 6 → 5.99 로 맞았습니다.

### 사이클 안의 딜레이는 128 샘플이 최소입니다

웹오디오 그래프의 사이클에는 반드시 DelayNode 가 있어야 하고, 그 딜레이는
렌더 퀀텀(48 kHz 에서 128 샘플 = 2.67 ms) 이상으로 강제됩니다. 위의 모든
딜레이가 그보다 긴 건 의도된 것입니다. 교과서적인 슈뢰더 올패스의 1.7 ms 는
조용히 2.67 로 늘어나고, 그러면 설계한 장치가 아닌 게 됩니다.

플레이트의 확산 올패스를 2.9–5.1 ms 로, 탱크를 17–38 ms 로 잡은 이유입니다.
그리고 확산단 출력을 직접 출력에 탭합니다 — 올패스에는 즉시 경로가 있어서,
그 탭이 있어야 플레이트가 딜레이 라인 하나만큼 늦게 오는 대신 **즉시**
밀도를 가집니다.

## 프리셋 — 어디서 시작할지

프리셋은 소리가 아니라 **어디서부터 다툴지**입니다. 그래서 전부 무엇을 **위한**
것인지로 이름이 붙어 있습니다 — "리드 보컬 홀", "게이트 스네어". "Hall 3" 같은
이름은 decay 노브를 직접 돌려도 알 수 있는 것 외에 아무것도 알려주지 않습니다.

**부분 파라미터 맵으로 저장됩니다.** 프리셋이 실제로 정하는 것만 들어 있고,
언급하지 않은 것은 장치의 기본값이 됩니다. 나중에 장치에 파라미터를 추가해도
모든 프리셋이 조용히 0 을 받지 않습니다.

**어떤 프리셋을 불렀는지는 세션에 저장하지 않습니다.** 노브를 하나 움직이는
순간 그건 이미 그 프리셋이 아니고, 다음에 열었을 때도 그 프리셋이라고 우기는
세션은 거짓말을 하는 겁니다. 노브를 만지면 표시가 "직접 설정"으로 돌아갑니다.

| 장치 | 프리셋 |
|---|---|
| Space Reverb | 보컬 5 · 드럼 5 · 기타/건반 5 · 라이브 5 · 오케스트라 3 · 특수 4 |
| Plate | 5 |
| Spring | 4 |
| Shimmer | 4 |
| Reverb (구형) | 3 |
| Compressor · Limiter · Delay | 5 |

### 내 프리셋 — 귀로 찾은 걸 남기는 곳

공장 프리셋은 앱에 컴파일돼 들어간 고정 목록입니다. 나머지 절반이 이겁니다:
귀로 찾아낸 세팅을 **자기가 붙인 이름으로** 두고, **같은 픽커 안에** 놓습니다.
소리를 찾으러 손을 뻗는 순간에는 누가 만든 프리셋인지 아무도 신경 쓰지 않기
때문입니다. 내 프리셋이 맨 위, 그 아래로 공장 그룹들입니다.

**저장된 프리셋은 코드가 아니라 데이터입니다.** 손으로 고칠 수 있고, 기계
사이를 오가고, 백업에서 복원되고, 쓰다 만 파일로 깨질 수 있습니다. 그래서 값은
들어올 때와 나갈 때 **양쪽에서** 장치가 선언한 파라미터에 맞춰 검사합니다 —
없는 id 는 버리고, 범위 밖 값은 범위로 당깁니다. 다음 빌드의 프리셋 파일이
장치를 갈 수 없는 자리에 놓을 수 있어서는 안 됩니다.

**공장 프리셋과 반대로 전체 스냅샷으로 저장합니다.** 공장 프리셋은 자기가
정하는 것만 담습니다(나중에 파라미터가 추가돼도 0 을 받지 않도록). 내 프리셋은
"이 소리 그대로"라는 뜻이므로 전부 담습니다 — 그리고 나중에 장치에 파라미터가
추가돼도 불러올 때 기본값이 밑에 깔리므로 여전히 안전합니다.

| 상황 | 하는 일 |
|---|---|
| 같은 이름으로 또 저장 | **거절**합니다. 픽커에 같은 이름 두 개는 소리를 잃는 방법입니다 — 덮어쓰기는 따로 있습니다 |
| 가져오기에서 이름 충돌 | `이름 (2)` 로 **둘 다 남깁니다.** 가져오는 사람은 어느 쪽을 원했는지 알 수 없습니다 |
| 이 빌드에 없는 장치의 프리셋 | 건너뛰고 **어느 장치인지 이름을 말합니다** |
| 다른 프로그램의 JSON | 파일이 자기 종류(`kind`)를 밝히므로 거절합니다 |
| 저장소가 꽉 참 / 프라이버시 모드 | 실패했다고 **말합니다.** 저장된 척하지 않습니다 |

**파일로 나갈 수 있습니다.** localStorage 는 작업을 두는 곳이 아닙니다 —
재설치 한 번, 프로필 초기화 한 번, "사이트 데이터 지우기" 한 번에 사라집니다.
`내보내기` / `가져오기` 는 실제 파일 다이얼로그를 거쳐 `.louipreset` 로
읽고 씁니다.

**저장 버튼은 저장할 수 있는 장치에만 그립니다.** 외부 호스트로 부르는
서드파티 플러그인은 이 빌드에 파라미터 목록이 없어서 검증할 대상이 없습니다.
항상 실패하는 버튼은 없는 버튼보다 나쁩니다.

### 목록인 파라미터는 노브가 아닙니다

공간 32개를 노브에 올리면 원하는 하나에 닿기까지 31개를 눈 감고 지나가야
합니다. `PluginParamDef.choices` 가 있는 파라미터는 **드롭다운**으로 그려지고,
`choiceNotes` 가 있으면 고른 항목의 설명이 밑에 붙습니다 — 그 공간이 몇 초짜리
몇 미터인지가 고르는 자리에 적혀 있습니다.

값은 여전히 숫자(인덱스)입니다. 세션은 파라미터를 숫자로 저장해왔고 앞으로도
그렇습니다. 바뀐 건 컨트롤뿐입니다.

### 그림은 소리와 같은 숫자로 그립니다

플러그인 창의 리버브 그림은 삽화가 아닙니다. 초기 반사 막대는 이미지 소스
모델이 **실제로 내놓은 탭**을 그 시간에 그린 것이고, 뒤의 곡선은 잔향이
**실제로 감쇠하는 엔벨로프**입니다. 게이트 공간의 그림이 끊기는 이유는 방이
끊기기 때문입니다.

### 구형 Reverb 는 그대로 열립니다

`reverb` 는 DAW 가 처음 가졌던 리버브고, 리버브 패밀리가 생기기 전에 저장된
세션이 아직 가리키는 id 입니다. **파라미터는 하나도 안 바뀌었으니** 그 세션들은
저장된 그대로 열립니다. 바뀐 건 무엇과 컨볼브하느냐입니다 — 감쇠하는 노이즈
버스트가 아니라 합성된 방입니다. 비용은 0 이고 완전히 다른 악기가 됐습니다.
방을 고르고 싶으면 Space Reverb 를 쓰세요.

### 픽커는 체인 순서로 접힙니다

알파벳 순이면 D 로 시작한다는 이유로 딜레이가 맨 위에 옵니다. 그러면 매번
읽어야 합니다. 여기서는 **채널을 실제로 만드는 순서** — 정리하고, 다듬고,
제어하고, 색을 입히고, 움직이고, 배치하고 — 라서 원하는 그룹이 눈이 이미
가 있는 자리에 있습니다. EQ 와 다이내믹스는 기본으로 열려 있습니다. 실제
채널에서 다섯 중 넷이 거기서 나오니까요. 검색하면 전부 펼쳐집니다 — 앱이 이미
찾아낸 걸 폴더를 뒤져 다시 찾게 하면 안 됩니다.

### 몇 가지 설계 결정

**Mid/Side 는 행렬입니다** — M = (L+R)/2, S = (L−R)/2. 스플리터 · 게인 ·
머저로 직접 짭니다. 대신 해주는 노드가 없습니다. Mid/Side EQ · Mono Maker 가
이 위에 올라갑니다.

**Mono Maker 는 베이스를 되살리지 않습니다** — 못 합니다. 모노 합이 0인
베이스는 그게 합의 정의입니다. 이 장치가 하는 일은 **스테레오와 모노가
어긋나지 않게** 하는 것입니다. 사이드 필터는 4폴입니다. 완만한 기울기는
코너 아래 한 옥타브의 사이드를 남기는데, 그게 바로 미터에는 보이고 모노에서는
사라지는 그 베이스입니다.

**Soft Clipper 는 실링을 지킵니다** — 4배 오버샘플링은 앨리어싱을 막지만
리샘플링 필터가 울려서 커브를 1 dB 쯤 넘깁니다. 실링이 권고사항인 클리퍼는
클리퍼가 아니라서, 뒤에 오버샘플링 없는 하드 스테이지를 하나 더 답니다.

**Tape Delay 의 핵심은 피드백 루프 안입니다** — 매 반복마다 어두워지고,
부드러워지고, 살짝 흔들립니다. 깨끗한 딜레이 뒤에 필터를 다는 것과는 다릅니다.

**Dither 노이즈는 시드 고정입니다** — 바운스는 재현 가능해야 하고
`Math.random` 은 그렇지 않습니다.

**모듈레이션은 자유 진행 LFO 입니다** — 위상이 재생 위치가 아니라 오디오
컨텍스트를 따르므로 바운스가 모니터링과 같은 위상에서 시작하지 않습니다.
동기되지 않은 모듈레이션은 어느 DAW 에서나 그렇지만, 이 엔진은 그것 말고는
라이브와 오프라인이 동일하므로 `freeRunning` 으로 표시하고 창에도 적습니다.

**Loudness Meter 는 아무것도 바꾸지 않습니다** — 오디오는 그대로 지나가고
옆으로 딴 탭이 BS.1770-4 K-weighting(1681.97 Hz 하이셸프 +3.999 dB → 38.135 Hz
RLB 하이패스)을 거칩니다. 창에 보이는 숫자가 납품 기준이 쓰여 있는 그 측정값과
같습니다.

### 37개 전부를 렌더해서 검증합니다

장치 37개는 무음 하나 · 폭주 하나 · NaN 하나 · 바이패스가 바이패스가 아닌 것
하나가 섞일 기회가 37번입니다. 코드를 읽어서는 안 보입니다.

`plugin-rack-selftest` 는 **전수** 검사입니다. 모든 장치를 실제
`OfflineAudioContext` 로 만들어 실제 오디오를 먹이고 측정합니다 — 유한한가,
무음이 아닌가, 폭주하지 않는가, 바이패스가 ±0.2 dB 안인가, **모든 파라미터를
최소·최대로 밀어도** 그래프가 안 깨지는가. 그다음 구체적인 주장을 하는 장치는
그 주장으로 검증합니다.

이 스윕이 실제로 잡은 것: `withBypass` 가 `reduction`/`analyse` 를 조용히
버리고 있었습니다. 지난 라운드에 넣은 GR 미터는 영원히 null 을 읽고 있었고,
그건 "열심히 일 안 하는 컴프레서"처럼 보일 뿐 에러가 아닙니다.

## 다이내믹스 — 컴프레서를 제대로 만든 이야기

**증상**: 컴프레서가 존나 튄다. 그리고 재생 중에 플러그인을 켜면 소리가 끊긴다.

### 1. 끊김 — 인서트 하나 바꾸려고 그래프 전체를 부수고 있었다

`structureKey` 안에 인서트 목록이 들어 있었습니다. 플러그인 하나를 추가하면
키가 바뀌고 → `teardown()` → **모든 채널이 파괴**되고 → 재생 중인 소스 노드가
사라진 노드에 물려 있게 됩니다.

테이크 중간에 컴프를 잡는 건 엔지니어가 하는 가장 평범한 일입니다. 그게 테이크를
날리면 안 됩니다.

지금은 인서트 지문(`insertsKey`)이 그래프 지문에서 분리돼 있고, 장치만 바뀌면
`rebuildInserts` 가 **그 채널의 인서트 체인만** 다시 엮습니다. `input` ·
`insertOut` · 페이더 · 센드는 그대로라 재생 중인 클립과 스트리밍 워클릿이
변경을 통과해서 계속 갑니다. 라우팅처럼 진짜 구조가 바뀌면 여전히 재빌드합니다.

### 2. 튐 — 디텍터가 파형을 쫓고 있었다

옛 컴프레서는 손으로 만든 디텍터였고, **어택과 릴리즈가 로우패스 하나를
공유**했습니다. 마지막에 만진 노브가 이깁니다. 그리고 어택 0.1 ms 를 요구하면
그 필터가 **1591 Hz** 에 앉습니다 — 정류된 파형의 리플이 그대로 게인 스테이지로
들어갑니다. 압축이 아니라 링 모듈레이션이고, 보컬에서는 못 들어줍니다.

필터 그래프로는 고칠 수 없습니다. BiquadFilter 는 LTI 라서 **올라갈 때와
내려갈 때 속도를 다르게 할 수가 없습니다**. 비대칭 어택/릴리즈가 필요하면
`DynamicsCompressorNode` 를 써야 합니다 — 네이티브 노드이고, 소프트 니가 있고,
**자기 게인 리덕션을 보고**합니다.

### 3. 그런데 그 노드에는 숨은 게인이 있었다

크로미움에서 측정:

```
thr -24 · knee 6 · ratio 8:1
  스레숄드보다 26 dB 아래 신호 → +11.41 dB 더 커져서 나옴
```

WebKit 커널이 threshold/knee/ratio 에서 **자동 메이크업**을 유도해 전부에
적용합니다 (`fullRangeMakeup = (1 / saturate(1)) ^ 0.6`). 웹오디오 컴프레서가
"진짜 컴프로 쓰기 어렵다"는 말의 정체입니다.

그래서 `webAudioAutoMakeup()` 이 WebKit 알고리즘을 그대로 재현해 그 값을 다시
나눕니다. 근사가 아니라 재현입니다 — 근사는 스레숄드를 움직일 때마다 잔차가
달라집니다.

크로미움 120 에서 5가지 설정 전부 **잔차 ±0.00 dB**. 이제 컴프레서를 꽂아도
압축하지 않는 구간의 레벨은 변하지 않고, Makeup 노브가 그 박스 안의 유일한
게인입니다.

### 4. 사이드체인은 따로 나갔다

Web Audio 컴프레서는 외부 키를 못 받습니다. 그래서 **Sidechain Ducker** 가
별개 장치입니다. 배선에 따라 DSP 가 몰래 바뀌는 플러그인은 믿을 수 없습니다.
더커의 디텍터는 여전히 손으로 만든 것이고, 그래서 어택 하한이 5 ms 입니다 —
더킹은 파형을 쫓을 일이 없습니다.

모든 디텍터의 `smoother` 는 이제 **2폴이고 60 Hz 를 넘지 않습니다**. 440 Hz
톤의 정류 리플(880 Hz)이 46 dB 아래로 떨어지면서도 3 ms 면 정착합니다.

### 5. GR 미터는 측정값이다

`DynamicsCompressorNode.reduction` 을 그대로 읽어 창에 그립니다. 노브에서
유도한 값이 아니라 **지금 이 테이크가 실제로 받는 압축**입니다.

## 플러그인 창 — 연필에서 소리까지

트랙 헤더의 **✎** → 그 트랙의 인서트 랙 → 장치를 누르면 **떠 있는 플러그인 창**.

랙은 메뉴가 아니라 랙입니다. 슬롯 A–J 는 비어 있어도 자리를 지킵니다 —
"컴프는 C 에 있다"가 엔지니어가 채널을 기억하는 방식이고, 장치를 추가할 때마다
목록이 다시 흐르면 그게 무너집니다.

창은 **DawPage 레벨**에 붙어 있습니다. Edit 에서 Mix 로 넘어간다고 방금 잡던
컴프가 닫히면 안 됩니다. 여러 개를 동시에 띄우고, 타이틀바로 끌어 옮기고,
겹치면 클릭한 것이 위로 옵니다.

**그림은 장치가 실제로 하는 일입니다** (`daw/model/plugin-curves.ts`).
Audio EQ Cookbook 전달함수를 엔진이 쓰는 것과 같은 계수로 평가합니다 —
장식용 곡선이 소리와 어긋나면 그건 없는 것만 못합니다. 신뢰받으니까요.

- EQ 계열 → 밴드를 합친 주파수 응답
- 다이내믹스 → 전달 곡선 + 스레숄드 마커 + **지금 이 연주가 어디에 있는지**
  (트랙 미터에서 읽은 실시간 점). "4:1" 과 "스네어마다 니를 때리고 있다" 의 차이
- 딜레이 → 반복이 언제 어느 크기로 오는지
- 리버브 → RT60 감쇠

노브는 세로 드래그(Shift 미세, 더블클릭 기본값)이고, 드래그 중에는
`applyTransient`, 손을 뗄 때 `commitEdit` 입니다. 2초짜리 스레숄드 스윕이
**언두 한 단계**지 400단계가 아닙니다.

`applyParams` 가 세션 변경마다 `instance.setParam` 을 부르므로, 재생 중에 노브를
돌리면 그래프에 바로 들어갑니다. 읽고 맞추는 게 아니라 듣고 맞춥니다.

**측정으로 잡은 버그 하나** — Web Audio 는 highpass/lowpass 의 `Q` 를
**데시벨**로 읽습니다 (`alpha = sin(w0) / (2 * 10^(Q/20))`). 리니어 Q 로 그렸더니
곡선은 -3 dB 코너를 보여주는데 엔진은 +0.7 dB 를 내고 있었습니다. 테스트가
실제 `OfflineAudioContext` 렌더와 대조해서 잡았습니다. Butterworth 는
`Q = 0` 이 아니라 `Q = -3.01 dB` 입니다.

## 디스크 스트리밍 — 트랙 수의 상한을 없앤 방법

48 kHz 스테레오 f32 는 **트랙당 23 MB/분**입니다. 전부 메모리에 올리면:

| 4분 세션 | RAM |
|---|---|
| 8스템 | 740 MB |
| 16스템 | 1.5 GB |
| 40스템 | 3.7 GB — 죽습니다 |

DAW 가 넘어야 하는 벽이고, 넘는 방법은 **"이 트랙이 보인다"와 "이 샘플들이
메모리에 있다"를 분리하는 것**입니다.

```
메인 프로세스                 리더 Worker              오디오 스레드
ffmpeg → PCM 스토어    ──►    Range 512KB      ──►    AudioWorklet
(경로+mtime 키, 영구)        (SAB 링버퍼 2초)        (링을 비우기만)
        │
        └─ 피크 엔벨로프 32KB ──► 타임라인 그리기
```

**PCM 스토어** (`main/ipc/decodeHandlers.ts`) — 소스별로 한 번 디코딩해서
float32 로 디스크에 둡니다. 키는 `경로 + mtime + 크기 + 샘플레이트` 라
세션을 다시 열면 며칠 전 디코딩 결과를 그대로 씁니다. 피크 엔벨로프도 여기서
같이 계산해 사이드카에 넣습니다 — 타임라인을 그리는 데 트랙당 **92 MB 가
아니라 32 KB** 면 됩니다. Pro Tools 의 변환 파일, Ableton 의 `.asd` 와 같은
구조입니다. 12 GB 상한, 오래된 것부터 정리.

**링버퍼** (`daw/engine/ring-buffer.ts`) — 락 없는 SPSC 링. 오디오 스레드는
락을 기다릴 수 없습니다. 렌더 쿼텀 하나가 막히면 그건 클릭입니다.
카운터는 **저장소 오프셋이 아니라 절대 소스 프레임 위치**입니다. 그래서 시크가
"양쪽 다 이제 N" 한 줄이고, 시크 이전에 출발한 블록이 늦게 도착하면
**끼워 넣지 않고 버립니다**.

**리더 Worker** (`public/daw-reader.worker.js`) — `aimaster-local://` 이
HTTP Range 를 처리하므로 512 KB(스테레오 1.4초)를 **6 ms** 에 읽습니다.
2초 링에 200배 여유입니다. 메인 스레드에 두면 React 렌더 한 번에 드롭아웃이
나므로 반드시 별도 스레드입니다.

**워클릿** (`public/daw-stream.worklet.js`) — `currentFrame` 으로 세는
샘플 정확 배치. 128프레임 블록 중간에서 시작하는 클립은 정확히 그 샘플에서
시작합니다 — `AudioBufferSourceNode` 와 같은 자리입니다. 링이 비면 **멈추지
않고 무음을 내보내고 부족분을 셉니다**. 늦은 읽기는 조용한 블록 하나여야지
멈춘 렌더 쿼텀이면 안 됩니다.

**스트리밍하지 않는 것** — 워프된 클립(이미 버퍼로 렌더됨), 그리고 **오프라인
바운스**. 바운스는 실시간보다 빠르게 도므로 리더 스레드에 의존할 수 없습니다.
같은 스토어의 같은 샘플을, 시계 없이 통째로 읽어 씁니다. SharedArrayBuffer 나
워클릿이 없는 환경도 자동으로 버퍼 재생으로 내려갑니다 — 스트리밍은 최적화지
재생의 전제가 아닙니다.

`SharedArrayBuffer` 는 `app.commandLine.appendSwitch('enable-features',
'SharedArrayBuffer')` 로 켭니다. 크로미움은 cross-origin isolation 뒤에
숨겨두는데 커스텀 프로토콜 + 개발 서버로는 만족시킬 수 없고, 애초에 서드파티
콘텐츠를 띄우는 앱이 아닙니다.

**측정** (4분 48 kHz 스테레오 8스템, Electron + Xvfb)

| | 전 | 후 |
|---|---|---|
| 콜드 오픈 | 41.7 s | **6.4 s** |
| **재오픈 (스토어 warm)** | 41.7 s | **21 ms** |
| 재생 시작 | 전부 디코딩 대기 | **0 ms** |
| 8스템 RAM | 703 MB | **링 6 MB** |
| 언더런 | — | **0** |

40트랙이면 링 30 MB 입니다. 상한이 사라졌습니다.

## 재생은 기다리지 않는다 · 스템은 사라지지 않는다

STEM 세션(4분 스테레오 8개 = 약 740 MB)에서 두 가지가 무너졌습니다.

**1. 스페이스바를 눌러도 한참 뒤에 재생됐다**

`play()` 가 `preloadAll(session.files)` 를 **await** 했습니다. 전부 디코딩될
때까지 플레이헤드가 멈춰 있었습니다.

이제 기다리지 않습니다. 준비된 것으로 바로 시작하고, 남은 스템은 룩어헤드가
받아 갑니다 — 늦게 도착한 클립은 올바른 오프셋으로 중간부터 들어옵니다.
시크해서 클립 중간으로 들어갈 때 스케줄러가 이미 하던 일과 같습니다.

재생이 필요한 파일만 디코딩합니다. 테이크 10개를 가져와 2개만 쓰는 세션이
나머지 8개를 디코딩하고 재생을 시작할 이유가 없습니다.

**2. 보컬 같은 특정 스템이 통째로 안 나왔다**

바이트 예산(700 MB)이 방금 디코딩한 스템을 도로 밀어냈습니다. 그러면
`scheduleClip` 이 버퍼를 못 찾고 **조용히 return** 합니다. 재생 중에는 아무것도
디코딩하지 않으므로, 한 번 건너뛴 클립은 그 테이크 내내 무음입니다.

- **열려 있는 세션의 파일은 절대 밀어내지 않습니다** (`pinFiles`). 열려 있는
  소재는 캐시가 아니라 작업물입니다. 예산은 아무도 참조하지 않는 파일에만
  적용됩니다
- 그래도 버퍼가 없으면 스케줄러가 **조용히 넘어가지 않고 디코딩을 요청**합니다.
  파일당 한 번만 (초당 50번 재시도하지 않도록)

**측정** — 4분 48 kHz 스테레오 8스템, Electron + Xvfb

| | 콜드 오픈 | 재생 시작 |
|---|---|---|
| before | 41.7 s | 매번 재디코딩 · 일부 스템 무음 |
| after | **12.1 s** | **0 ms · 빠진 스템 0/8** |

12.1 s 를 만든 것:

1. **PCM 을 IPC 로 보내지 않는다** (5.9 s → 1.4 s / 스템). 92 MB 를
   `ipcMain.handle` 반환값으로 돌려주면 구조화 복제에만 4.5 초가 듭니다 —
   FFmpeg 이 곡을 디코딩하는 데 걸리는 1.4 초의 세 배입니다. 이제 FFmpeg 이
   스크래치 파일로 바로 쓰고 렌더러가 `aimaster-local://` 로 스트리밍해서
   읽습니다. 프레임 수도 파일 크기에서 정확히 나옵니다
2. **동시 디코딩 3개**. 디코딩은 메인 프로세스의 FFmpeg 자식 프로세스이므로
   한 번에 하나씩 돌릴 이유가 없습니다. 3인 이유는 코어 수가 아니라 동시에
   메모리에 올라오는 곡 수 때문입니다
3. **온셋 검출을 지연시킨다**. 스템당 0.7 초짜리 모노 합산이 **그림을 그리는
   스레드**에서 돕니다. Tab to Transient 나 워프 에디터가 실제로 요구할 때
   찾고, 그다음부터 기억합니다

## 디코딩 메모리 — 지켜야 하는 규칙

48 kHz 스테레오 5분 곡 하나가 디코딩되면 **float32로 약 115 MB**입니다.
홈 큐는 최대 20곡이므로, 전부 한꺼번에 디코딩하면 2 GB가 넘는 요청이 한 번에
들어가고 렌더러 프로세스가 죽습니다. 렌더러가 죽으면 창은 자기
`backgroundColor`(`#09090b`)만 남습니다 — **에러 메시지 없는 검은 화면**의
정체가 이것입니다. 보고할 렌더러가 이미 없기 때문입니다.

`audio-cache.ts`가 강제하는 두 가지:

1. **디코딩은 순차적이다.** `decodeForDisplay` · `preloadAll` 은 한 번에 한
   파일만 처리합니다. `Promise.all(files.map(loadAudio))` 은 금지 — 최대 메모리가
   "캐시 + 한 곡"이 아니라 "세션 전체"가 됩니다.
2. **캐시 한도는 개수가 아니라 바이트다.** 5분짜리 12곡과 8마디 루프 12개는
   같은 개수이고 메모리는 100배 차이입니다 (`MAX_CACHE_BYTES` = 700 MB,
   `evictionPlan()` 이 순수 함수로 규칙을 들고 있습니다).

버퍼가 밀려나도 **피크 엔벨로프와 온셋 마크는 남습니다**(`getMeta`). 파형은
계속 그려지고 Tab to Transient도 그대로 동작하며, 샘플이 다시 필요해지는
순간에만 재디코딩합니다.

## MIDI 입력 캡처 — 건반을 꽂으면 연주가 파트가 됩니다

Key Editor 도, MIDI 2.0 모델도, 인스트루먼트도 이미 있었는데 **건반을 연결할
길이 없었습니다.** 노트를 전부 마우스로 찍어야 했고, `canRecord` 는
인스트루먼트 트랙을 대놓고 거절하고 있었습니다.

이제 인스트루먼트 트랙의 ● 를 누르면 건반이 열리고, REC 를 누르면 연주가
파트가 됩니다. 오디오 테이크와 **같은 플랜, 같은 카운트인, 같은 프리롤,
같은 펀치, 같은 루프 테이크 규칙**을 씁니다. 보컬을 녹음해 본 사람이 건반을
녹음하려고 새 규칙을 배울 이유가 없기 때문입니다.

### 노트는 이벤트가 아니라 짝입니다

버그가 사는 곳은 전부 이 짝짓기입니다. 네 가지를 정면으로 다룹니다.

| 상황 | 흔한 처리 | 여기서 하는 일 |
|---|---|---|
| 같은 건반이 떼기 전에 다시 눌림 | 피치로 짝지어 **한 개의 긴 노트**로 합쳐짐 | 채널:피치별 FIFO — 먼저 누른 쪽이 먼저 온 릴리스를 가져갑니다. 두 번 누르면 두 노트 |
| 테이프가 멈출 때 건반이 아직 눌려 있음 | 짝이 없어서 **버려짐** (테이크 마지막 코드가 사라지는 이유) | 테이크 끝에서 닫고, 몇 개가 잘렸는지 보고합니다 |
| 벨로시티 0 인 노트온 | 노트온으로 처리 → **영원히 안 꺼짐** | 노트오프로 읽습니다. 80년대 이후 모든 건반이 이렇게 보냅니다 |
| 페달을 밟은 채 건반을 뗌 | 건반을 뗀 순간 노트가 끝남 | 페달을 뗄 때 끝납니다. 페달은 컨트롤러가 아니라 **길이**입니다 |

페달이 잡고 있는 노트를 **같은 건반으로 다시 치면 새 노트**입니다. 이게
피아노가 실제로 하는 일이고, 이렇게 하지 않으면 페달 밟은 트레몰로가
한 음이 됩니다.

### 휠은 "울리고 있는 것"에 붙습니다

피치 벤드는 채널 메시지입니다. MPE 컨트롤러에서 그 채널은 노트 하나를,
평범한 건반에서는 코드 전체를 들고 있습니다. **두 경우가 같은 규칙**입니다 —
커브는 그 채널에서 울리고 있는 모든 노트에 들어갑니다. 페달이 잡고 있는
노트도 아직 울리고 있으므로 함께 받습니다.

노트 중간에 시작된 커브는 **첫 점을 노트 시작의 중립값에 박아 둡니다.**
그러지 않으면 노트가 시작하자마자 이미 휠이 올라가 있던 값으로 튑니다.

### 기록하지 않는 것은 말합니다

`pitchBend` · `pressure` · `timbre(CC74)` 만 노트 표현으로 남습니다. 나머지
CC 는 **재생하는 쪽이 없기 때문에** 기록하지 않고, 대신 무엇이 버려졌는지
`CC 1 미기록` 처럼 테이크 직후에 알려 줍니다. 모듈레이션 휠을 돌렸는데
아무 데도 없더라는 걸 나중에 발견하게 두지 않습니다.

이 저장소의 규칙 — **그리기만 하고 아무 일도 하지 않는 컨트롤은 만들지
않는다** — 이 여기서도 같은 모양입니다.

### 시계가 두 개입니다

Web MIDI 는 메시지마다 `performance.now()` 로 도장을 찍고, 트랜스포트는
`AudioContext.currentTime` 위에서 돕니다. 서로 다른 원점, 서로 다른
드리프트입니다.

`MidiTimebase` 는 녹음을 시작할 때 두 시계를 **한 번** 맞춰 두고 그 차이로만
변환합니다 (가능하면 `getOutputTimestamp()` 로, 없으면 두 값을 연달아 읽어).
메시지마다 시계를 다시 읽으면 코드 하나가 이벤트 루프 한 틱으로 뭉갭니다.

### 라이브 모니터링

건반은 들려야 연주할 수 있습니다. 들어온 노트온은 즉시 트랙의 인스트루먼트로
소리 납니다.

인스트루먼트 디스크립터는 **길이를 미리 알아야** ADSR 을 그립니다. 라이브
노트는 건반을 뗄 때까지 길이가 없습니다. 그래서 보이스를 긴 홀드로 띄우고
**자체 게이트 GainNode** 를 통해 채널로 보냅니다 — 노트오프는 그 게이트를
릴리스만큼 내리고 나서 보이스를 뜯어냅니다. 네이티브 노드만 씁니다.

CC 120 / 123 (all sound off / all notes off) 도 받습니다. 컨트롤러를 코드 도중
뽑았을 때 음이 영원히 남는 걸 막는 유일한 방법입니다.

### 무엇이 아직 안 되나

- **노트는 여전히 초 단위**입니다. 녹음한 파트도 템포 맵을 따라가지 않습니다
  (아래 남은 작업 1번과 같은 문제)
- 애프터터치는 모델과 에디터에는 남지만 내장 인스트루먼트 2종은 아직
  읽지 않습니다. 벤드와 CC74 는 실제로 소리가 바뀝니다
- 입력 퀀타이즈는 없습니다. 녹음 후 노트 도구의 퀀타이즈를 쓰세요
- 오디오 트랙과 인스트루먼트 트랙을 동시에 무장할 수 없습니다

## 다중 트랙 동시 녹음 — 밴드 한 번에

한 번에 한 트랙이었습니다. `canRecord` 가 두 트랙 무장을 대놓고 거절했고,
런타임은 캡처를 하나만 들고 있었습니다. 마이크 여섯 개짜리 드럼 킷을 녹음할
방법이 없었습니다.

이제 무장은 트랙마다 독립입니다. 오디오 트랙 여러 개 + 인스트루먼트 트랙까지
**같은 트랜스포트, 같은 테이프 0** 에서 함께 굴러갑니다.

### 트랙마다 자기 입력입니다

인터페이스 하나에 꽂힌 마이크 여섯 개는 **서로 다른 입력 여섯 개**입니다.
"입력 장치" 하나만 말할 수 있는 녹음 패널로는 밴드를 녹음할 수 없습니다.

무장한 오디오 트랙마다 자기 `getUserMedia` 스트림, 자기 장치, 자기 채널 수,
자기 미터를 가집니다. 트랙 4의 장치를 바꿔도 나머지 다섯은 끊기지 않습니다 —
다시 여는 건 그 트랙 하나뿐입니다.

### 테이프가 하나입니다

모든 캡처가 **같은 타이머 콜백 한 번**에서 시작합니다. 루프를 돌면서 하나씩
`start()` 를 부르면 몇 밀리초에 걸쳐 흩어지고, 트랙 1 은 맞는데 트랙 4 가 8ms
늦은 테이크는 밴드 테이크가 아닙니다.

건반도 같은 테이프 0 을 씁니다. `MidiTimebase` 를 그 순간에 앵커해서,
마이크와 건반이 같은 원점에서 출발합니다.

### 패스 하나가 편집 하나입니다

여섯 트랙을 따로 커밋하면 테이크 이전으로 돌아가는 데 Cmd+Z 를 여섯 번 눌러야
하고, 그 사이 다섯 단계는 **반쯤 녹음된 세션**입니다.

`commitPass` 가 세션을 트랙마다 꿰어서 **한 번** 돌려줍니다. 한 번의 undo 가
패스 전체를 되돌립니다.

### 한 트랙의 실패가 패스의 실패는 아닙니다

채널 4 의 마이크가 빠져 있었다고 나머지 다섯을 버릴 수는 없습니다. 트랙마다
독립적으로 커밋하고, 잘못된 건 **이름과 함께 보고**합니다:

| 상황 | 결과 |
|---|---|
| 무장했는데 테이프가 비어 있음 | 나머지는 커밋, `Mic 2: 녹음된 오디오가 없습니다` |
| 파일 쓰기 실패 | 나머지는 커밋, `Mic 2: 디스크가 가득 찼습니다` |
| 전부 비어 있음 | 이때만 에러입니다 (`passIsEmpty`) |
| 입력이 안 열린 트랙이 있음 | 녹음 자체를 거절하되 **어느 트랙인지 이름을 말합니다** |

여섯 개가 무장돼 있을 때 "입력이 열려 있지 않습니다" 는 어느 걸 봐야 하는지
아무것도 알려주지 않습니다. 그래서 하나면 이름을, 여럿이면 개수와 첫 이름을
말합니다.

### 건반은 무장한 인스트루먼트 트랙 전부로 갑니다

MIDI 입력은 하나인데 인스트루먼트 트랙이 둘 무장돼 있으면, **같은 연주가 둘
다에** 들어갑니다. 라이브 모니터링도 둘 다에서 소리 납니다. 피아노 밑에 패드를
깔 때 하는 일이 정확히 이겁니다. 캡처는 **한 번만 파싱**해서 공유하므로 두
트랙의 노트가 어긋날 수 없습니다.

### 한계는 말해 둡니다

`MAX_RECORD_TRACKS = 16`. 무장한 오디오 트랙마다 별도 `getUserMedia` 스트림과
워클릿이라, 브라우저는 이 한참 전에 힘들어합니다. **말해 둔 한계에서 깨끗하게
거절하는 것**이 말 안 해둔 한계에서 아홉 번째 테이크에 샘플을 흘리는 것보다
낫습니다.

### 어레인지 섹션 — 곡을 구간으로 편집합니다

"마지막 코러스를 두 배로" 와 "두 번째 벌스를 빼자" 는 **한 생각**인데, 클립
단위 편집기에서는 오후 반나절입니다. 이제 한 동작입니다.

### 마커는 점이고 구간은 범위입니다

마커 두 개로 범위를 흉내 내면 틈과 겹침이 생기고, "1:12 에 뭐가 있나" 에
답할 수 없는 편집기가 됩니다.

그래서 구간은 **시작만 저장합니다.** 끝은 다음 구간의 시작입니다. 이 결정 하나가
버그 한 종류를 통째로 없앱니다:

- **틈도 겹침도 표현 자체가 불가능합니다.** 동기화할 게 없습니다 — 끝이
  어디에도 저장돼 있지 않으니 어긋날 수가 없습니다
- **경계를 옮기는 건 편집 하나입니다.** 벌스와 코러스 사이의 선을 끌면 둘 다
  움직이는데, 그게 그 선을 끈다는 뜻입니다
- **모든 지점에 답이 정확히 하나입니다.** `sectionAt` 은 검색이 아니라 조회입니다

### 리플 편집은 전부 같이 움직여야 합니다

하나라도 빠지면 세션이 조용히 어긋나고, 세 번의 편집 뒤에야 드러납니다.

| 무엇 | 어떻게 |
|---|---|
| 클립 | 경계에서 **자르고** 옮깁니다. 컷 전체를 가로지르던 클립은 두 조각이 되어 이웃이 됩니다 |
| 오토메이션 | 안쪽 점은 오디오와 함께 사라지고, **잘린 자리에 그때의 값을 못 박습니다** |
| 마커 · 코드 | 같이 옮기고, 안쪽 것은 같이 사라집니다 |
| 구간 | 같이 옮기고, 잘린 구간의 경계도 같이 사라집니다 |
| **템포** | **비트로** 옮깁니다 |

**템포를 초로 옮기면 안 됩니다.** 템포 이벤트는 "비트 64부터 128" 이라고
말합니다 — 초로 옮기면 다른 비트에 앉게 되고, 그 뒤의 **모든 마디선이 다른
자리에** 떨어집니다. 테스트가 이걸 증명하는 방법: 리플 뒤에 그 이벤트의
**초가 정확히 리플 길이만큼** 움직였는지 봅니다. 비트로 옮겼을 때만 그렇게
나옵니다.

**박자 맵은 항상 따라갈 수 없습니다.** 박자 변경은 **마디**에 붙어 있어서 마디
단위로만 움직일 수 있습니다. 리플이 마디 단위가 아니면 박자 이벤트는 그대로
두고 **말합니다** — 틀린 마디로 반올림하지 않습니다.

### 세 가지 동작

| 동작 | 하는 일 |
|---|---|
| **복제** | 구간의 내용을 복사해 바로 뒤에 붙이고, 뒤의 모든 것을 밉니다. 클립 · 오토메이션 · 마커 · 코드 **그리고 그 구간 자신의 템포 변화까지** — 빨라지는 코러스는 두 번째에도 빨라집니다 |
| **잘라내기** | 구간을 **시간째로** 없앱니다. 곡이 짧아집니다 |
| **경계만** | 라벨만 지웁니다. 오디오는 그대로입니다 |

복제와 잘라내기는 곡 길이를 바꾸므로 **드래그가 아니라 버튼**입니다. 마우스가
한 번 미끄러져서 일어날 일이 아닙니다.

## 랙 프리셋 — 체인 전체를 한 이름으로

`내 프리셋` 은 **장치 하나**를 저장합니다. 이건 **체인**을 저장합니다 —
컴프레서와 EQ 와 리버브를, 각자의 슬롯에, 설정과 바이패스까지. 엔지니어가
"내 보컬 체인" 이라고 할 때 말하는 그것입니다. 인서트 랙 상단에서 저장하고
불러옵니다.

**슬롯은 소리의 일부입니다.** "컴프레서는 C 에 있다" 가 채널을 기억하는
방식이고, 불러올 때 A 부터 채워 넣는 랙은 그걸 부숩니다. 그래서 슬롯 번호를
그대로 저장하고 그대로 되돌립니다.

| 상황 | 하는 일 |
|---|---|
| **replace** | 트랙의 인서트가 **정확히 이 랙**이 됩니다 |
| **merge** | 랙이 언급한 슬롯만 덮어쓰고 나머지는 **그대로 둡니다** |
| 이 빌드에 없는 장치 | 건너뛰고 **이름을 말합니다.** 조용히 빠지면 디에서 없는 체인이 되고, 전부 거절하면 나머지 여섯을 잃습니다 |
| 랙에 없는 슬롯 번호 | 잘라 맞추지 않고 **거절**합니다 |
| 서드파티 플러그인 | 랙에 **담기지 않습니다.** 검증할 파라미터 목록이 없고, 플러그인이 없는 기계에서 조용히 사라지는 랙 파일이 됩니다 — 저장할 때 이름과 함께 알려 줍니다 |
| 빈 랙 저장 | 거절합니다. 빈 랙을 불러오는 건 "인서트를 전부 지워라" 인데, 빈 채널에서 저장을 누른 사람이 뜻한 건 그게 아닙니다 |
| 빈 랙 **불러오기** | 체인을 비웁니다. 랙을 지우는 유일한 방법이고, 이건 에러가 아닙니다 |

**사이드체인 소스는 따라가지 않습니다.** 저장한 세션의 버스를 가리키는 id 라,
불러온 세션에는 그 버스가 없습니다. 그대로 들고 가면 더커가 **엉뚱한 것을
키로 삼고**, 이건 믹스가 틀어질 때까지 아무도 못 듣는 유일한 실패입니다.

**레이턴시는 받는 쪽에서 다시 계산합니다.** 지연 보정이 그 숫자에 맞춰 채널을
정렬하므로, 저장할 때의 샘플레이트에서 계산된 값을 들고 가면 안 됩니다.

**인서트 id 는 새로 붙습니다.** 엔진이 플러그인 인스턴스를 id 로 찾기 때문에,
복사된 id 는 한 채널의 노브가 다른 채널의 장치를 움직이게 만듭니다.

이름 충돌은 **이름 변경**입니다 (컨트롤 서피스와 반대). 비슷한 이름의 랙 둘은
둘 다 쓸모 있지만, 한 페이더에 매핑 둘은 절대 아니기 때문입니다.
`.louirack` 파일로 내보내고 가져옵니다.

## 컨트롤 서피스 — 손으로 만지는 믹서

MIDI 입력은 있었지만 **건반으로만** 쓸 수 있었습니다. 페이더가 달린 컨트롤러를
꽂아도 노트만 들어왔고, 트랙을 무장해야만 포트가 열렸습니다.

이제 `Alt+K` 로 컨트롤 서피스 패널이 열립니다. 대상을 고르고 노브를 움직이면
연결됩니다.

### 픽업 — 이게 없으면 서피스를 뽑게 됩니다

물리 페이더는 0 에 있고 트랙은 −6 dB 에 있습니다. **앉을 때 둘이 같은 적은
없습니다.** 스치기만 해도 트랙이 유니티로 튀어 오르면 믹스가 망가집니다.

픽업 모드는 컨트롤이 **현재 값을 지날 때까지 아무것도 하지 않습니다.** 지나는
순간 넘겨받고, 그다음부터는 전부 따릅니다. 기본값이 픽업인 이유입니다.

첫 메시지만 예외입니다 — 지나온 위치가 없으니 **이미 거기 있을 때만** 잡습니다.
"이미 거기"는 7비트 컨트롤러의 **한 스텝 이내**입니다. 그보다 엄격하면 정확히
맞춰 둔 페이더가 영영 안 잡힙니다. 자기 스텝 사이의 위치를 보고할 방법이
없으니까요.

### 엔코더는 위치를 안 보냅니다

끝없이 도는 엔코더는 "왼쪽으로 세 칸"을 보냅니다. 그리고 그걸 표현하는 방식이
**두 가지**인데 와이어에서는 똑같이 생겼습니다:

| 인코딩 | 위로 | 아래로 |
|---|---|---|
| `signedBit` | 0x01…0x3F | 0x41…0x7F (비트 6이 부호) |
| `twosComplement` | 1…63 | 127…65 |

메시지 하나로는 구분이 안 되므로 **감지하지 않고 설정**으로 둡니다. 잘못
고르면 노브가 빠르게 반대로 돕니다 — "내 엔코더가 귀신 들렸다"의 정체입니다.
매핑 줄의 `SIGNED`/`2COMP` 로 바꿉니다.

### 버튼은 메시지를 두 번 보냅니다

누를 때와 뗄 때. 둘 다에 반응하는 토글은 **두 번 뒤집혀서 제자리로**
돌아옵니다. 그래서 릴리스는 의도적으로 무시하고, 무시했다는 것도 보고합니다.

### 활동 표시줄이 여기서 제일 쓸모 있습니다

들어오는 모든 메시지를 **무엇에 연결됐는지와 함께** 찍습니다.

```
CC 7 = 64 · ch1    → Vox · 볼륨
CC 21 = 100 · ch1  → 연결 안 됨
```

**"데스크는 말하는데 아무도 안 듣는다"** 는 서피스를 설정할 때 가장 흔하게
빠지는 상태이고, 이 줄이 없으면 보이지 않습니다.

### 포트는 무장과 무관하게 열려 있습니다

무장이 MIDI 포트를 열고 해제가 닫습니다 — 그대로 두면 트랙을 해제하는 순간
서피스가 죽습니다. 그래서 런타임에 **홀드**가 있습니다: 서피스가 포트를 잡고
있는 동안 `closeMidiInput` 은 트랙만 떼어냅니다.

### 페이더 한 번이 undo 한 번입니다

페이더는 초당 백 개씩 메시지를 보냅니다. 매번 커밋하면 undo 히스토리가
쓰레기가 됩니다. 그래서 메시지마다 트랜지언트로 적용하고, 페이더가 멎으면
(240 ms) 한 번 커밋합니다 — 오토메이션 제스처가 이미 쓰는 규칙입니다.

### 매핑은 데스크의 것이지 곡의 것이 아닙니다

같은 페이더는 어떤 세션을 열어도 트랙 1의 볼륨입니다. 프로젝트마다 스무 개를
다시 학습하는 것이 사람들이 컨트롤 서피스를 포기하는 이유입니다. 그래서
세션이 아니라 앱 설정 옆에 저장하고, `.louisurface` 파일로 내보낼 수 있습니다.

| 상황 | 하는 일 |
|---|---|
| 이미 매핑된 컨트롤을 다시 학습 | **교체**합니다. 학습을 누르고 이미 쓰던 노브를 흔든 건 "이걸로 바꿔"라는 뜻입니다 |
| 가져오기에서 컨트롤 충돌 | **교체**하고 몇 개를 교체했는지 말합니다. 한 페이더에 두 개는 절대 원한 게 아닙니다 |
| 같은 컨트롤에 매핑 두 개 | 패널이 **빨간 줄로 경고**합니다. 하나만 동작하는데 다른 하나가 고장난 것처럼 보이기 때문입니다 |
| 채널 지정 vs 모든 채널 | 채널을 지정한 쪽이 이깁니다. 굳이 "채널 3" 이라고 쓴 사람은 그걸 의도한 겁니다 |
| 삭제된 트랙을 가리키는 매핑 | 아무 일도 안 하고 **어느 것인지 보고**합니다 |

### 무엇에 연결할 수 있나

- **트랜스포트** — 재생/정지 · 정지 · 녹음 · 처음으로 · 루프. 메트로놈은 앱에
  없어서 **목록에 없습니다**
- **트랙 스위치** — 뮤트 · 솔로 · 녹음 무장 (세션의 토글러를 거치므로 솔로

- **연속 파라미터** — 오토메이션 레인이 가질 수 있는 대상 전부. 볼륨 · 팬 ·
  센드 레벨 · **플러그인 파라미터**까지 같은 목록입니다

## 픽처 — 영상에 맞춰 쓰기

세션은 영상을 **하나만** 가집니다. 제약이 아니라 결정입니다. 픽처에 맞춰
작곡하는 모든 DAW 는 픽처가 하나고, 두 번째 영상 트랙은 자기 뷰어와 자기
동기 정책과 "타임코드는 어느 쪽 것인가"에 대한 답을 각각 필요로 하는데,
그 질문들에는 음악적인 답이 없습니다.

### 영상은 오디오 그래프에 들어가지 않습니다

`<video>` 는 **음소거**이고 앞으로도 그렇습니다. 영상의 소리가 필요하면 보통
오디오 트랙으로 가져옵니다 — 그래야 트림도 페이드도 미터도 바운스도 다른
모든 것과 똑같이 걸립니다. 소리 나는 `<video>` 는 그 전부를 못 받는 두 번째
사운드 경로일 뿐 아니라, **두 번째 시계**이기도 합니다.

### 오디오 시계가 마스터입니다 — 언제나, 한 방향으로

트랜스포트는 `AudioContext.currentTime` 에 스케줄됩니다. `<video>` 는 자기
나름의 시간 감각과 키프레임 단위 탐색과 수십 밀리초의 시작 지연을 가진
디코더입니다. 그쪽이 앞장서서 좋을 일이 없으므로 앞장서지 않습니다.

순진한 버전은 한 줄입니다 — 매 틱마다 `video.currentTime = playhead`. 그리고
**볼 수가 없습니다.** 탐색은 디코드 파이프라인을 헐고 가장 가까운 키프레임에서
다시 세우기 때문에, 초당 스무 번 고치면 슬라이드쇼가 됩니다. 정작 고치려던
드리프트는 애초에 보이지도 않았고요.

그래서 보정은 사다리를 올라가고, 대부분의 경우 정답은 "아무것도 하지 않기"
입니다.

| 어긋난 양 | 하는 일 |
|---|---|
| 반 프레임 미만 | **유지.** 볼 게 없습니다 |
| 0.5초 미만 | **속도.** 간격이 닫힐 때까지 1–5 % 빠르거나 느리게. 2 % 속도 변화는 아무도 못 보고, 탐색은 누구나 봅니다 |
| 그 이상 | **탐색.** 진짜 뭔가 일어난 겁니다 — 로케이트, 루프 랩, 스톨 |

탐색이 진행 중일 때는 판단을 미룹니다. 아직 도착하지 않은 탐색은 옛날
`currentTime` 을 보고하고, 그걸로 판단하면 두 번째 탐색이 나오고, 세 번째가
나옵니다.

**픽처 밖에서는 정지합니다.** 마지막 프레임에 얼려 두면 크레딧 위에서
"아직 재생 중"처럼 읽히는데, 스코어링 세션이 절대 헷갈리면 안 되는 딱 하나가
그것입니다.

### 프레임은 초가 아닙니다

히트 포인트는 **프레임** 위에 있고, 프레임 레이트는 정수인 적이 거의 없습니다
— 23.976 · 29.97 · 59.94. 그래서 타임코드는 진짜 SMPTE 이고 드롭 프레임을
포함합니다.

29.97 은 초당 서른 프레임을 세지만 29.97 개만 받으므로, 논드롭 타임코드는
한 시간에 **3.6초**를 앞서갑니다. 드롭 프레임은 매 분 첫머리에서 프레임
**번호**를 건너뛰어 그걸 되돌립니다 — 열 번째 분은 예외입니다. 그림에서
버려지는 건 없고 라벨만 움직입니다.

```
프레임 1799 → 00:00:59;29
프레임 1800 → 00:01:00;02      ;00 과 ;01 은 쓰이지 않습니다
프레임 17981 → 00:09:59;29
프레임 17982 → 00:10:00;00     열 번째 분은 건너뛰지 않습니다
실시간 1시간 → 01:00:00;00 (DF) / 00:59:56:12 (NDF)
```

**한 시간의 타임코드는 한 시간의 초가 아닙니다.** 23.976 에서 `01:00:00:00`
은 86400 프레임이고 그건 3603.6초입니다. 실제 클립으로 확인했습니다 —
ffprobe 가 `startTimecodeSec: 3603.6` 을 돌려주고, 이건 테스트가 못 박아 둔
숫자와 같습니다.

### 프레임 레이트는 재는 것이지 추측하는 것이 아닙니다

`<video>` 엘리먼트는 길이는 알려 주지만 **프레임 레이트는 알려 주지 않습니다.**
그런데 스코어링에서 가장 중요한 숫자가 그겁니다. 23.976 과 25 는 4 % 차이이고,
90분 릴이면 4분입니다. 틀린 레이트 위에 찍은 히트 포인트는 뒤로 갈수록
점점 더 틀립니다.

그래서 ffprobe 가 답합니다(디코드 경로에 이미 번들되어 있습니다). `r_frame_rate`
가 아니라 **`avg_frame_rate`** 를 읽습니다 — 앞엣것은 타임 베이스라서 가변
레이트 폰 영상이면 600 이나 90000 으로 나오고, 그러면 모든 히트 포인트가
말이 안 되게 됩니다. 유리수 그대로 받아서(`24000/1001`) 한 번만 나눕니다.

### 창은 떠 있습니다

탭이 아닙니다. 스코어링은 편곡을 **하면서** 픽처를 보는 일이고, 보려고
타임라인을 떠나야 하는 픽처는 안 보게 되는 픽처입니다. 그래서 EDIT · KEY ·
MIX 어디에 있든 위에 떠 있고, 끄는 건 클릭 한 번입니다.

`Shift+Alt+P` 로 켜고 끕니다. `Shift+Alt+,` / `Shift+Alt+.` 는 **한 프레임씩**
움직입니다 — 23.976 에서 41.7 ms 이고, 아무도 넛지 값을 그렇게 맞춰 두지
않습니다. 픽처가 없으면 프레임 레이트도 없으므로 25 를 지어내지 않고
그렇다고 말합니다. 타임코드를 더블클릭하면 타이핑해서 그 프레임으로
갑니다 — 스포팅 노트에는 "문이 01:02:14:07 에 닫힌다"고 적혀 있으니까요.

추천 테스트는 "값을 만들어냈다"를 확인하지 않습니다. **측정 가능한 딱 한
가지만 다른 신호 두 개**를 만들어서, 설정이 그걸 따라 움직이는지 봅니다 —
6 kHz 치찰음과 9.5 kHz 치찰음에서 디에서 주파수가 옮겨가는지, −70 dB
플로어와 −50 dB 플로어에서 게이트 스레숄드가 각각 플로어 6 dB 위에 앉는지,
120 BPM 과 90 BPM 에서 딜레이가 250 ms 와 333 ms 가 되는지, 험이 있을 때
50 과 60 을 가르고 없을 때 거절하는지. **오디오가 움직여도 안 움직이는
추천은 프리셋**이고, 이 테스트가 그게 추천으로 출시되는 걸 막습니다.

템포 테스트가 확인하는 것: 램프 적분이 **40만 스텝 수치적분과 1e-7 안에서
일치**하는지, 비트↔초 왕복이 1e-9 안에서 정확한지, 시간이 절대 뒤로 가지
않는지, 6/8 마디가 4분음표 셋인지, 마디선이 맵이 말하는 자리에 정확히
떨어지는지, 아첼레란도에서 뒤쪽 마디가 실제로 좁아지는지, 스냅이 초가 아니라
비트 축에서 반올림하는지, 맵이 저장/로드를 견디는지, 그리고 **워프가 클립
위치의 맵을 쓰는지 + 두 클립이 다른 캐시 키를 받는지**.

오토메이션 테스트는 "뭔가 썼다"를 확인하지 않습니다. 페이더 라이딩을 샘플
단위로 재구성해서 커밋한 다음, **특정 시각에 레인을 다시 읽습니다** — 움직임이
만든 자리에 있는지, 패스 양옆의 오토메이션이 살아남았는지, touch 는 돌아오고
latch 는 안 돌아오는지, trim 이 밑에 깔린 모양을 지키며 옮겼는지, write 가
끝나고 스스로 무장해제했는지. 엔진이 읽는 `pointValueAt` 으로 읽으므로,
여기서 통과한 레인은 재생도 같습니다.

리버브 테스트가 **측정하는** 것: 슈뢰더 역적분으로 잰 RT60 이 카탈로그 값의
20 % 안에 드는지(전 공간), 모든 IR 의 에너지가 같은지(0.1 dB 안), Size 를
바꾸면 첫 반사가 그만큼 움직이는지, 댐핑이 정말 어두워지는지(밴드 에너지 비),
돌이 나무보다 저역이 오래 남는지, 게이트가 끊기고 리버스가 차오르는지,
플레이트와 스프링의 decay 노브가 진짜 초 단위인지, 그리고 **피치 시프터가
440 Hz 에서 880 Hz 를 만드는지**(괴르첼). 프리셋은 전부 실제로 렌더해봅니다 —
오타 하나가 처음 눌러보는 사람에게는 고장난 장치입니다.

프리셋 테스트가 확인하는 것은 "저장이 되나"가 아니라 **데이터가 틀렸을 때**
어떻게 되나입니다: 범위 밖 값이 당겨지는지, 없는 파라미터가 버려지는지, 깨진
저장소가 던지지 않고 빈 목록으로 읽히는지, 쓰기를 거부하는 저장소가 실패를
**말하는지**, 이 빌드에 없는 장치의 항목이 건너뛰어지며 이름이 나오는지,
이름 충돌이 둘 다 남기는지. 그리고 **장치 전부**를 저장 → 목록 → 불러오기
왕복시켜서 모든 파라미터가 자기 범위 안의 숫자로 돌아오는지 봅니다.

MIDI 입력 테스트는 건반 없이 **와이어 전체**를 돕니다. 가짜 포트를 만들어
실제 바이트를 흘려보내고 — 페달을 밟은 채 친 삼화음, 위쪽 노트 밑에서 돌린
휠, 떼기 전에 다시 누른 같은 건반, 테이프가 멈출 때 아직 눌려 있던 손 —
그게 파싱 · 짝짓기 · 커브 · 프리롤 컷 · 루프 패스를 지나 **파트 안의 노트로
같은 타이밍에 도착하는지**를 봅니다. 짝이 어긋나거나 페달이 무시되면 노트
개수나 길이가 바로 틀어지므로, 이 검사들은 조용히 통과할 수 없습니다.

호스트 테스트는 **진짜로 fork 합니다**. 진짜로 크래시하고 진짜로 멈추는 자식
프로세스를 만들어서, 각각이 예외가 아니라 에러로 돌아오는지 확인합니다. 그리고
렌더러 → 호스트 → 렌더러 왕복을 Electron 만 빼고 전부 실제 코드로 돌려서,
−6 dB · 위상 반전이 정말로 AudioBuffer 에 반영돼 돌아오는지 샘플로 봅니다.

엔진 테스트가 실제로 측정하는 것: 클립 게인, 페이더, 뮤트, 솔로, 팬,
포스트/프리 페이더 센드, Aux 리턴 합산, 인서트와 바이패스, 사이드체인 더킹,
페이드 커브, **지연 보정 정렬**(같은 클릭이 두 경로에서 같은 샘플에 도착하는지).

## 남은 작업

1. **MIDI 노트를 비트로** — 지금 노트는 초 단위로 저장돼 있어 템포 맵을
   따라가지 않습니다. 워프된 오디오는 따라갑니다. 이게 템포 트랙에서 가장
   먼저 이어져야 할 작업입니다
2. 오토메이션 대상을 **매크로**까지 — 플러그인 파라미터는 됩니다(위 참조).
   매크로는 값 하나가 여러 모듈의 여러 파라미터로 퍼지고 그중 어느 것도 단일
   AudioParam 이 아니라서, 퍼진 파라미터마다 곡선을 따로 만들어야 합니다
3. 장치별 `automatableParams` 넓히기 — 지금은 EQ 2종 · Trim · Delay ·
   Compressor · Reverb 입니다. 나머지는 장치마다 한 줄씩 붙이는 일이고,
   붙이지 않은 장치는 메뉴에 안 나옵니다
4. 서피스 피드백 — 지금은 **입력만** 받습니다. 모터 페이더를 되돌리거나 LED 를
   켜려면 MIDI 출력이 필요하고, Web MIDI 출력 포트를 여는 건 별도 작업입니다
5. 구간 순서 바꾸기 — 지금은 복제와 잘라내기만 있습니다. 코러스를 브리지 앞으로
   **옮기는** 건 잘라내기와 삽입을 한 편집으로 묶는 별도 작업입니다
6. Spot 모드 다이얼로그 (Grid/Slip/Shuffle은 동작)
7. 트랙별 입력 설정을 세션에 저장 — 지금은 앱을 다시 켜면 기본 입력으로
   돌아갑니다
8. 영상의 오디오를 한 번에 가져오기 — 지금은 영상과 그 소리를 각각
   불러와야 합니다. ffmpeg 가 이미 둘 다 읽으므로 배선만 남았습니다
9. 픽처를 타임라인에서 끌어 옮기기 — `startSec` · `offsetSec` 는 모델에
   있지만 뷰어에서 바꿀 수 있는 것은 프레임 레이트뿐입니다
