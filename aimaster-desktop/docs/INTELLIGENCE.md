## 하나의 어휘

이 층의 모든 기능이 똑같은 것을 만들어 냅니다: **타입이 정해진 액션 목록**.
진단도, 오토 믹스도, 레퍼런스 매칭도, 자연어도 세션을 직접 건드리지 않습니다.

```ts
type IntelAction =
  | { kind: 'trackVolume'; trackId; db }
  | { kind: 'trackPan'; trackId; pan }
  | { kind: 'macro'; trackId; macroId; value }
  | { kind: 'insertParam'; trackId; pluginId; paramId; value }
  | { kind: 'addInsert' | 'removeInsert' | 'bypassInsert'; … }
  | { kind: 'automation'; trackId; target; points }
  | { kind: 'reharmonize'; options }
  | { kind: 'writeNotes'; trackId; clipId; notes; mode }
```

이 제약이 층 전체를 믿을 수 있게 만듭니다.

* **전부 미리 볼 수 있습니다.** 액션은 적용 전에 문장으로 설명되므로, 사용자가
  무슨 일이 일어날지 읽고 결정합니다.
* **전부 되돌릴 수 있습니다, 공짜로.** UI가 쓰는 것과 같은 `apply()` 를 지나므로
  지능적 동작 하나가 undo 하나입니다.
* **전부 테스트할 수 있습니다.** 제안 엔진은 *측정값 → 액션* 의 순수 함수라
  테스트에 오디오도 I/O도 없습니다.
* **자연어 프론트엔드는 교체 가능합니다.** 오늘은 규칙 파서가 이 액션을 만들고,
  내일 모델이 만들어도 아래쪽은 아무것도 바뀌지 않습니다.

한 문장으로 설명할 수 없는 액션은 여기 들어오지 않습니다.

## 12 · 16. AI Analyze / Problem Detection

미터는 **숫자**를 말합니다. 진단은 **그 숫자가 문제라고** 말하는데, 그건 다른
주장입니다 — 임계값이 필요하고, 그 임계값이 존재하는 이유가 필요하고, 그리고
대부분의 도구가 건너뛰는 부분, **적용 가능한 수정**이 필요합니다.

그래서 모든 발견은 세 가지를 함께 들고 다닙니다.

| | |
|---|---|
| **측정값** | 사용자가 판정에 반박할 수 있도록 |
| **이유** | 왜 그 숫자가 중요한지, 한 문장 |
| **수정** | 액션 목록, 혹은 정직하게 제안할 게 없으면 없음 |

**수정이 없는 발견도 보고할 가치가 있습니다** ("좌우가 위상 상쇄 중입니다").
하지만 수정이 추측인 발견은 침묵보다 나쁘므로, 그런 것들은 `actions: []` 로
나가고 대신 무엇을 확인해야 하는지 말합니다.

검출 항목: 트루 피크 초과, 라우드니스 타깃 이탈, 과압축/과다 다이내믹, 위상
상쇄, 과도한 모노, 200–450 Hz 뭉침, 2–5 kHz 거침, 고역 부족 — 그리고 트랙별로
클리핑, 위상, 저역 실종(킥/베이스인데 저역이 없음), 치찰음, 묻힘, 무음.

## 13. AI Mix

여기서 하는 주장은 **일부러 작습니다.** 곡을 믹스하지 않습니다. 기계적이고,
모든 엔지니어가 먼저 하고, 측정값에서 실제로 계산 가능한 세 가지만 합니다.

**BALANCE** — 각 요소를 역할이 보통 앉는 자리 근처로. 페이더 위치가 아니라
**LU 로** 재는데, 무엇이 녹음됐는지 모르면 페이더 위치는 아무 의미가 없기
때문입니다.

**MASKING** — 같은 대역에서 싸우는 두 트랙을 찾아, 역할 우선순위에서 지는 쪽을
겹치는 주파수에서 좁게 깎습니다. 두 스펙트럼 모두 **레벨 정규화**되어 있으므로
"둘 다 여기가 크다"는 각자 자기 기준으로 크다는 뜻입니다 — 그게 마스킹의 실제
정의입니다. 조용한 패드와 큰 킥은 킥이 더 크다는 이유만으로 서로를 가리지
않습니다.

**SPREAD** — 중복된 역할을 센터에서 떼어 놓습니다. 가운데 두 대의 기타는 같은
자리에 있는 두 대의 기타이고, 해법은 EQ가 아니라 기하학입니다.

**하지 않는 것**은 취향입니다 — 리버브 선택도, 컴프레션 캐릭터도, 편곡 의견도
없습니다. 모든 이동에 상한이 있고, 모든 이동이 자기를 만든 측정값을 밝히므로
틀린 추측은 눈에 보이고 거절이 쌉니다.

> 이름을 알아보지 못한 트랙은 **건드리지 않습니다.** 감으로 페이더를 움직이는
> 것보다 안 움직이는 게 낫습니다.

## 14. AI Master

마스터링은 "이게 어떤 소리여야 하는가"에 방어 가능한 답이 있는 유일한 곳입니다.
납품 타깃이 숫자이기 때문입니다 — 라우드니스, 실링, 톤 밸런스, 폭.

그래서 오토 마스터는 취향을 추측하지 않고, 믹스가 **있는 곳**과 타깃이 **말하는
곳** 사이의 거리를 계산해 그걸 닫는 **가장 작은 체인**을 제안합니다.

순서는 고정입니다. 그게 작동하는 순서이기 때문입니다.

```
EQ → Compressor → Width → Limiter
```

밸런스를 먼저 고쳐야 뒤의 것들이 올바른 것에 반응하고, 폭은 레벨이 안정된 뒤에
잡고, 리미터는 피크를 만드는 모든 것 뒤에 옵니다.

**측정값이 "이미 괜찮다"고 하는 단계는 추가하지 않습니다.** 바이패스된 플러그인
다섯 개는 마스터가 아니라 잡동사니입니다.

타깃은 프리셋(Streaming −14 / Club −8 / CD −11) 또는 **레퍼런스 트랙**입니다.
레퍼런스가 언제나 이깁니다 — 그건 사용자가 원하는 실제 소리를, 측정한 것이니까요.

## 17. Reference Intelligence

REFERENCE 창은 이미 "내 믹스가 이 트랙과 어떻게 다른가"에 답합니다. 문장으로요:
80 Hz 근처를 2 dB 깎으세요, 리미터를 푸세요, 사이드를 넓히세요. 유용함에서 한
걸음 모자랍니다 — 사용자가 가서 **직접 해야** 하니까요.

이 모듈이 그 간극을 닫습니다. **같은 `ReferenceComparison`** 을 받아 각 행을 그
차이를 닫는 동작으로 바꿉니다. 이동 크기는 차이 크기에서 나오고, **상한이
있어서 나쁜 레퍼런스가 믹스를 망칠 수 없습니다.**

한 규칙이 이걸 정직하게 유지합니다: **이미 "일치"인 행은 아무것도 만들지
않습니다.** 도구의 일은 간극을 닫는 것이지, 없는 간극에 대해 의견을 갖는 게
아닙니다.

## 18. 자동 Automation

두 가지 일, 둘 다 계산할 만큼 기계적이고 손으로 하기엔 지겨운 것들입니다.

**RIDING** — 벌스 내내 6 dB 흔들리는 보컬을 자기 중앙값 쪽으로 되돌립니다.
절대 타깃이 아니라 **트랙 자기 자신의 중앙값**인 이유는, 연주를 스스로와
일관되게 만드는 게 목적이고 절대 타깃은 그냥 페이더 이동이기 때문입니다.

**DUCKING** — 킥마다 베이스가 비켜 줍니다. 사이드체인 컴프레서로 라이브로 하는
대신 오토메이션으로 **찍어 냅니다**.

### 왜 컴프레서가 아니라 오토메이션인가

**오토메이션은 보이고 편집됩니다.** 컴프레서의 결정은 보이지 않고 렌더할 때마다
다시 내려집니다. 그려진 곡선은 들여다보고, 동의하지 않고, 손으로 밀 수 있습니다.
라이브 반응이 필요한 경우를 위해 엔진에는 이미 사이드체인 컴프레션이 있습니다 —
이건 다른 도구입니다.

곡선을 음악적으로 유지하는 세 규칙: **상한**(폭주하는 라이딩은 안 하느니만
못합니다), **슬루 제한**(음절이 아니라 프레이즈를 탑니다), **씨닝**(나중에 손으로
고칠 수 있게).

## Riff Machine

### 스케일에 맞는 노이즈도 노이즈다

쉬운 버전의 이 기능은 스케일에서 아무 음이나 고르고, 그건 쓸모가 없습니다.
리프와 무작위 행보를 가르는 건 모든 작곡가가 생각 없이 지키는 짧은 규칙 목록이고,
그것들은 전부 계산 가능합니다.

| 규칙 | 없으면 |
|---|---|
| **화성** — 강박은 코드 톤, 약박은 경과음 | "조성 안"과 "코드 위"의 차이가 사라짐 |
| **윤곽** — 프레이즈는 어디로 갔다가 돌아온다 | 곡이 아니라 연습곡 |
| **성부 진행** — 기본은 순차, 도약은 반대 방향 순차로 해소 | 아무도 못 부르는 멜로디 |
| **반복** — 리프는 모티프 + 변형이지 새 16마디가 아님 | 서로 무관한 네 마디 |

### 고르지 않고 채점한다

각 온셋에서 가능한 모든 음을 **채점하고 최고점을 고릅니다** — 윤곽이 원하는
음역과의 거리, 앞 음과의 음정, 도약 후 해소 보너스를 저울질합니다. "합법적인"
음 중에서 무작위로 뽑는 것이 바로 스케일에 맞는 노이즈를 만드는 방식입니다.

### 테스트가 잡은 세 가지

* **반복이 화성을 넘어 복사되고 있었습니다.** 뒷마디가 앞마디의 음정을 사후에
  덮어쓰는 방식이었는데, 그 사이 코드가 바뀌면 C에서 코드 톤이던 음이 F 위에
  얹혔습니다. 이제 반복은 **같은 후보군 안에서의 편향**이라, 채점이 이미 코드
  톤을 강제하므로 화성을 벗어날 수 없습니다.
* **도약 제한이 점수만으로는 지켜지지 않았습니다.** 윤곽이 세게 당기면 −20점
  페널티가 져서 15반음을 뛰었습니다. 이제 **후보군에서 아예 걸러냅니다** —
  점수로 말릴 수 있는 것이 아니라 선택지가 아니어야 합니다.
* 같은 방향 연속 도약에 페널티를 넣었습니다. 음역 끝으로 달아나고 실수처럼
  들립니다.

### 변형

이조(다이어토닉) · 반전 · 역행 · 엇박 이동 · 솎아내기 · 조밀하게. 전부 스케일
안에 머무는데, **조성을 벗어난 변형은 이 아이디어의 변형이 아니라 다른
아이디어**이기 때문입니다.

역행은 **리듬을 두고 음정만** 뒤집습니다. 리듬이 리프의 정체성이라, 그것까지
뒤집으면 다른 리프가 됩니다.

### 통합

코드는 세션의 코드 트랙에서 파트의 시계로 옮겨옵니다 — 파트가 시작될 때 **이미
울리고 있던 코드**도 0초에 실어 옵니다. 마디 수는 파트 길이에서 나오므로 리프가
파트를 채우고 넘치지 않습니다.

생성 결과는 다른 모든 제안과 같은 `Suggestion` 으로 도착하고, **확신도 0.45 로
체크가 해제된 채** 나옵니다. 생성기는 출발점이지 답이 아닙니다. 패턴에 링크된
파트라면 쓰기가 패턴을 고치므로 **모든 배치가 함께 바뀝니다**.

## 15. Natural Language Control

> "보컬 좀 더 앞으로", "킥 2dB 올려", "여기 코드 좀 재즈스럽게 바꿔"

**결정론적 의도 파서**이고, 그렇게 부르는 게 중요합니다. 언어 모델이 아니고
그런 척하지도 않습니다 — 대상·동사·양의 작은 문법을 매칭하고, **못 알아들으면
추측하는 대신 그렇게 말합니다.** 남의 믹스에서 페이더를 움직이는 도구에게
"이해하지 못했습니다"는 그럴듯한 틀린 동작보다 훨씬 나은 실패입니다.

중요한 설계 결정은 **이음매**입니다. 파서의 출력이 `IntelAction[]` — 오토 믹스와
오토 마스터가 내놓는 것과 같은 어휘 — 이므로, 모델이 이 파일을 통째로 대체해도
아래쪽은 아무것도 바뀌지 않습니다. 미리보기도, undo도, 설명도, 테스트도 그대로
동작합니다.

### "앞으로" 는 컨트롤 하나가 아니다

엔지니어에게 이 말을 하면 레벨을 조금 올리고, 프레즌스를 조금 올리고, 공간을
조금 줄입니다. 그래서 파서도 그렇게 합니다. 한 제스처가 세 액션이 되고, 셋 다
설명되어 나옵니다.

### 언어 모델 — 파서가 진 자리에서만

이음매는 비워 둔 채로 두는 게 아니라 쓰라고 만든 것이므로, 이제 그 자리에
Claude 가 들어갑니다. **파서를 대체하지 않고 뒤에 섭니다.**

```
"보컬 2dB 올려"           → 규칙 파서가 즉시 해석. 아무것도 밖으로 안 나감
"보컬이 좀 답답한데 뚫어줘" → 파서가 모른다고 말함 → 모델이 브리핑을 읽고 제안
```

이 순서가 설계 전부입니다. 흔한 문장은 **네트워크도, 비용도, 대기도 없이**
처리되고, 모델은 결정론적인 쪽이 이미 "모르겠습니다"라고 말한 순간에만
불립니다 — 근사가 값어치를 하는 정확히 그 지점입니다.

#### 모델은 아무것도 편집하지 않는다

모델이 내놓는 것은 세션 수정이 아니라 **같은 `IntelAction` 목록**이고, 그
목록은 `parsePlan` 을 먼저 지납니다.

| 검사 | 통과 못 하면 |
|---|---|
| 트랙 id 가 이 세션에 있는가 | 거절 — 어떤 id 였는지 말하고 |
| 장치 id 가 레지스트리에 있는가 | 거절 |
| 그 장치에 그 파라미터가 있는가 | 거절 |
| 매크로가 일곱 개 중 하나인가 | 거절 |
| 숫자가 유한한가 | 거절 (NaN 페이더는 믹스에 뚫린 구멍입니다) |
| 값이 **그 장치의** 범위 안인가 | 범위로 자르고 **잘랐다고 말함** |
| 인서트를 뺄 슬롯이 비어 있지 않은가 | 거절 |

**버려진 동작은 전부 화면에 나옵니다.** 넷 중 셋이 검증에서 탈락한 계획을
"이해했습니다"로 읽게 두는 것이 이 파일이 막으려는 실패입니다.

그래서 환각이 할 수 있는 일은 두 가지뿐입니다 — 거절당하거나, 사용자가 문장으로
읽고 거절하는 합법적이지만 틀린 페이더 이동. 규칙 파서가 가진 노출과 **똑같습니다.**
프론트엔드가 바뀌었지 신뢰 경계는 그대로입니다.

#### 값은 전부 최종값이다

"2dB 올려" 는 `+2` 가 아니라 브리핑의 현재 볼륨에서 계산한 **최종 페이더 위치**로
옵니다. 같은 계획을 두 번 적용해도 두 번 움직이지 않고, undo 스택이 정직해집니다.

#### 키는 렌더러에 없다

렌더러는 세션과 서드파티 플러그인 UI 를 돌립니다. 거기 있는 키는 페이지에 있는
키입니다. 그래서 API 키는 **메인 프로세스에만** 있고, OS 키체인이 받쳐 주는
`safeStorage` 로 암호화해 저장하며, **돌려주는 IPC 채널이 아예 없습니다** —
설정과 삭제와 "있느냐"만 있습니다.

키체인이 없는 리눅스처럼 암호화가 불가능한 환경에서는 평문으로 쓰지 않고
**이번 실행에만** 들고 있으면서 그렇다고 화면에 말합니다. 믹싱 앱이 과금되는
자격 증명을 조용히 `~/.config` 밑 JSON 에 남기는 건 아무도 동의한 적 없는
거래입니다.

#### 캐시

장치 카탈로그 — 모든 플러그인의 모든 파라미터와 범위 — 가 프롬프트의 크고
안 변하는 절반입니다. 그건 캐시 구분점 뒤의 `system` 에 들어가고, 매번 달라지는
세션 브리핑은 메시지에 들어갑니다. 이걸 반대로 넣으면 요청마다 캐시가 빗나갑니다.
브리핑이 결정론적인지( `Date.now()` 하나가 섞여 들지 않았는지) 확인하는 테스트가
따로 있는 이유입니다.

### 실제로 잡은 버그

`'스'` 를 디에서 키워드로 두었더니 **`재즈스럽게` 안에서 매칭**됐습니다. 한 글자
키워드는 거의 모든 것에 걸립니다. 그래서 지금은 ASCII 키워드를 **단어 경계로**
매칭하고(`up` 이 `output` 에 안 걸리게), 한국어 키워드는 두 글자 미만을 두지
않습니다. 회귀 테스트가 남아 있습니다.

## 트랙별 레퍼런스 — "내 보컬을 쟤처럼 앉혀 줘"

위의 REFERENCE 는 믹스 대 믹스입니다. 이건 한 단계 아래이고, **거절로 시작합니다.**

> **보컬을 완성된 마스터와 비교할 수 없습니다.** 상용 믹스에는 60 Hz 에 킥이,
> 2 kHz 에 기타가, 12 kHz 에 심벌이 있습니다. 그 스펙트럼 차이를 "당신 보컬에
> 필요한 것"이라고 부르면 확신에 차고 구체적이며 완전히 틀린 EQ 가 나옵니다 —
> 그리고 **맞아 보입니다.** 그게 비싼 이유입니다.

그래서 레퍼런스가 무엇인지 묻습니다.

| 종류 | 무엇을 비교하나 |
|---|---|
| `stem` | 같은 역할의 솔로 트랙. 음색 · 다이내믹 · 폭. **레벨은 안 봅니다** — 스템의 절대 레벨은 아무 뜻이 없습니다 |
| `stemWithMix` | 그 스템 **과 그게 나온 믹스**. 여기서 레벨이 의미를 갖습니다 |
| `mix` | 완성된 마스터. **거절**하고, 이유와 함께 REFERENCE 창을 가리킵니다 |

### 레벨은 절대값이 아니라 관계다

사람들이 실제로 원하는 숫자는 이겁니다:

```
쟤네 보컬은 쟤네 믹스보다  4.2 LU 아래
내  보컬은 내  믹스보다  7.8 LU 아래
                        → 내 보컬 +3.6 dB
```

양쪽 스템의 절대 레벨은 서로 아무 관계가 없으므로, 관계만이 비교 가능합니다.

### 대역은 역할에서 나온다 — 잘라내는 게 아니라 없는 것

리드 보컬 비교표에는 **40 Hz 대역이 아예 없습니다.** 상한을 걸거나 가중치를 낮춘
게 아니라 목록에 존재하지 않습니다. 그래서 숫자가 뭐라고 하든 보컬에 40 Hz 이동을
제안할 방법이 없습니다. 킥에는 30 Hz 가 있고, 하이햇에는 1.5 kHz 아래가 없습니다.

### 양쪽 다 비어 있는 대역은 비교하지 않는다

두 킥이 12 kHz 에서 서로 다른 만큼은 **측정 노이즈**이고, 노이즈는 아주 확신에 찬
EQ 를 만듭니다. 그래서 자기 최대 대역보다 35 dB 아래인 대역은 "양쪽 다 에너지가
없습니다" 로 표시하고 점수에서도 뺍니다.

### 세 대역까지만

다섯 대역을 다 맞추는 건 믹싱이 아니라 **스펙트럼 복사**이고, 그 결과물은
레퍼런스처럼 측정되면서 어느 쪽 소리도 아닙니다. 그래서 차이가 큰 순서로 세 개만
움직이고, **남긴 대역의 이름을 말합니다.**

### 없는 방향으로는 제안하지 않는다

내 트랙이 레퍼런스보다 **덜** 다이내믹하면 아무것도 제안하지 않습니다. 트랙의
압축을 되돌릴 수는 없고, "다이내믹을 맞추려면 익스팬더"는 측정으로 위장한
추측입니다. 모노 레퍼런스에는 맞출 폭이 없으므로 폭 행 자체가 생기지 않습니다.

### 테스트가 고친 것

처음엔 "몇 개 옥타브에 에너지가 있는가"로 풀 믹스를 가려내려 했습니다.
**안 됩니다** — 재보니 보컬도 풀 믹스도 여섯 개로 나옵니다. 둘 다 완만하게
롤오프하는 곡선이라 그렇습니다(보컬 80 Hz 가 −12 dB, 풀 믹스가 −3 dB).

실제로 갈라지는 건 **양 끝을 동시에 가졌는가**입니다. 편곡에는 80 Hz 아래 킥과
10 kHz 위 심벌이 둘 다 있고, 보컬에는 둘 다 없고, 베이스는 아래만, 하이햇은
위만 있습니다. 지금은 두 끝을 봅니다. 이건 막지 않고 **한 문장 말할 뿐입니다** —
파일이 뭔지는 사용자가 압니다.

## 테스트

```
pnpm --filter @aimaster/desktop test:intel
pnpm --filter @aimaster/desktop test:nl
```

76개 + 37개 검사. 남의 믹스에서 페이더를 움직이는 기능은 **증명 가능하게 보수적이어야**
신뢰를 얻으므로, 테스트는 그걸 겨냥합니다.

* 모든 이동에 상한이 있는가 — 60 LU 차이를 줘도 6 dB 상한을 넘지 않는가
* 모든 액션이 설명되는가 — 여덟 종류 전부가 트랙 이름과 숫자를 말하는가
* **증거 없이는 발동하지 않는가** — 깨끗한 믹스는 심각 발견 0개, 이미 일치하는
  레퍼런스는 제안 0개, 모르는 지시는 액션 0개와 에러 하나
* 이름을 모르는 트랙은 건드리지 않는가
* 마스킹이 한 트랙을 두 번 깎지 않는가 (두 번째가 첫 번째를 덮어씀)
* 체인 순서가 EQ → Comp → Width → Limiter 인가 (실제로 적용해서 슬롯 확인)
* 파서가 아무것도 적용하지 않는가 (`interpret()` 전후 세션이 동일한가)

`test:nl` 은 거의 전부가 **공격**입니다 — 지워진 트랙, 없는 파라미터, +400 dB
페이더, 구현되지 않은 액션 종류, 배열 안의 `null`. 주장은 항상 같은 모양입니다:
거절되는가, 그리고 **소리 내어** 거절되는가. 나머지는 순서(규칙 먼저), 저하
(모델이 안 되면 파서 답을 이유와 함께), 그리고 브리핑이 같은 세션에서 같은
바이트인가입니다. 가짜 브리지를 주입하므로 **키 없이 오프라인으로 돕니다** —
자격 증명이 있어야 도는 테스트는 곧 안 도는 테스트입니다.

Riff Machine 은 **"노트가 나왔다"가 결과가 아니라서** 다른 잣대로 잽니다.

* 강박이 **전부** 코드 톤인가 (10/11 이 아니라 11/11)
* 상승 윤곽이 실제로 올라가는가 (앞 40 %와 뒤 40 %의 평균 음고 비교)
* 움직임의 40 % 이상이 순차이고, **한 옥타브를 넘는 도약이 없는가**
* 도약의 55 % 이상이 반대 방향 순차로 해소되는가
* 같은 시드가 같은 리프인가, 다른 시드는 다른 리프인가
* 반전이 모든 상승을 하강으로 바꾸는가, 역행이 리듬은 두는가
* 이조가 반음이 아니라 **음계 도수**로 움직이는가 (간격이 3과 4를 오가는가)

## 정직하게 말해 둘 것

진단 · 오토 믹스 · 오토 마스터 · 레퍼런스 · 오토 오토메이션 · Riff Machine 은
**측정과 규칙**입니다. 학습된 모델도, 클라우드 호출도 없습니다. 역할 추정은
키워드 매처이고 스스로 그렇게 말합니다. 레벨 프로파일은 엔지니어가 출발하는
숫자이지 법칙이 아닙니다. 그래서 오프라인이고, 즉각적이고, 결정론적입니다.

**클라우드를 쓰는 곳은 자연어 한 군데뿐이고, 거기서도 규칙 파서가 먼저입니다.**
키가 없으면 그 기능만 규칙 파서로 남고 나머지는 아무것도 달라지지 않습니다.

모델 호출 자체는 **키 없이 테스트할 수 없어 검증하지 못했습니다.** 검증한 것은
요청을 만드는 코드가 SDK 타입에 맞는다는 것과, 모델이 무엇을 돌려주든 `parsePlan`
이 막는다는 것입니다. 그래서 `strict: true` 를 켜지 않았습니다 — 스키마에 선택
속성이 있고 그걸 strict 가 받아 주는지 확인할 방법이 없는데, 틀리면 **모든** 요청이
깨집니다. 벽은 어차피 `parsePlan` 이고, 테스트가 실제로 두들기는 것도 그쪽입니다.
