## 3. Policy 통과율

```
Python adapter:  LUFS in tolerance ✓ 1/9 (11%) ─── (ballad only)
TS adapter:      LUFS in tolerance ✓ 3/9 (33%) ─── (acoustic, edm, lofi)
TP hard-ceiling: 9/9 통과 (✓) — limiter 둘 다 안전
LRA in band:     0/9 통과 — 양측 모두 다이내믹 범위 정책 미달
```

**해석:**
- **TS** 가 low-target 프리셋 (natural, -16 LUFS) 에서 잘 도달 — `loudnessMaximizer` 의 iterative push 가 효과.
- **Python** 은 ballad/warm 의 mid-target (-14 LUFS) 에서만 정확 — linear loudnorm 이 적당한 푸시를 함.
- **둘 다** loud-target (-8 ~ -10 LUFS) 에서 미달 — 양 측 chain 모두 정책 LUFS 까지 못 밀음.
- **LRA** 는 9개 모두 정책 범위 밖. 두 chain 모두 다이내믹을 정책보다 강하게 압축.

## 4. 핵심 발견 (M1.5)

### 4.1 합성 톤 vs 실제 음악의 격차

M1 (synthetic) 의 ΔLUFS 16.80 은 **artefact** 였다. 실제 음악-like 입력에서는 ΔLUFS 3.19 로 5× 줄어든다.

→ **결정**: M2 의 진짜 적합도 검증은 real-music fixture 로 한다. M1 synthetic 테스트는 sanity (limiter 안전 등) 용도로만 유지.

### 4.2 ISSUE-M1.5-A: Python 의 static loudnorm 이 dynamics-poor 입력에서 약함

M1 의 `ISSUE-M1-A` 가 본 테스트에서 정량 확정:
- 합성 사인 톤 (LRA=0) 에서 Python loud 프리셋 출력: −24.85 LUFS (target −10)
- 실제 EDM 픽스처 (LRA=2.70) 에서 Python loud 프리셋 출력: −11.07 LUFS (target −8)

⇒ Python static chain 의 "음압 푸시 능력" 이 입력의 LRA 에 비례한다. LRA < 3 인 입력에서는 사실상 동작 안 함.

**M2 결정 필요**:
- Option A: dsp-core 의 loudness-norm 모듈을 single-pass K-weighted iterative 로 통일 → 입력 dynamics 와 무관하게 타겟 도달.
- Option B: 정책으로 명시 — "라우드 프리셋은 LRA ≥ 3 입력에서만 보장" — 사용자에 노출.
- 우리는 **A** 권장 (M2 의 Rust dsp-core 가 어차피 단일 알고리즘으로 통일).

### 4.3 ISSUE-M1.5-B: 양 chain 모두 LRA 정책 미달

9/9 fixture 가 LRA 정책 (`lraMinLu`) 미달. 즉 **두 chain 모두 다이내믹을 정책보다 더 압축**한다.

원인 분석:
- Python: bus comp (ratio 1.6~2.2) + dynamic EQ + glue + loudnorm → cumulative ratio compression
- TS: gain staging (RMS target) + transient protection + iterative loudness max → loudness convergence 가 LRA 를 깎음

이는 **두 chain 모두의 설계 결함** 이거나 **정책 (target LRA) 이 너무 보수적** 이거나. M2 에서 결정:
- Option A: chain 의 다이내믹 보존 강화 (compressor ratio 한도 더 보수적으로, vocal_protection 확장)
- Option B: 정책 완화 (lraMinLu 를 3 → 2 등으로)

A 권장 — DSP 가 정책을 깎으면 안 된다.

### 4.4 ISSUE-M1.5-C: ai-harsh-mix 가 mastering 으로 LRA 회복 불가

ai-harsh-mix-01 의 pre-master LRA = 0 (의도된 brickwall). 마스터링 후에도 LRA = 0.

⇒ **마스터링은 다이내믹을 잃을 수만 있고, 회복할 수 없다.** 이는 본질적 제약 — 정책 (lraMinLu = 4) 은 비현실적.

**결정**: ai-harsh-mix 의 LRA 정책을 `lraMinLu: 0` 으로 완화. 본 fixture 의 목적은 LRA 회복이 아니라 **harsh peak 와 sub rumble 의 EQ 정리 및 TP 안전 확보** 임을 명시.

### 4.5 ISSUE-M1.5-D: TS 의 limiter 가 Python 보다 더 보수적

거의 모든 pair 에서 Δ TP < 0 (TS 의 TP 가 Python 보다 낮음). 즉 TS 의 `peakLimiter` (look-ahead + soft clip) 가 Python 의 `alimiter` 보다 더 깎는다.

이는 **TS 가 더 안전한 출력을 내고 있음** 을 의미 — 양호. 그러나 M2 에서 dsp-core 의 limiter 가 어느 동작을 기준선으로 할지 결정 필요.

### 4.6 ISSUE-M1.5-E: 입력 LUFS metadata 부정확

fixture metadata 의 `characteristics.preMasterLufsI` 가 실측과 크게 다른 경우 있음:
- `acoustic-fingerpick-01` metadata: -26 LUFS / actual: -33.32 LUFS
- `lofi-chill-01` metadata: -23 / actual: -28.71

⇒ informational 필드이므로 fail 은 아니지만 향후 metadata 자체 회귀 테스트 필요 (generator 출력 LUFS = metadata 가 일치하는지).

## 5. 카테고리별 분석

### kpop / hiphop / edm (loud 군)
- 양측 모두 target LUFS 미달.
- TS 가 Python 보다 +2 ~ +3 LU 더 라우드 — iterative maximizer 효과.
- TP 는 둘 다 ceiling 이내.
- **결론**: M2 에서 dsp-core 가 TS 의 iterative 방식 채택하면 target 도달.

### ballad / acoustic / lofi (natural / warm 군)
- Python: ballad 만 정책 통과 (warm preset).
- TS: acoustic / lofi 정확히 -16 LUFS 도달 (natural preset).
- **결론**: low-loudness 카테고리는 TS chain 이 이미 거의 동작. Python 의 `linear` mode 가 일부 fixture 에서 -2 LU 정도 over.

### female-vocal / male-vocal (vocal 군)
- 양측 모두 -14 → -11/-12 정도에서 멈춤.
- 원인: vocal_protection 의 `MAX_ENTRY_GAIN_DB=6 dB` 클램프가 vocal-range 입력에서 라우드니스 푸시 제한.
- **결론**: 의도된 동작. 그러나 정책이 -14 LUFS 라면 vocal protection 의 클램프와 충돌 — M2 에서 정책 vs 보호 합의 필요.

### ai-harsh-mix
- LRA = 0 유지 (회복 불가).
- LUFS 는 -11 (target -14) — 약간 너무 라우드 (입력이 이미 -5 LUFS, 마스터링이 -6 dB 정도만 깎음).
- 양측 모두 harsh peak 를 줄였는지는 스펙트럼에서 확인 필요 (현재 코드에 없음 — M2 에서 추가).
- **결론**: AI 마스터링 product 의 "rescue" 기능 검증 — 부분 동작.
